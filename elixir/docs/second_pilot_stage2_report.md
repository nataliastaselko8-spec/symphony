# Этап 2: сохранённая синхронизация статусов GitHub Projects

Дата: 2026-09-21. Статус: этап 2 выполнен в исходниках, полный `make all` пройден. Основание — [план второго пилота](second_pilot_implementation_plan.md).

## Что даёт этот этап

Controller получил механизм, который сохраняет намерение изменить статус карточки вместе с событием задачи. Если процесс остановится или ответ GitHub потеряется, намерение останется в журнале. Успех подтверждается повторным чтением карточки. Завершение цикла больше не обязано означать потерю незавершённой финальной синхронизации.

Выбран существующий delivery store и существующий процесс Runtime: именно controller уже владеет циклом, бюджетами и доказательствами PR/CI/deployment. Отдельный сервис или база данных здесь не нужны. Новая операция отделена от публикации комментариев, но использует тот же журнал и того же владельца записи.

Это основа для этапа 3. Обычные lifecycle-события и действия оператора пока не переведены целиком на новый механизм. Установленная Symphony, agent-runner, pins и GitHub не изменялись; новый пилот не запускался, issue #132 не использовалась.

## Реализация по пунктам плана

| Пункт | Что сделано и зачем |
| --- | --- |
| Роли статусов | Конфигурация принимает прежние четыре роли либо полный набор из семи. Добавлены `review`, `dev_validation`, `production_ready`. Проверяются уникальность названий и отсутствие новых ролей среди active/terminal. IDs берутся из схемы Project. |
| Событие и намерение | Команда `status_transition` атомарно применяет разрешённое событие и добавляет намерение. Целевой статус определяется ролью события, а не произвольной инструкцией агента. Новых инструментов записи для агента нет. |
| Сохраняемые данные | ID, номер и время события, причина, repo/cycle/task, исходный статус, целевая роль, актуальные PR/SHA/deployment/validation, наблюдаемый статус, ошибка, счётчики, сроки повторов и подтверждение. Начало работы не требует ещё не существующих PR/run. |
| Завершение и restart | Намерения находятся на уровне всего snapshot и сохраняются после переноса цикла в `last_cycle`. Ожидающая синхронизация блокирует новую задачу и автоматическое завершение controller после complete. Явный Stop сохраняет её для следующего старта. |
| Независимость от комментария | Новая операция меняет только статус; запись комментария не является её предварительным шагом. Runtime сериализует её с публикацией. Подключение существующего `project_block` и остальных производителей событий — этап 3. |
| Проверка перед записью | Сверяются scope, карточка, issue, исходный статус и доказательства соответствующего этапа. Перед mutation выполняется ещё одно чтение карточки и проверка разрешения controller. |
| Подтверждение и ошибки | Перед mutation сохраняется отметка отправки. После неё читается результат. Потерянный ответ не разрешает повторную mutation; изменённая вручную карточка или изменившиеся доказательства дают видимый конфликт. |
| Повторы и панель | Сохраняются backoff и rate-limit задержки; максимум три попытки mutation и десять завершённых сверок, deadline задачи — 60 секунд. Панель показывает цель, наблюдаемое значение, состояние, ошибку и время подтверждения. |
| Устаревшие события | Неотправленное событие, утратившее актуальность, получает `superseded`. Уже отправленное сверяется чтением. Порядок колонок не используется как версия состояния. |

Для `working` проверяются текущая база dev и разрешение запуска. Для handoff/review — назначенный открытый PR, CI на точных head/base SHA и native issue–PR linkage. Для post-merge — назначенный merged PR и включение merge SHA в dev. Для готовности к production дополнительно нужны успешный deployment и совпадение SHA/workflow/run/attempt с сохранённой положительной ручной validation.

Закрытая issue допустима только для подтверждённого post-merge результата. Само закрытие issue не доказывает завершение задачи и не открывает новый допуск.

## Совместимость

Старый журнал schema 1 воспроизводится без изменения формы состояния. Поле `status_sync` появляется только после новой явной команды; прежним completed-циклам не приписывается синхронизация задним числом. Повтор того же event ID не создаёт вторую операцию.

Расширенная конфигурация меняет scope fingerprint. Поэтому установка с четырьмя ролями требует проверяемого обновления профиля и состояния на последующих этапах. Это изменение нельзя вводить простой заменой конфигурации во время работы. Старый бинарник не понимает новые команды журнала — это также нужно учитывать при rollback.

## Что проверено

Целевые тесты проходят на реальных процессах Gate/Runtime и временных приватных Linux stores, с управляемыми ответами GitHub:

- Атомарное сохранение события и намерения, replay старого/нового snapshot, повтор event ID.
- Перезапуск после complete до отправки и после сохранённой отметки отправки при уже принятой GitHub записи.
- Потеря ответа mutation, сбой чтения после неё, ручной конфликт до/после записи.
- Временная недоступность API, rate limit, отказ в правах, исчерпание повторов.
- Изменение journal revision во время проверки, Stop, timeout и падение задачи синхронизации.
- Точная актуальность базы/CI/deployment и native linkage; закрытая post-merge issue.
- Новая синхронизация не запускает worker; ожидание статуса удерживает конкурирующую публикацию.
- Отображение неопределённости и подтверждения в панели, экранирование текста ошибки.
- Явная конфигурация семи ролей и отклонение неполного/неоднозначного набора.
