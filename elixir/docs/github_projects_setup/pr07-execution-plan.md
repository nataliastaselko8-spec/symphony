Дата: 2026-09-16. Статус: реализовано локально в `agent/feat/github-delivery-observer`; push и merge выполняет владелица.

**Результат:** конечный read-only observer, отдельный профиль `delivery_read`, проверка
закреплённых исходников/evidence и команда `mix github_projects.delivery.inspect`.
Пройдены `make all`: 445 Elixir tests, 0 failures, 6 skipped, 100% измеряемого покрытия,
8 Python store/crash tests, format, specs, Credo и Dialyzer. Живое чтение App подтвердило

[Описание реализации и запуск](../github_projects_delivery.md),
[описание для GitHub PR](pr07-description.md).

При реализации уточнены фактические данные GitHub: CI хранит head задачи отдельно от
проверенного merge SHA; jobs deployment используют несколько статических environments
`development*`. Эти связи проверяются по закреплённым исходникам и API. Контекст цикла
передаётся доверенным controller API; JSON диагностики не является командой для store.
Новая проверка Queue после ручного снятия паузы остаётся границей PR-10, как в плане ниже.

## Результат и границы

Symphony должна получать проверяемое наблюдение о текущей задаче, PR, ветке `dev`,
проверках CI и последнем подтверждённом deployment. Наблюдение объясняет, чего
ждёт цикл и какие сведения не удалось подтвердить. Оно потребуется PR-08 для
допуска и остановки worker, а PR-10 — для панели и действий оператора.

PR-06 сохраняет состояние и бюджеты. PR-07 добавляет источник проверенных фактов.
Успех deployment означает переход к ожиданию ручной проверки, а не разрешение
следующей задачи. Реальный запуск `github_projects` остаётся закрыт существующими
проверками startup, CLI и reload.

Изменения выполняются в `D:/symphony`, в личном форке
`nataliastaselko8-spec/symphony`, от `main`.
Ветка реализации: `agent/feat/github-delivery-observer`.
Локальная `main` при подготовке плана: `56b4fbb`, содержит merge PR-06.
Перед реализацией база и незакоммиченные изменения проверены.
Push и merge выполняются владельцем; upstream `openai/symphony` не является целью.

Приложение и база знаний в этот PR не изменяются. Из приложения читаются
утверждённые workflow и контракт PR-05. Код классификации причин падения CI,
автоматические reruns, публикация, действия с Queue и браузерные проверки сайта
в этот PR не входят.

## 1. Зафиксировать источники и проверяемый контракт

Проверить доступ к `EmotionStat/app` и Project `EmotionStat/1`, текущую `dev`,
сохранённый цикл PR-06 и настройки identity GitHub App.

Сопоставить локальные файлы приложения с принятой версией в GitHub:

- `.github/workflows/pr-ci.yml` — проверки до merge;
- `.github/workflows/verify.yml` — общий набор проверок;
- `.github/workflows/deploy-development.yml` — deployment;
- `.github/scripts/deployment-evidence-contract.json` — контракт версии 1;
- `.github/workflows/deployment-evidence.md` — описание producer PR-05.

Настройки наблюдателя задают repo, base `dev`, workflow paths и обнаруженные IDs,
разрешённые события, ожидаемую среду `development`, версию и отпечаток принятого
контракта. Числовые workflow IDs определяются через GitHub, не угадываются.
Контракт берётся из явно принятого immutable commit приложения; кандидат задачи
не может сам уменьшить список обязательных проверок своим изменением JSON.
Изменение обязательных jobs/steps требует review и явного обновления контракта.

Проверки и время deployment сохраняются раздельно. Существующие пределы
60 минут исходной работы, 60 минут исправлений, 2 исправления, 6 CI-попыток,
2 повтора на SHA и timeout `verify` 20 минут в PR-07 не пересматриваются.

Новые параметры входят в restart-only контракт PR-06. Несовместимый старый scope
не заменяется пустым состоянием. Если понадобится изменение формата snapshot,
сначала описывается явная совместимость/миграция; автоматического сброса нет.

## 2. Добавить профиль credentials только для чтения delivery

В текущем коде `projects_read` содержит Projects/Issues/Contents/Metadata read,
но не Actions и Pull requests. Общий профиль `github` включает write-права и для
наблюдателя не подходит. Добавить отдельный профиль `delivery_read`:

| Repository permission | Уровень | Назначение |
| --- | --- | --- |
| Metadata | read | Проверить identity репозитория |
| Contents | read | Прочитать ref, коммиты и принятые workflow |
| Pull requests | read | Состояние и связь текущего PR |
| Actions | read | Runs, попытки, jobs и артефакты |

Project продолжает читаться существующим `projects_read`. Оба профиля используют
одну выбранную App/installation, ограничены `EmotionStat/app`, имеют отдельные
ключи кэша по permissions и получают обновление installation tokens через PR-03.
Наблюдатель не получает Actions write или доступ к произвольному repo.

При живой проверке подтвердить permissions реально выданного токена и чтение
каждого нужного API. Ошибку 403/404 не трактовать как отсутствие PR или deployment.
Если App не имеет нужных read-grants, показать точный недостающий доступ; ключ
остаётся на controller и не выводится в отчёт или логи.
Чтение runs и артефактов поддерживает installation token с Actions read.
См. [GitHub: workflow runs](https://docs.github.com/en/rest/actions/workflow-runs#list-workflow-runs-for-a-repository)
и [GitHub: artifacts](https://docs.github.com/en/rest/actions/artifacts#download-an-artifact).

## 3. Сделать ограниченный клиент наблюдения

Добавить именованные операции для repo/ref, PR, сравнения коммитов, workflows,
runs, конкретной попытки, jobs и артефактов. Использовать существующее обновление
credentials; не добавлять универсальный GitHub-инструмент для worker.
REST-запросы — GET; GraphQL — только заранее определённые запросы чтения Project.

Все коллекции читать по страницам с проверкой формы ответа, повторных страниц,
курсоров и полноты. Ошибка поздней страницы аннулирует положительный результат
всего наблюдения. `nil`, пустая страница после ошибки и HTTP 404 не означают `idle`.

Предлагаемые начальные пределы для пилота:

| Ограничение | Значение | Что происходит при достижении |
| --- | --- | --- |
| Один API-запрос | 30 секунд | Наблюдение остаётся неподтверждённым |
| Один конечный проход сверки | 5 минут | Возврат частичного диагностического результата |
| Страница | До 100 элементов | Продолжить по валидной следующей странице |
| Одна коллекция | До 100 страниц | `observation_incomplete`, без положительного допуска |
| ZIP артефакта | До 5 MiB фактически прочитанных байтов | Отклонить превышение |
| JSON после распаковки | До 2 MiB | Отклонить превышение |

Это пределы работы reader, не бюджеты агента и не запуски CI. Для временного
сетевого сбоя разрешить один повтор GET в пределах общего deadline. При rate limit
вернуть время следующего допустимого чтения с учётом GitHub headers; не держать
Codex-сессию и не делать частые запросы. PR-08 организует периодическое наблюдение.
Версию REST API закрепить и проверить совместимость, не менять попутно старые
GitHub trackers.

## 4. Проверить владельца и PR

Начинать с сохранённых owner/item/issue/branch/PR из PR-06. Проверить repo ID,
PR ID/номер, head repo/ref/SHA, base ref `dev`, признак merge и merge SHA.
Связь issue с PR подтверждается сохранённой ассоциацией и проверенными метаданными;
одного заголовка или `Closes #...` недостаточно. Создание связи относится к PR-09.

Отличать открытый PR, draft, закрытый без merge, merged, изменённую базу и
неоднозначную связь. Новый head отменяет применимость проверок предыдущего head.
Закрытие без merge, `Done`, удаление/архивирование карточки не освобождают цикл.

Просматривать необходимые открытые PR и блокирующие карточки независимо от
pilot `item_ids`. Наблюдение продолжается даже без карточек Ready for agent.
Чужой PR не становится задачей агента автоматически; блокировка возникает при
неоднозначном владении, относящемся к циклу конфликте или изменении общей среды.

## 5. Проверить актуальную dev и результаты PR CI

Прочитать текущий dev SHA. Для merged PR проверить включение его результата
в историю текущей dev; учитывать squash/rebase merge по результату PR API,
не требовать наличия исходного feature head как предка после squash.
Исчезновение принятого merge из истории требует решения оператора.

Для PR CI сверять workflow identity, событие, PR, head/base и конкретный run/attempt.
У pull_request-проверок может использоваться синтетический merge commit:
явно различать SHA исходной ветки, тестируемого merge ref и целевой dev.
Не привязывать проверку к задаче лишь по имени check или совпавшему заголовку.

Наблюдение существующей зарезервированной попытки связывается с ней один раз.
Повтор чтения не увеличивает счётчик. Ручные и внешние попытки сохраняют отдельное
происхождение; reader не создаёт задним числом разрешение на автоматическую попытку.
Если связь reservation ↔ run/attempt неоднозначна, результат остаётся unknown.
Отмена CI не считается подтверждённым сетевым сбоем и не разрешает rerun.

## 6. Выбрать актуальную deployment-попытку

Нельзя ограничиваться первым зелёным run текущего SHA. Проверить ожидаемый
development workflow и все релевантные runs, в том числе другие SHA и старые runs,
для которых позже запустили rerun. `created_at` старого run не доказывает,
что его новая попытка не могла повлиять на среду.

Для пилота выполнять полное ограниченное перечисление runs целевого workflow
без отсечения лишь по head SHA или возрасту; дополнительно читать сохранённые run IDs.
Дедуплицировать по ID и сверять последние `run_attempt`, status и времена выполнения.
Если история не укладывается в лимит и полнота не доказана, сохранить блокировку.
Оптимизация истории возможна позже с доказанной границей наблюдения.

У GitHub для отфильтрованного поиска runs документирован предел 1000 результатов.
Он не является доказательством полной истории; reader не должен объявлять её полной
после усечения. [GitHub: list workflow runs](https://docs.github.com/en/rest/actions/workflow-runs#list-workflow-runs-for-a-workflow).

Новый pending/failed run для того же SHA отменяет прежнюю готовность. Незавершённая
или более поздняя попытка другого SHA, способная менять ту же среду, тоже блокирует
положительное решение. Старый запуск можно исключить из таких блокировок только
при подтверждении, что он не менял среду или его изменения перекрыты более поздним
полным подтверждённым deployment. Отсутствие отчёта не является таким подтверждением.

Jobs читать через endpoint конкретного run/attempt; не объединять зелёные jobs
разных попыток. Partial rerun без полного доказательства текущей попытки остаётся
неподтверждённым, с предложением оператору выполнить полный повтор.
См. [GitHub: jobs for an attempt](https://docs.github.com/en/rest/actions/workflow-jobs#list-jobs-for-a-workflow-run-attempt).

## 7. Скачать и независимо проверить evidence

Найти единственный подходящий `development-evidence-<run_id>-<run_attempt>` и
`development-evidence.json` внутри него. Проверить artifact ID, run/repo/head
metadata, срок доступности, digest и фактический размер. Проверка SHA-256 делается
для байтов формата, описанного GitHub; поддержку проверить на настоящем артефакте,
не подменять сравнением хеша распакованного JSON с хешем ZIP.

Download API возвращает краткоживущий redirect. Токен передаётся только API GitHub;
переход к проверенному HTTPS storage URL выполняется без Authorization. Запретить
произвольные адреса, локальные endpoints и бесконечные redirects; signed URL с query
не писать в логи. Архив читать без извлечения в workspace, с ограничением размера,
числа файлов и путей; отклонять дубликаты JSON, symlinks и опасные пути.
Основание: [GitHub: download an artifact](https://docs.github.com/en/rest/actions/artifacts#download-an-artifact).

Проверить JSON schema v1, repo, workflow/ref/event, SHA, current_dev_sha, freshness,
run/attempt и обязательные jobs/steps по принятому контракту. IDs в JSON — строки
положительных десятичных чисел, в PR-06 — числа: преобразование строгое, без
частичного парсинга и потери точности.

Текущий контракт содержит: verify, scheduler_freeze, queue_pause, postgres_migrate,
cloudflare_deploy, container_deploy, score_container_deploy, result_container_deploy,
scheduler_finalize, queue_finalize. Дополнительно проверить завершение самого job
сборки/публикации evidence и итог текущего workflow.

Сверять обязательные шаги с GitHub jobs/steps; не предполагать, что Actions API
возвращает YAML `id` каждого шага. Проверить отображаемые имена, reusable workflow
и соответствие принятому YAML. Неоднозначное сопоставление требует остановки;
оно не разрешает пропустить verify. `outcome` и `conclusion` evidence обязательного
шага должны быть success; skipped/neutral и скрытый continue-on-error не подходят.

Environment `development` подтверждается принятым workflow и его выполнением.
Поле `environment.status` отчёта не является названием GitHub Environment.
Если среда вычисляется динамически и привязку нельзя доказать доступными данными,
reader возвращает unknown; не придумывать отсутствующее подтверждение.

`deployment`, `environment.status`, blockers и ошибки reader выводит из проверенных
фактов и сверяет с итогами JSON. Один флаг `success` не заменяет эти проверки.
`manual_validation=pending` и `next_task_allowed=false` обязательны для producer v1.

## 8. Разделить deployment, готовность среды и ручную проверку

| Ситуация | Результат reader | Следующее действие после подключения runtime/UI |
| --- | --- | --- |
| PR открыт, CI идёт | Ожидание CI | Наблюдать, не запускать следующую задачу |
| CI упал | Провал конкретной попытки | Политика исправлений и бюджеты следующих PR |
| PR готов, merge ещё нет | Ожидание review/merge | Решение оператора |
| PR закрыт без merge | Требуется решение | Явная отмена/продолжение, без автоматического освобождения |
| Deployment идёт | Ожидание deployment | Дождаться полной попытки |
| Deployment упал/отменён | Failure или unconfirmed с причиной | Решение оператора, без автоматического recovery |
| Deployment успешен, Queue inherited_pause | Success + environment blocked | Снять паузу и получить новое подтверждение |
| Deployment успешен, readiness подтверждена | Ожидание ручной проверки | Оператор проверяет сайт |
| Новый SHA/run/attempt | Предыдущее подтверждение устарело | Повторная сверка и новая применимая проверка |
| API/evidence недоступны или неполны | Unknown | Повторить наблюдение, очередь закрыта |

Данные report о Queue/Scheduler относятся к моменту deployment. GitHub App не
обеспечивает чтение текущего Cloudflare. В PR-07 фиксируется источник и время
этого наблюдения; оно не описывается как постоянная проверка здоровья среды.

После ручного снятия паузы старый artifact остаётся blocked. PR-07 не снимает
эту блокировку по кнопке или словам оператора. До приёмки действия в PR-10 нужно
выбрать и реализовать доверенный источник нового чтения Queue/Scheduler с
минимальными правами. Это отдельное оставшееся решение; оно не мешает реализации
GitHub reader, но блокирует завершение сценария обновления readiness после паузы.

## 9. Сформировать observation и контракт с PR-06

Результат содержит scope/contract fingerprint, ожидаемые epoch/revision цикла,
owner/task/PR/head/base/merge, текущую dev, workflow/run/attempt, artifact identity,
итоги deployment/readiness, источник и время фактов, полноту и список причин.
Сырые HTTP ответы, логи CI, токены и URL скачивания в durable snapshot не попадают.

Разделить `complete` (полнота наблюдения) и `success` (результат процесса).
Полное наблюдение может доказывать провал. Ошибка внешнего чтения не уничтожает
старую историю, но запрещает использовать прежний success как актуальный допуск.

В конце прохода перечитать dev, head/состояние PR и указатели релевантных попыток.
Если они изменились, вернуть `observation_changed`; не собирать положительный
snapshot из разных моментов. Эти проверки не являются общей транзакцией с GitHub:
PR-08 и PR-10 обязаны повторно сверять факты перед исполнением и операторским решением.

Подготовить проверяемое сопоставление observation с командами PR-06. Сам reader
не вызывает `complete`, `finish_cancel`, `assign_recovery`, `start_work` и не
принимает решения за оператора. Запись из observer в работающий цикл и supervision
подключаются PR-08. В PR-07 совместимость проверяется через изолированный controller
и временный store; поздний результат для старой revision отклоняется.

Сохранённая отмена имеет приоритет: наблюдение merged PR во время отмены уточняет
требования к проверке среды, но не отменяет решение пользователя. Мерж основного
PR во время recovery и потеря его ancestry дают явную причину для согласования.

## 10. Проверить результат одной командой без worker

Добавить отдельный конечный режим диагностики delivery, например
`mix github_projects.delivery.inspect --workflow <path>`; точное имя закрепить
в реализации и инструкции. Он запускает только HTTP/credentials reader,
возвращает JSON и понятное резюме, затем завершает работу.

Отчёт показывает repo/dev SHA, PR/head, run/attempt, ссылку на Actions, результат
evidence, blockers и полноту. При пустом цикле всё равно наблюдается общая среда.
Для сценария текущего owner принимается явно заданный проверенный контекст без
записи в production store. В fixtures и интеграционных тестах используются временные
хранилища PR-06. Не запускать для диагностики обычный supervisor приложения,
bootstrap, рабочую очередь или произвольные hooks.

Однозначно документировать exit codes: ошибка чтения/настроек, подтверждённая
блокировка и полный отчёт. Ни один код не является разрешением стартовать worker.

## 12. Проверки и критерии завершения

Сначала целевые тесты новых модулей; после реализации полный `make -C elixir all`
в controller Ubuntu WSL2. Сохранить порог покрытия проекта, проверки specs, Credo,
Dialyzer и валидный PR body. Тесты выполняют реальные операции parser/store там,
где важно поведение; ответы GitHub задаются fixtures/локальным HTTP стендом.

Обязательные сценарии:

1. Полный успех актуального deployment → только ожидание ручной проверки.
2. Старый green, новый head/dev/run/attempt → старые сведения неприменимы.
3. Несколько runs одного SHA; более поздний pending/failed блокирует готовность.
4. Rerun старого SHA после нового deployment; проверка его возможного влияния.
5. Partial rerun, неполные jobs, skipped/neutral, скрытый continue-on-error.
6. Чужие repo/workflow/ref/event/environment, подменённый контракт.
7. Reusable verify и неоднозначные имена jobs/steps.
8. Положительный JSON при неуспешной/неполной публикации итогового job.
9. Неверный digest, malformed ZIP/JSON, лишние/дублирующиеся файлы, превышение размеров.
10. Отсутствующий/истёкший artifact, неподдерживаемая schema, неверные строковые IDs.
11. Повторный redirect, истёкший download URL, отсутствие токена на storage-хосте.
12. Поздняя страница 403/500, rate limit, timeout, повтор страницы, предел истории.
13. PR закрыт без merge; owner вне pilot filter; отсутствие active cards.
14. Merge ещё входит в dev; squash/rebase merge; исчезнувший предок после изменения истории.
15. Отмена оператором во время CI, merge или наблюдения; late response не отменяет её.
16. Recovery и suspended owner сохраняются; обычная задача B не получает допуск.
17. Inherited pause отдельно от failed resume и от неизвестного состояния Queue.
18. Повтор observation не расходует бюджет; внешний run не выдаёт новую попытку агенту.
19. Изменение revision/epoch/настроек во время чтения; restart перед применением результата.
20. Клиент и диагностика не выполняют GitHub mutations, store writes или запуск worker.

Затем провести один read-only проход через реальную App: доступ к PR/ref/Actions,
скачивание опубликованного PR-05 artifact, проверка identity/digest/jobs и вывод
результата. Не инициировать для этого deployment или rerun. Если настоящего отчёта
ещё нет, подготовка кода может завершиться, но пункт живой приёмки остаётся явно
не пройденным до появления отчёта и повторной проверки.

PR готов к передаче владельцу, когда код и полные тесты пройдены, сохранена защита
от исполнения, подготовлены описание и инструкция диагностики, а результат живой
проверки честно отмечен как подтверждённый либо заблокированный конкретной причиной.
Подключение допуска в PR-08 и пилот не принимаются на основании одних fixtures.
