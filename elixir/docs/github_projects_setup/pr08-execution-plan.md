## Результат для владельца

Модель цикла PR-06 и наблюдатель PR-07 должны управлять реальными путями scheduler:
первым запуском, следующими turns, retry, остановкой, восстановлением и cleanup.
Задача A остаётся владельцем репозитория, пока ждёт CI, review, merge, deployment
или ручной проверки dev. Задача B в это время не запускается.

В этом PR интеграция проверяется на управляемых тестовых worker-процессах.
Обычный запуск задач `github_projects` остаётся закрыт существующими проверками
startup, CLI и reload до готовности последующих этапов. Полноценная панель,
публикация кода и пилот в PR-08 не входят.

## 2. Подключить единственного владельца состояния

В `AgentRuntimeSupervisor` подключить `DeliveryGate` к общей судьбе scheduler и
worker tasks для профиля Projects. Gate остаётся единственным писателем store.
Оркестратор принимает решения о запуске и владеет временными ссылками на процессы;
вторую постоянную очередь или копию delivery state не создавать.

Порядок запуска: разобрать конфигурацию → открыть store и получить lock → прочитать
состояние → сверить GitHub → разрешать только допустимые действия. Observer работает
без Codex и не блокирует обработку отмены/таймеров длительным сетевым вызовом.
Одновременно допускается один проход observer; повторные запросы обновления объединяются.

Потеря gate/store/scheduler отзывает допуски и инициирует остановку worker.
Рестарт supervisor не должен создавать нового агента поверх старого. Отдельно
проверить порядок завершения дочерних процессов и подтверждение остановки transport.

## 3. Соединить наблюдения GitHub с переходами цикла

Перед сверкой брать текущий доверенный context из Gate. При получении результата
снова проверять scope, epoch/revision и содержимое цикла. Старый результат после
отмены, restart или изменения состояния не применять к новой версии автоматически.

Кандидаты `observe_ci`, `merged`, `deployment` применять по одному, только после
проверки допустимости. После записи версия меняется; остаток старого списка не
исполняется как готовый batch. Повтор одинакового факта не создаёт новую запись
в журнале и не расходует CI-бюджет.

Разделить факты и разрешения: успешный deployment может быть записан как факт,
но ручная validation, bootstrap, resume и recovery не возникают из него сами.
Неполное чтение, rate limit, новый SHA/attempt, неизвестный владелец или неподтверждённая
Queue readiness сохраняют соответствующую блокировку.

Сверка PR-06 сейчас разрешена только при остановленном интервале и разрешённых
неизвестных CI-операциях. Этот запрет нельзя убрать ради интеграции: активный запуск
имеет отдельную проверку продолжения, описанную ниже.

## 4. Сделать запуск атомарным относительно цикла

Последовательность первого запуска:

1. Проверить карточку: существующая открытая issue нужного repo/Project,
   `Ready for agent`, `Agent allowed=yes`, допустимый фильтр пилота.
2. Получить полную сверку repo и подтверждённую оператором актуальную базу dev.
3. Проверить свободный цикл и отсутствие действующего/неопределённого worker.
4. Сохранить владельца, ID цикла, отдельную ветку `agent/...` и ожидаемый SHA dev.
5. После изменения версии заново проверить допуск, затем сохранить рабочий интервал
   и резерв времени до выполнения hooks и Codex.
6. Разрешить ровно один запуск для этого интервала и зарегистрированного процесса.

В PR-06 `admission` действует для `reserved`, а `start_work` переводит в `working`
и снимает отметку сверки. Поэтому нельзя просто вызвать `admission` после
`start_work` или использовать `replayed` receipt как разрешение spawn.
Добавить узкую controller-операцию начала запуска: проверка актуального допуска,
сохранение интервала и одноразовое разрешение связанному worker. Разрешение живёт
в controller, не передаётся в аргументах агента и не восстанавливается из старого receipt.

Поток worker до разрешения не выполняет hooks/команды. Отмена между подготовкой и
фактическим запуском отзывает разрешение. Если результат spawn или записи неизвестен,
второй запуск запрещён до сверки; если подтверждено, что работа не началась,
интервал закрывается с фактическим расходом без освобождения владельца.

Создание/проверка ветки в рабочем checkout выполняется будущим доверенным launcher
по переданному контексту; реализация его git-операций относится к последующим PR.
При изменении dev перед созданием ветки launcher должен отказать, а не выбрать
другую базу молча. Обновление dev после начала работы блокирует новое продолжение
до сверки; сохранённая ветка не пересоздаётся автоматически.

## 5. Подчинить тому же правилу продолжение и retry

Проверку добавить перед каждым turn и каждым повторным запуском. Она подтверждает
тот же cycle/item/interval, действующий процесс, отсутствие отмены/блокировки,
доступный бюджет и свежесть необходимых внешних фактов. Положительный результат
для уже работающего интервала разрешает только его продолжение, не нового worker.

Не запускать полный пятиминутный observer на каждом checkpoint. Для работающей
задачи использовать ограниченную проверку условий остановки; полный проход выполнять
перед новым допуском и когда worker остановлен. Изменение, требующее полной сверки,
приостанавливает исполнение до её завершения. Поздний ответ не продлевает допуск.

При обычном завершении Codex различать продолжение работы, ожидание CI/review,
блокировку и отмену. Старая логика «normal exit → retry через секунду» не должна
воскрешать ожидающую или отменённую задачу. Старые retry timers и сообщения предыдущего
интервала отклоняются по идентификаторам, даже если issue та же.

Свободный worker slot сам по себе не означает свободный repo. Продолжение использует
ту же ветку/workspace и тот же открытый PR. Отсутствующая association PR не угадывается;
её подготовка до handoff остаётся PR-09.

## 6. Подключить фактический учёт времени и лимиты

| Ограничение | Поведение PR-08 |
| --- | --- |
| Первоначальная работа — 60 минут | Отдельный счётчик; исчерпание останавливает автоматическую работу |
| Исправления после CI — ещё 60 минут суммарно | Только после допуска к исправлению, без переноса остатка первого бюджета |
| Не более двух циклов исправления | Резерв цикла до старта; коммиты внутри одного исправления не считаются новыми циклами |
| До шести попыток PR CI | Продолжение не обходит лимит; успешная шестая попытка допускает review |
| До двух инфраструктурных повторов на SHA | Счётчики сохраняются; классификация и реальный rerun остаются PR-09 |
| Verify — 20 минут | Уже настроено в app workflow; PR-08 его не меняет |

Controller измеряет активное время монотонными часами и передаёт накопленное,
а не приращённое значение checkpoint. Время hooks подготовки, локальных команд,
Codex и локальных тестов относится к активному интервалу. Следующий turn, новая
сессия, новый SHA или restart не начинают бюджет заново.

Предлагаемые технические значения для первого профиля: checkpoint каждые 10 секунд,
лёгкая внешняя проверка не чаще одного раза в 30 секунд, срок свежести её результата
60 секунд. Истечение свежести закрывает продолжение. Полный observer сохраняет
ограничение PR-07 до 5 минут; Actions polling учитывает `Retry-After`, без перекрытия
проходов. Эти значения проверяются тестами с управляемыми часами и нагрузкой;
изменение их не меняет согласованные бюджеты 60/60/2/6.

Независимый таймер завершает допуск по оставшемуся времени, даже если Codex перестал
посылать сообщения. Задержка остановки включается в измеренный расход и не маскируется
как ожидание. При потерянном точном времени применяется консервативное восстановление
PR-06; выдуманного нулевого расхода не будет.

Ожидание GitHub Actions, review и оператора не расходует активное время только после
подтверждённой остановки worker. Фраза агента «жду» не является подтверждением.
Постоянный observer работает отдельно и не требует платной Codex-сессии для ожидания.

## 7. Реализовать остановку, паузу и явную отмену

При отмене сначала записать `request_cancel` с доверенным решением оператора,
отозвать разрешение новых turns/retry, затем остановить текущую работу. Интервал
закрыть после подтверждения остановки; workspace, ветка и неопубликованные файлы
сохраняются. Не запускать обычные publication hooks как побочный эффект отмены.

Для управляемых локальных процессов предусмотреть корректное завершение, затем
принудительное завершение своей группы процессов при необходимости. Для SSH закрытие
соединения или `Port.close` не считать доказательством остановки удалённой команды.
Ввести результат transport `stopped` либо `stop_unconfirmed`; во втором случае
владение, неопределённый интервал и запрет следующего запуска сохраняются.
Проверка реального Podman/SSH дерева процессов и его остановки — обязательная приёмка PR-11.

До merge отмена не освобождает repo до проверки отсутствия текущей работы и
неопределённых операций. После merge отмена не отменяет изменения в dev:
сохраняются требования deployment и ручной проверки. Отмена recovery возвращает
блокировку исходному владельцу. `Done`, archive и закрытие issue не заменяют отмену.

В PR-08 проверяется внутренний controller API отмены. Кнопка и подтверждение личности
оператора добавляются в PR-10; worker не получает доступ к этим командам.

## 8. Подключить возврат из review и recovery

Возврат после review требует явного разрешения оператора продолжить работу с
дополнительным бюджетом согласно §6.5 основного плана. Сохранить тот же открытый PR,
ветку, историю затрат и CI-попыток. Одна перестановка карточки или свободный slot
не создают новый бюджет. В модели добавить минимальный явный переход из review к
разрешённому продолжению, с привязкой к текущим PR/head, reason и controller actor;
не ослаблять проверки обычного `resume` и не выдавать замечания review за провал CI.

Источником такого разрешения будет будущий авторизованный операторский компонент.
В PR-08 переход проверяется через доверенный тестовый controller, без HTTP-кнопки,
автоматического чтения произвольных комментариев и самовольного решения агента.

Recovery запускается только по уже сохранённому явному назначению существующей
подходящей карточки, с её веткой от текущей dev и назначенными бюджетами. Исходная
задача сохраняется как приостановленная, обычная очередь закрыта. После восстановления
и validation, если A ещё не merged, продолжать можно A после сверки базы, а не B.
Если A merged, завершение её цикла следует уже согласованной модели PR-06.

## 9. Защитить workspace во всех путях cleanup

Проверка ownership должна предшествовать `before_remove` и любой destructive очистке,
включая `remove_recorded`, cleanup после failed create и startup terminal cleanup.
Предпочесть отказ в удалении при неизвестной связи, а не считать папку бесхозной.

Сохранять рабочие папки текущего и приостановленного владельца/recovery, в том числе
при `Done`, отсутствии карточки, failed hook, retry, corrupted store и несовместимом scope.
Проверка самого пути под workspace root остаётся обязательной независимо от gate.
Удаление допускается только после подтверждённого завершения и разрешённого cleanup
либо явного решения оператора с сохранением нужной работы. PR-08 не добавляет кнопку удаления.

## 10. Ввести одинаковый JSON-контекст для hooks

Версионированный контекст содержит repo, Project/item/issue IDs, cycle ID и version,
назначенную ветку, ожидаемый SHA dev, ID интервала и режим `new/continue/recovery`.
Формат фиксируется в документации вместе с ограничениями длины и обязательными полями.

Контекст передаётся как данные через ограниченный файл/канал, одинаково для local и
SSH. Для SSH не подставлять JSON и значения карточки в shell-текст. Проверить передачу
кавычек, Unicode и спецсимволов, безопасный путь файла и отсутствие symlink-подмены.

Worker не получает App key, controller credentials или разрешение изменить base/ref.
Контекст не является секретным токеном допуска и не превращает редактируемый worker
файл в authority: controller проверяет любые будущие запросы по своему состоянию.
Исполняемый `WORKFLOW.md` и продуктовые launch scripts остаются в `D:/agent-runner`;
в PR-08 задаётся контракт Symphony, сам agent-runner и app не изменяются.

## 11. Проверить startup, reload и crash вместе

Путь store, repo/Project/base, identity App, фильтр пилота, политика validation,
закреплённый observer-контракт, workspace root и worker mapping — restart-only.
Проверить фактический список в `DeliveryGate.Settings`: одного нынешнего scope hash
недостаточно для всех условий rollout; недостающие поля включить явно.

При изменении этих параметров не продолжать автоматически по старому разрешению:
остановить Projects worker, сохранить цикл, сообщить `restart_required`. Последняя
корректная конфигурация пригодна для диагностики, но не скрывает запрет исполнения.
Ротация токена той же identity обслуживается PR-03 без сброса цикла.

Изменение scope/hash/schema не мигрирует старый store молча. Если нужна совместимость
нового внутреннего перехода, проверить воспроизведение журналов PR-06/07; непроверенное
состояние оставить закрытым и документировать явный путь восстановления.

Проверить crash до/после reserve, start_work, spawn, остановки, checkpoint, записи
факта GitHub и отмены. Новый epoch отклоняет старые сообщения; незакрытый интервал
не становится свободным. После потери SSH новый worker не создаётся без проверки
отсутствия прежнего. При неизвестном состоянии store cleanup тоже закрыт.

## 12. Добавить объяснимое состояние для будущей панели

В существующие внутренние snapshots и логи добавить: owner/task, фазу, текущий
интервал, worker running/stopping/stop_unconfirmed, причину запрета продолжения,
доступные бюджеты, возраст последнего проверенного наблюдения и ожидаемое действие.
Показать отдельно `deployment success`, readiness по артефакту и manual validation.

Унаследованная пауза Queue остаётся `resume_queue_before_dev_validation`.
После ручного снятия паузы старый артефакт не подтверждает новый статус. Источник
свежего подтверждения Queue остаётся отдельной функцией до PR-10/пилота; этот PR
не вводит ручную «галочку доверять» и не обращается к Cloudflare.

Полноценная панель, кнопки resume/cancel/recovery и аутентификация — PR-10.
Нельзя обещать, что после PR-08 они уже появятся в dashboard.

## 13. Приёмка и тесты

Тесты используют реальные OTP supervisor/task процессы, временный Linux store,
управляемые часы/worker и API fixtures. Не требуется настоящая задача приложения.
Adversarial review выполнить локально на ранних тестах гонок; воспроизводимые сбои
устранить до общего прогона. Затем выполнить `make -C elixir all`, format/specs,
Credo/Dialyzer, тесты store, `git diff --check` и проверку PR body.

| Сценарий | Обязательный результат |
| --- | --- |
| Одновременные кандидаты A и B | Только A резервирует цикл и получает один worker |
| A ждёт CI/review/merge | Worker остановлен, B не запускается, активное время не растёт |
| `:DOWN`, retry timer или новый turn после паузы | Нет обхода gate и самовольного возобновления |
| Отмена между reserve и spawn | Ни один hook/turn не начинается после отзыва допуска |
| Старый observer после отмены/checkpoint/restart | Не открывает допуск и не переписывает новое состояние |
| Изменились dev, PR head или deployment attempt | Старое подтверждение не позволяет продолжение/validation |
| API недоступен или факт просрочен | Нет положительного допуска из cached success |
| 60 минут initial/fix, два исправления | Остановка с сохранением работы и занятым циклом |
| Повтор события CI или смена SHA | Нет повторного списания события и сброса общего бюджета |
| Успех шестой CI-попытки | Можно передать PR на review без седьмой попытки |
| Review return | Тот же PR/ветка, явное разрешение и дополнительный бюджет |
| Recovery до merge A | После восстановления возвращается A, очередь B закрыта |
| Отмена после merge | Deployment и ручная validation всё ещё обязательны |
| Потеря store/helper/scheduler | Старый worker лишается допуска, нового поверх него нет |
| Потеря SSH/нет доказательства остановки | `stop_unconfirmed`, запрет нового запуска и cleanup |
| Done/archive/missing/failed create | Работа владельца и suspended owner не удаляется |
| Reload scope/filter/state_path | Restart required без переключения store и сброса затрат |
| Hooks local/SSH, кавычки и Unicode | Один JSON-контракт, данные не исполняются как shell |
| Другие trackers | Сохраняются существующие dispatch/retry/cleanup semantics |
| Обычный startup Projects и диагностика PR-07 | Startup всё ещё закрыт; read-only диагностика не пишет store |
