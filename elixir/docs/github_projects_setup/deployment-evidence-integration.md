# Подключение отчёта deployment к Symphony

Этот документ относится к настройке и будущему запуску Symphony для EmotionStat.
Рабочая копия Symphony находится в `D:/symphony`, приложение — в
`D:/EmotionStat_app/app`, исполняемый профиль и запуск worker относятся к
`D:/agent-runner` по [плану реализации](../github_projects_pr_rollout_plan.md).

## Граница готовности

PR-05 реализован локально в `EmotionStat/app`, ветка
`agent/feat/deployment-evidence`; публикация и первый реальный запуск нового
workflow ещё не подтверждены. Он готовит данные о deployment. Чтение этих данных
controller-ом, снятие блокировок и действия оператора в панели — следующие этапы.

Сейчас реализована [конечная read-only инспекция Project](../github_projects.md)
с [учётными данными GitHub App](../github_app_credentials.md). Обычный запуск
исполнения задач с `tracker.kind: github_projects` пока отклоняется.
Отчёт о deployment сам по себе не включает очередь задач.

Для просмотра демонстрационной панели сохранён
[Start-Symphony-Demo.cmd](Start-Symphony-Demo.cmd); он вызывает
[start-dashboard-demo.ps1](start-dashboard-demo.ps1) в controller-дистрибутиве
`Ubuntu` под `nataselko`. Ему нужны собранный `elixir/bin/symphony` и ранее
подготовленный приватный demo `WORKFLOW.md`. На момент переноса документации
`D:/symphony/elixir/bin/symphony` отсутствует; перед запуском демо нужна сборка
по [инструкции Elixir](../../README.md). Демо с пустой очередью не является
рабочей панелью допуска задач, проверки Queue или подтверждения dev.

## Где находится контракт

Формат JSON, обязательные deployment jobs/steps, значения статусов и правила
повторного deployment принадлежат репозиторию приложения:
`EmotionStat/app`, `.github/workflows/deployment-evidence.md`.
На этом компьютере — [локальная копия контракта](D:/EmotionStat_app/app/.github/workflows/deployment-evidence.md).
Полный формат здесь не дублируется; reader должен поддерживать его явную версию.

Symphony получает файл `development-evidence.json` из артефакта
`development-evidence-<run_id>-<run_attempt>` ожидаемого development workflow.
Для чтения закрытого репозитория controller должен получить ограниченный token
GitHub App с `Actions: read` и доступом к `EmotionStat/app`; ключ остаётся вне
checkout и рабочих каталогов. Наличие grants у App и фактические permissions
выданного токена проверяются отдельно. Профиль чтения Project сам по себе не
доказывает доступ к Actions и скачиванию артефактов.

## Подготовка перед включением рабочих задач

1. Принять PR-05 в приложении и проверить один реальный deployment текущей `dev`:
   итоговое задание успешно, артефакт доступен, SHA/run/attempt совпадают с Actions.
2. В PR-06 реализовать постоянное состояние одного цикла репозитория и его
   бюджетов. Перезапуск Symphony не должен обнулять состояние или открывать очередь.
3. В PR-07 реализовать чтение и независимую сверку PR, `dev`, Actions и отчёта
   по правилам ниже. Проверить скачивание настоящего артефакта controller-ом.
4. В PR-08 связать эти результаты с допуском исполнения. В PR-09 реализовать
   ограниченные операции публикации и передачи работы оператору.
5. В PR-10 добавить идентификацию оператора, отображение причин блокировки,
   форму ручной проверки и проверку актуальности подтверждения на сервере.
6. Подготовить изолированный worker и исполняемый `WORKFLOW.md` в `agent-runner`
   по PR-11/PR-12; затем выполнить приёмку PR-13 и bootstrap здоровой `dev`.
7. Только после этих проверок разрешить одну выбранную пилотную задачу PR-14.

Точные зависимости и остальные условия сохраняются в
[поэтапном плане](../github_projects_pr_rollout_plan.md) и
[плане адаптера](../github_projects_adapter_plan.md). Здесь перечислены условия
подключения deployment evidence; это не команда запуска и не разрешение пилота.

## Что должен проверять controller

- Самостоятельно прочитать через GitHub API репозиторий, ожидаемый workflow,
  SHA, run ID, номер попытки и результаты jobs. Дождаться завершения именно этой
  попытки, включая успешную публикацию отчёта.
- Использовать jobs конкретной попытки. Сверить JSON с GitHub, поддерживаемой
  версией контракта и всеми обязательными jobs/steps. Проверить идентичность и
  контрольную сумму скачанного артефакта по доступным метаданным GitHub.
- Отклонять предыдущую попытку, частичный набор успешных jobs, другой SHA,
  неизвестную схему и недоступный артефакт. Его срок хранения — 30 дней;
  истечение срока не разрешает подставить старый зелёный результат.
- После отмены, потери runner, ошибки загрузки или противоречивых данных
  сохранять блокировку и понятную причину для оператора.
- Повторно сверять текущую `dev` перед принятием операторского действия и перед
  допуском следующей задачи. Между GitHub ref и изменениями среды нет общей транзакции.

Отчёт — наблюдение доверенного workflow, а не самостоятельная подпись или
защита ветки. Для private-репозитория на GitHub Free ограничения публикации
нужно реализовать в controller: worker не получает write-токен, а push broker
публикует только закреплённую за задачей ветку. Изменения проверок требуют
отдельного внимания при review. Имя успешного check не заменяет эти проверки.
Бюджеты агента и лимиты повторов реализуются в Symphony согласно плану адаптера;
они не задаются workflow приложения.

## Три результата в дашборде

| Результат | Условие |
| --- | --- |
| Деплой завершён успешно | Принят полный отчёт актуальной успешной попытки. |
| Среда готова к полной ручной проверке | Queue активна, Scheduler имеет ожидаемые расписания, нет операционных блокировок. |
| Ручная проверка пройдена | Оператор проверил приложение и подтвердил конкретные SHA/run/attempt и версию цикла. |

До выполнения всех условий обычная очередь Symphony закрыта. Ошибка deployment
или ручной проверки не запускает новую обычную задачу; восстановление требует
явного решения оператора по правилам основного плана.

### Queue сохранила исходную паузу

Это успешный deployment с операционной блокировкой, если workflow подтвердил,
что пауза существовала до deployment и корректно сохранилась. Панель должна
показать отдельное сообщение:

> Деплой завершён успешно.
> Перед полной проверкой dev необходимо снять паузу Queue.
> Очередь обработки сообщений сохранила паузу, установленную до деплоя.

Сохранённая пауза сама по себе не запускает исправление кода. Оператор принимает
решение о возобновлении обработки сообщений. До подтверждения активной Queue
нельзя завершить ручную проверку dev или разрешить следующую задачу Symphony.

После ручного снятия паузы старый артефакт остаётся неизменным. Controller должен
получить новое подтверждение фактического состояния Queue, заново сверить
Scheduler и текущую `dev`, привязать наблюдение к deployment и версии цикла,
затем обновить сообщение в панели. Кнопка «паузу сняла» может запросить проверку,
но не должна сама записывать Queue как активную.

**До реализации этого действия нужно определить и проверить источник нового
наблюдения:** доверенное чтение состояния Cloudflare и минимальные права для него.
GitHub App не даёт доступа к Cloudflare. Этот доступ и backend обновления состояния
ещё не реализованы; PR-05 предоставляет только исходный отчёт и код блокировки.

Если workflow должен был возобновить Queue, но не смог, это ошибка завершения
deployment. Если чтение состояния не удалось, результат не подтверждён.
Оба случая оставляют очередь задач закрытой и требуют внимания оператора.

## Приёмка подключения и первого запуска

До пилота проверить полный успех, унаследованную паузу, неуспешное возобновление,
ошибку чтения Cloudflare, исчезнувший артефакт, другую попытку и изменение `dev`
при открытой форме. Операторское подтверждение устаревшего состояния отклоняется
на сервере; данные формы не переносятся на новый коммит автоматически.

Проверить восстановление после рестарта: controller сначала сверяет состояние
с GitHub и средой, затем решает о допуске. `deployment=success` и прежнее локальное
значение «готово» по отдельности не открывают очередь.

Демонстрационная панель, успешный read-only dry-run Project и локальные тесты
отчёта не заменяют эту приёмку рабочего controller/worker.
