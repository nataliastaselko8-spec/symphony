## 1. Результат и границы

Агент получает несколько операций только для своей задачи. Он готовит изменения
и отчёт, а controller проверяет полномочия, публикует разрешённую ветку, создаёт
или находит её PR, наблюдает CI и передаёт проверенный результат оператору.
Задача сохраняет владение репозиторием во время ожидания и при сбоях.

В PR-09 входят инструменты, controller-публикация, журнал внешних операций,
раннее сохранение связи с PR, восстановление после неопределённого результата
и интеграционные тесты. Используем существующие Gate, Runtime и observer.
Второй store, произвольный GitHub proxy и отдельную очередь не создаём.

Обычное выполнение `github_projects` остаётся выключено. Реальная граница
SSH/Podman, экспорт результата worker и доказательство остановки подключаются
в PR-11, рабочий `WORKFLOW.md` и hooks — в PR-12. Их интерфейсы определяются
здесь, но тестовый заменитель остановки не включается в рабочий профиль.
Операторские кнопки и авторизация — PR-10. App workflows, настройки GitHub,
agent-runner и knowledge-base в этом PR не меняются. Live-записи выполняются
позже на согласованном тестовом объекте в O3c/O4, без запуска продуктовой задачи.

## 2. Уточнения, выявленные при проверке кода

1. `GitHubProjects.Adapter.agent_tool_specs/0` пока возвращает пустой список.
   Привязка dynamic tools сохраняет настройки tracker, но ещё не полномочия
   конкретного delivery cycle. Одного `opts[:issue]` для разрешения записи мало.
2. Сейчас `handoff` сохраняет `pr_number` только после успешного CI.
   Observer нуждается в этом номере раньше. Добавляем отдельное сохранение PR
   для ожидания CI; оно не означает `PR ready` или передачу на review.
3. `reserve_ci` требует закрытого интервала работы. Поэтому инструмент агента
   сначала сохраняет запрос публикации. Controller останавливает worker,
   подтверждает остановку, закрывает интервал и только затем публикует результат.
4. Текущий `app/.github/workflows/pr-ci.yml` реагирует на `opened`, `synchronize`,
   `reopened`, `ready_for_review`, `edited`. Служебное редактирование PR может
   создать новый запуск и отменить предыдущий из-за `cancel-in-progress: true`.
5. Профили credentials пока не включают запись в Projects. `Actions: read`
   позволяет наблюдать CI, но не запускать rerun. Права расширяются только
   в пределах отдельно разрешённых операций, не одним общим токеном для агента.

## 3. Подготовить базу и контракт

Перед реализацией проверить чистоту рабочего дерева, принятый PR-08, `origin`
личного форка и обновлённую `main`; затем создать ветку. Не переносить изменения
в upstream. Сверить действующие AGENTS, workflow приложения и схемы Gate.

Сначала описать переходы и отрицательные сценарии. Имена новых внутренних
команд можно уточнить при реализации, но смысл должен оставаться таким:
`prepare_publication` → подтверждённая остановка → `reserve_ci` → публикация
ветки → `bind_pr` → наблюдение CI → `handoff`.

Ранний разбор отказов должен проверить как минимум потерянный ответ GitHub,
отмену между проверкой и записью, раннюю Project automation, смену dev и рестарт
после удалённого эффекта, но до записи результата в store.

## 4. Привязать инструменты к текущему запуску

Передать доверенный delivery handle из `AgentRunner` через `AppServer` в binding
dynamic tools. На controller связать его с PID/сессией, cycle, item, issue,
репозиторием, веткой, epoch и интервалом работы. JSON от модели или hook context
не становится разрешением. Секреты и controller handle не отправляются worker.

Перед каждой операцией проверять актуальный handle и фазу; перед записью — также
свежие сведения GitHub и сохранённую версию цикла. Старые tool calls после отмены,
reload, restart, окончания интервала или смены задачи отклоняются.
Произвольные `repo`, `item_id`, `issue_id`, URL, GraphQL, HTTP method и refspec
не принимаются как выбираемое агентом назначение операции.

Предлагаемый набор инструментов:

| Операция | Что разрешено | Что считается успехом |
| --- | --- | --- |
| Контекст | Прочитать текущую задачу, ветку, PR, фазу, ограничения и остатки бюджета | Получены данные текущего cycle без секретов |
| Начало работы | Подтвердить `Agent working` для уже допущенного запуска | Gate разрешил запуск; поле перечитано после записи |
| Отчёт | Создать или обновить один отчёт в комментарии текущей issue | Подтверждены ID комментария, автор App и содержимое |
| Блокировка | Сообщить причину и сохранить прогресс | Внутренний цикл заблокирован; остановка worker инициирована |
| Подготовка PR | Передать описание результата и кандидат коммита | Сохранён запрос проверки и публикации, а не обещание готового PR |
| Передача результата | Завершить работу над кандидатом и запросить проверяемый handoff | Запрос принят; финальный успех публикует controller после CI |

«Начало работы» не создаёт новую сессию и не возобновляет задачу из review.
«Передача» не позволяет агенту объявить CI зелёным. Agent не получает операции
merge, deploy, rerun deployment, удаления веток, изменения `Agent allowed`,
подтверждения dev, выдачи бюджета, назначения recovery или установки `Done`.

## 5. Добавить журнал публикации в существующий Gate

В versioned JSON store добавить ограниченную запись текущей публикации:
operation ID, cycle/item/issue, repo ID, разрешённую ветку, ожидаемые base/head,
хеш неизменяемого кандидата, резерв CI, найденный PR и стадии внешних операций.
Отдельно сохранять ID постоянного отчёта. Gate остаётся единственным писателем.

Каждую запись в GitHub предваряет сохранённое намерение. Результаты различаются:
ещё не отправлено, отправлено с неизвестным исходом, подтверждено чтением,
отклонено. Сетевое ожидание выполняется вне GenServer, чтобы отмена и таймеры
обрабатывались своевременно; результат применяется только к своей версии операции.
Одновременно разрешена одна цепочка публикации текущего владельца.

Повтор tool call возвращает состояние уже принятой операции. Это не разрешение
ещё раз выполнить push или POST. После рестарта незавершённая операция сначала
сверяется с удалённой веткой, PR и Actions. Если доказательств недостаточно,
цикл остаётся закрытым с причиной, а не получает новый бюджет или второй PR.

Расширить валидатор схемы и scope fingerprint вместе с форматом. Старый активный
store не преобразовывать автоматически и не считать пустым. Для несовместимой
версии предусмотреть явную остановку и документированный путь обновления с
сохранением резервной копии. Проверить восстановление из старого snapshot:
оно не должно воскресить отменённое разрешение или повторить уже выполненный эффект.

## 6. Подготовить и проверить неизменяемый результат worker

Агент завершает локальные проверки, коммиты и отчёт. Запрос содержит предложение
кандидата; controller сверяет его с собственной записью задачи и ветки.
Далее запретить новые turns, остановить worker и получить доказательство остановки
всех его процессов. При `stop_unconfirmed` публикация не выполняется.
Закрыть рабочий интервал с учётом фактического времени.

Для публикации использовать неизменяемый Git bundle/набор Git objects,
полученный через доверенный транспорт. В PR-09 реализовать проверку кандидата
и публикацию на локальном тестовом транспорте; реальный экспорт из контейнера
должен соблюсти этот контракт в PR-11. Worker не выбирает произвольный путь
на controller. Запретить чтение за пределами выделенного staging-каталога.

Проверить целостность и ограничение размера, commit/tree, принадлежность истории
ожидаемой базе и непрерывность обновления ранее опубликованной ветки.
В MVP неподдерживаемые gitlinks/submodules и LFS-кандидаты останавливать с ясной
причиной вместо неявной загрузки из заданного worker внешнего источника.

Отдельно проверить изменения управляющих файлов: workflows, общий verify,
проверяющие scripts и их policy. Источник этой политики находится на controller.
Обычная задача не может заменить обязательные проверки или их критерии успеха.
Изменение защищённого контракта требует отдельного решения оператора; нельзя
«принять новый хеш» только потому, что его прислал агент.
Изменения обычных продуктовых тестов видны в отчёте и review; controller не может
формально доказать добросовестность любого изменения теста, поэтому review остаётся.

Если `dev` изменился, новый кандидат требует сверки готовности этой версии dev,
merge актуального dev в ту же рабочую ветку и новых проверок. Не выполнять rebase,
reset или force push. Для явно назначенного recovery действует уже согласованное
исключение: база — текущий сломанный dev; чужая recovery-задача не допускается.

## 7. Реализовать узкую публикацию и профили прав

Controller публикует проверенные объекты из собственного временного bare repo.
Не запускает git из изменяемого worker workspace и не читает его hooks/config,
credential helpers или startup scripts. Использует очищенное окружение,
ограниченные Git protocols, доверенный URL одного репозитория и явное назначение:
`<проверенный SHA>:refs/heads/<закреплённая ветка>`.

Допускаются создание закреплённой ветки и её fast-forward обновление. Запрещены
другие refs, `dev`, `main`, force, deletion, tags, `--all`, `--mirror` и параметры
Git от модели. Перед отправкой и после неё сверять удалённый head. Неожиданная
история или результат останавливают цепочку. Операцию получения токена отделить
от обработки недоверенных данных; token не помещать в URL, argv, store или логи.

Минимальные controller-профили: чтение; комментарий issue; создание PR/связь;
запись разрешённого поля Project; git publication с `Contents: write`.
Все profile IDs и назначение формирует код, не модель. Токены ограничиваются
репозиторием там, где GitHub поддерживает такое сужение; выбор конкретного
Project, item и ref дополнительно проверяет controller.

GitHub App с `Contents: write` не становится ограниченным одной веткой на стороне
GitHub. В выбранном профиле без обязательных branch rules запрет для агента
обеспечивают отсутствие write credentials у worker и этот механизм публикации.
Полноценность изоляции проверяется в PR-11. Это не ограничивает самостоятельные
действия владелицы или другого администратора GitHub.

## 8. Создавать один PR и запускать CI предсказуемо

**Предложение для MVP:** создавать обычный PR в `dev` для запуска проверок,
а готовность к review показывать отдельно статусом Project и постоянным отчётом.
Наличие открытого PR ещё не означает, что Symphony передала его на review.
Это позволяет работать с текущим workflow без дополнительного запуска
`ready_for_review`. Автоматический merge не включается.

Перед первым созданием подготовить стабильные title/body с задачей, целью,
ссылкой на постоянный отчёт и пометкой, что актуальная готовность определяется
CI и Project. Пока CI не прошёл, не добавлять native link, который может
включить существующую Project automation. Не вставлять closing keywords.

Порядок первой публикации:

1. Подтвердить остановку worker и сохранение кандидата.
2. Сверить актуальные разрешения, цикл, ветку и dev. Зарезервировать попытку CI
   до первого действия, которое может вызвать запуск.
3. Опубликовать ветку. Полностью проверить существующие PR по точной паре
   repo/head/base и сохранённому cycle. Совпадение заголовка не является связью.
4. Создать один PR, если отсутствие ранее созданного PR подтверждено и нет
   неизвестного исхода предыдущего создания. Сохранить его ID/номер и перечитать
   repo/head/base/SHA. Связать его с текущей issue в store командой `bind_pr`.
5. Перейти к ожиданию CI. Native Development link и `PR ready` пока не нужны.

При исправлении использовать ту же ветку и PR. Резервировать CI до push:
`synchronize` может возникнуть сразу. Предыдущая попытка должна быть сверена;
не создавать параллельные автоматические запуски поверх неизвестного результата.
Стабильное тело PR сохраняется, прогресс и свежие результаты обновляются в отчёте
issue. Человеческие правки title/body автоматически не перезаписываются.

Изменение body/title, reopening или смена draft-stage не являются бесплатным
способом повторить CI. MVP не вызывает эти события для служебного обновления.
Внешние запуски наблюдаются и учитываются по существующему консервативному
контракту; дополнительный бюджет автоматически не появляется.

При закрытом без merge PR — решение оператора, без автоматического reopening
или второго PR. При merged PR — переход к наблюдению deployment, без нового push.
При нескольких совпадениях, смене base/head, переносе issue или повторном
добавлении карточки в Project — остановка для сверки идентичности.

## 9. Финальная передача, связь с issue и Project

Только после успешной обязательной PR CI проверить актуальные head SHA, base/dev,
run ID/attempt, workflow и обязательные jobs. Старый зелёный запуск на другом
коммите, изменившейся базе или перед более поздним rerun не подходит.
Подтверждение проверок берётся из observer, не из отчёта агента.

Далее обновить постоянный отчёт: что изменено, что проверено, ссылки на PR/CI,
ограничения и что проверить человеку. Создание/обновление комментария сверять
по сохранённому ID, App actor и устойчивому маркеру cycle. Один маркер в чужом
комментарии не доказывает принадлежность. Не удалять комментарии для «очистки».

Сохранить намерение финальной передачи, затем установить и перечитать native
связь issue ↔ PR. Кандидат API — `addCloseIssueReferences`; проверить реальные
права App и обратное чтение связи до live. `Closes #…` не заменяет эту проверку,
особенно если `dev` не является default branch.

Если подтверждённая automation сама переводит item в `PR ready`, принять этот
результат. Иначе использовать только явно согласованный переход Status текущей
карточки. Не создавать две конкурирующие схемы управления статусом.
Недоступность native link не маскировать обычной ссылкой: перейти на явную
связь в store и прямое управление Status можно после согласования до пилота.

Операция, которая может выставить `PR ready`, выполняется после всех обязательных
действий worker. Controller заканчивает readback и сохраняет `awaiting_review`.
При аварии между изменением GitHub и сохранением store восстанавливает эту же
передачу. Видимый `PR ready` сам по себе не освобождает цикл и не запускает B.

Read-before-write Project API не обеспечивает атомарный compare-and-swap с
действиями человека. Повторное чтение, единственный controller и журнал сокращают
гонки, но не дают обещания транзакции с GitHub. Обнаруженный конфликт требует
сверки; локальная отмена всегда проверяется перед следующим действием.

Собственные ожидаемые записи также меняют данные, за которыми следит Runtime.
Обновлять baseline наблюдения только после подтверждения конкретного результата,
а не игнорировать все изменения от App. Любое дополнительное внешнее изменение
остаётся причиной повторной сверки. Если привязка или automation неожиданно
породила новый CI, старый успех не финализирует handoff: сначала учитывать и
проверять новый запуск; повторение на live блокируется до исправления контракта O4.

Возврат уже связанного PR из review проверить отдельно. Ту же ветку и PR сохранять,
продолжение разрешать только через `review_resume` и дополнительный бюджет
оператора. Если существующая automation преждевременно возвращает `PR ready`,
для пилота потребуется согласовать её изменение; расширять активные статусы
агента для обхода этой проблемы нельзя.

## 10. Сбои CI и согласованные лимиты

| Ограничение | Поведение PR-09 |
| --- | --- |
| Первоначальная работа | До 60 минут активного времени |
| Исправления CI | До 2 циклов исправления, суммарно до 60 активных минут |
| Все автоматические PR CI | Не более 6 попыток за цикл, включая новые SHA и повторы |
| Инфраструктурные повторы одного SHA | Не более 2; задержки 1 и 3 минуты при разрешённой автоматизации |
| Verify приложения | Существующий timeout 20 минут; в этом PR workflow не меняется |
| CI/review/deploy/ручная проверка | Ожидание не расходует активное время агента; worker остановлен |
| Шестая попытка успешна | Handoff разрешён при остальных выполненных условиях |
| Бюджет исчерпан или состояние неизвестно | Сохранить результат, `Needs human decision`, очередь закрыта |

Отчёт агента «это сеть» не является классификацией. Подтверждённое падение
продуктовых проверок допускает `begin_fix` в пределах бюджета. Сбой инфраструктуры
определяется только по узкому проверяемому набору признаков controller. Если
такого признака нет, причина остаётся неизвестной и требуется оператор.
Ошибки прав/секретов, отмены, skipped и timeout не превращаются автоматически
в инфраструктурный rerun. Отмена предыдущего CI из-за synchronize также не даёт
права повторять старый SHA.

**При текущем `Actions: read` автоматический rerun выключен.** PR-09 обеспечивает
учёт попыток, объяснение причины и наблюдение результата ручного повтора.
Если владелица отдельно разрешит Actions write, добавить отдельный controller
profile и узкую операцию полного rerun только известного PR CI текущего SHA,
с резервом до POST и сверкой run/attempt после ответа. Это не означает выдачу
Actions write worker и не разрешает повтор deployment. Без такого решения
работающий автоматический rerun не является обещанным результатом PR-09.

Рестарты, новые tool calls и новые коммиты не сбрасывают лимиты. Подтверждённые
внешние запуски фиксируются без двойного списания одного run/attempt; действия
оператора GitHub нельзя предотвратить локальным счётчиком. Неизвестный результат
не трактуется как неиспользованная попытка. Post-merge verify/deployment не входят
в шестёрку PR CI и продолжают удерживать очередь по правилам PR-06–PR-08.

## 11. Отмена и неопределённые ответы

| Ситуация | Что делает controller |
| --- | --- |
| Отмена до отправки | Сохраняет отмену, отзывает дальнейшие операции, останавливает worker |
| Отмена во время push/create PR | Уже отправленное действие может завершиться; сверяет эффект, не продолжает handoff |
| GitHub создал PR, ответ потерялся | Ищет строго связанную ветку/PR; сохраняет найденный результат, не создаёт второй вслепую |
| Readback временно не видит PR после timeout | Сохраняет unknown, повторяет чтение; отсутствие в одном ответе не разрешает новый POST |
| Push прошёл, процесс controller упал | После restart проверяет SHA удалённой ветки и продолжает ту же цепочку только при подтверждении |
| 401/403/404, отозван App или доступ к карточке | Останавливает запись; ошибка доступа не считается доказательством отсутствия объекта |
| Rate limit или ошибка связи | Соблюдает Retry-After, не воспроизводит mutation автоматически как обычный GET |
| Удалена/пересоздана карточка, изменён repo/head/base | Сохраняет работу и требует сверки; не переходит на похожий объект |
| После handoff PR merged человеком | Observer переводит цикл к deployment и ручной проверке; следующая задача пока не допускается |
| Deployment сломался | Сохраняется блокировка; только явно назначенная recovery получает отдельную ветку/PR от текущего dev |

Отмена не удаляет ветку, PR, workspace и неопубликованные коммиты, не откатывает
merge и не отменяет deployment автоматически. Освобождение цикла выполняется
только после предусмотренных моделью доказательств, включая остановку worker
и отсутствие неразрешённых внешних эффектов. Worker не может отменой сам себе
выдать новый чистый цикл.

## 13. Проверки и критерии приёмки

Проверять реальные Gate/Runtime/OTP процессы и наблюдаемые эффекты. Git publisher —
на локальных временных bare remotes; HTTP — на управляемом сервере с задержками,
ошибками и потерянными ответами. Не проверять запрет посредством настоящего push
в `EmotionStat/app:dev`.

Обязательные сценарии:

- Поддельный cycle/item/repo/head/base, старый handle, чужой PID, повтор tool call:
  ни одной неразрешённой записи; Linear и старый GitHub tracker не регрессируют.
- Отдельная операция в каждую запрещённую ref, force/delete/mirror, вредоносные
  Git config/hooks/credentials и подмена staging-файла: публикация блокируется.
- Первая публикация, новый SHA того же PR и успех CI: ровно ожидаемые push/PR/CI,
  номер PR доступен observer до handoff; финальный `PR ready` только после проверки.
- Смена dev, неожиданная удалённая история, closed/merged PR, несколько совпадений:
  нет потери работы, сброса ветки или автоматического второго PR.
- Crash до/после каждой внешней записи и до фиксации readback: восстановление
  без двойного эффекта; unknown остаётся заблокированным при нехватке доказательств.
- Отмена, отзыв разрешения, потеря Gate/store и поздний ответ: новые действия
  отозваны, уже начатые отражены честно; B не запускается поверх A.
- `stop_unconfirmed`: ни push, ни создание PR. Тестовая остановка не становится
  производственным обходом требований PR-11.
- `edited`/`ready_for_review`/внешний rerun и новый SHA: фактические попытки
  не теряются; нет handoff по старому зелёному run, нет автоматической седьмой попытки.
- 60/60 минут, два исправления, два допустимых rerun одного SHA, шестая успешная
  попытка, перезапуск и повтор событий: лимиты не сбрасываются и не списываются дважды.
- Собственная запись Project не воспринимается как разрешение игнорировать
  одновременную отмену человека; ранняя automation не освобождает цикл.
- Неправильная или отсутствующая native связь, неоднозначный комментарий и
  re-added item блокируют final handoff; реальная automation проверяется отдельно в O4.

Во время реализации — целевые проверки и ранний разбор отказов. Перед передачей —
`make -C elixir all` в Ubuntu WSL2, проверки Python store, формат, specs, Credo,
Dialyzer и описание PR по точному шаблону через `mix pr_body.check --file …`.
Количество прошедших тестов записывается по фактическому результату, не заранее.

Готовность PR-09: тесты доказывают публикацию только назначенной ветки, один
проверенный PR, резервирование CI до запуска, восстановление без слепых повторов,
приоритет отмены и сохранение владельца. В документации прямо указано, что live
runtime, operator UI и проверка реальных Project automations ещё впереди.
После реализации подготовить локальный commit и текст PR; push/merge — владелица.

## 14. Что предлагается подтвердить при валидации плана

1. Обычный PR появляется до окончания CI; основание для review — `PR ready` и
   подтверждённые проверки. Альтернатива с draft требует учесть дополнительный
   `ready_for_review` запуск или отдельно изменить workflow приложения.
2. Один постоянный отчёт находится в issue; тело существующего PR автоматически
   не редактируется ради прогресса. Код обновляется в той же ветке/PR.
3. Закрытый без merge PR не открывается повторно и не заменяется автоматически.
4. При текущих правах повтор CI выполняет оператор; автоматический rerun требует
   отдельного разрешения Actions write и реализации ограниченного endpoint.
5. Native link и действующая Project automation проверяются до live. Если они
   несовместимы с порядком handoff, изменение способа связи согласовывается отдельно.

Это новые уточнения для проверки, а не уже принятые решения владелицы.

Код, тесты и [исполняемый контракт](../github_projects_publication.md) готовы в отдельной

ручной rerun, лимиты, неподтверждённый dev, recovery, чужой отчёт, закрытый PR,
гонка remote ref, hostile Git hooks/config, LFS/submodule и изменения CI-файлов.
Приходящие через Status readback Project fields не дублируются в store.

Обычные PR, постоянный issue comment и ручные Actions reruns приняты как профиль PR-09.
Live writes/O3c пока не проводились. Нет exporter/stop verifier для реального worker,
кнопок PR-10 и рабочего профиля PR-12; live Projects execution остаётся выключенным.

не входит в этот PR и остаётся отдельным условием подготовки к live-пилоту.
