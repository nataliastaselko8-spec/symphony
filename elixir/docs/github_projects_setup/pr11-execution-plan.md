# PR-11 — переносимый запуск и изолированный worker

Дата: 2026-09-17. Статус: **реализация PR-11 в локальной ветке `agent/feat/portable-worker-runtime`**.
Фактический контракт: [runtime/README](../../../runtime/README.md).
Результаты приёмки и оставшиеся эксплуатационные шаги: [pr11-validation.md](pr11-validation.md).

**Уточнение владелицы:** разработчик, скачавший fork, должен настраивать его на своём
компьютере без изменения исходного кода и без копирования личной WSL/файловой конфигурации.

Основной репозиторий PR-11 — `nataliastaselko8-spec/symphony`, текущая локальная
папка разработки — `D:/symphony`. Рабочая ветка — `agent/feat/portable-worker-runtime`,

поставляются вместе с форком. `EmotionStat/agent-runner` хранит профиль проекта (PR-12).
Push и merge выполняет владелица. Изменения продукта и базы знаний в этот этап не входят.
Названия текущих папок здесь описывают место разработки, а не требования к установке.

## 1. Результат и важное уточнение границ

PR-11 должен дать проверенную среду исполнения, средства её установки и обслуживания,
перенос Git-данных без выдачи GitHub credentials worker и предварительную диагностику.
**Обязательное требование владелицы:** процессы, исполняющие задачу (SSH session,
hooks, Codex, проверки и их потомки), не имеют доступа на чтение, просмотр содержимого,
запись или удаление к файловой системе хоста вне явно выделенных ресурсов задачи.
Это условие допуска исполнения и приёмки PR-11, а не рекомендация в prompt агента.

После него другой разработчик сможет повторить установку и проверку тестового worker
в поддерживаемой среде, указав собственные параметры. Приёмка включает чужое имя
пользователя, другой checkout и другое имя WSL distro.

Реальные задачи Project пока не запускаются. В текущем Symphony:

- `symphony --dry-run /absolute/WORKFLOW.md` читает Project и завершается;
  этот режим не поднимает dashboard и несовместим с `--port`;
- `mix github_projects.delivery.inspect --workflow ...` отдельно проверяет delivery;
- обычный startup и reload `github_projects` заблокированы;
- `stop_verifier(worker)` и `export_candidate(cycle, sha)` принимаются как внутренние
  callbacks. YAML и shell launcher сами по себе не могут подключить эти функции.

В PR-11 создаём transport/helper и проверяем его через существующие интерфейсы в
изолированном harness. Необходимые точечные изменения контракта движка также проходят
тесты этого PR в fork. Постоянное подключение в startup Symphony, проверка всей упаковки
и снятие запрета исполнения — PR-13. Не подменяем подключение callback shell-командой,
`mix run -e` или обходом startup guard. Не объявляем интеграцию законченной
по одной успешной проверке shell-скриптов.

Проектный шаблон `WORKFLOW.template.md` и продуктовые hooks создаются в agent-runner в PR-12.
Из шаблона и локальных параметров получается исполняемый `WORKFLOW.md` в локальном config
каталоге разработчика. Путь к нему явно передаётся Symphony; файл не содержит private keys.
Для PR-11 используются явно выбранные fixtures. Отсутствие рабочего профиля выдаёт
понятную ошибку и не включает тестовый профиль автоматически.

## 3. Выбранная схема размещения

| Компонент | Где работает | Что хранит / делает |
| --- | --- | --- |
| Controller Symphony | Выбранная Linux account в настроенном controller distro | Gate/store, App credentials, operator auth, GitHub publisher |
| Управление контейнером | Выбранный worker distro, доверенный host-helper | Container ID, generation, cgroup, stop/export; без бизнес-очереди |
| SSH, hooks и Codex | Внутри rootless Podman-контейнера | Только текущая рабочая копия, необходимые инструменты и собственная авторизация Codex |
| Оператор | Браузер на компьютере разработчика | Review, merge и решения через защищённую панель после интеграции |

Общий код редактируем в fork Symphony. Launcher определяет корень собственного checkout
от расположения скрипта; путь к проектному профилю получает из локальной конфигурации.
Worker image и доверенные host-скрипты доставляем в настроенный distro как проверенный
пакет. Имена Windows-дисков и автоматическое включение interop для этого не требуются.

Рабочие файлы worker, container volumes, controller store, locks и bundles размещаем
в Linux filesystem. Controller secrets находятся вне git и task workspace. Пути
фиксируются в локальной конфигурации и проверяются manifest; они не берутся из текста issue.

Host-helper не дублирует DeliveryGate: его реестр описывает только технические ресурсы
и их принадлежность interval/generation. Он не решает, какую задачу брать, не выдаёт
бюджет, не подтверждает dev и не владеет GitHub credentials.

### Три уровня конфигурации

| Уровень | Что хранится | Где |
| --- | --- | --- |
| Общая поставка | Launcher/preflight, контейнер, transport, схемы, тесты, безопасные defaults | Публичный fork Symphony, `runtime/` |
| Профиль проекта | Repo/Project, ветка dev, правила задач, проверки, бюджеты, шаблон WORKFLOW и hooks | `EmotionStat/agent-runner`, доступный участникам проекта |
| Личная установка | Distro/accounts, host UID/GID mappings, пути, порты, SSH endpoints, ссылки на credentials | Локальный config вне git каждого разработчика |

Названия `EmotionStat`, `app`, номер Project и ветка `dev` допустимы в проектном профиле.
Они не являются личными параметрами компьютера. Общие скрипты получают этот профиль как
входные данные, не ищут его по зашитому пути и не выбирают произвольный fork/upstream.
В текущем движке остаются существующие ограничения delivery-контракта, в частности dev;
адаптация к любым другим продуктовым процессам не входит в требование переносимости.

Первый поддерживаемый вариант установки — Linux runtime через WSL2 + rootless Podman.
Имя и версия distro на host не проверяются сравнением с личным `Ubuntu-26.04`:
проверяются требуемые возможности и совместимость инструментов. Базовый контейнерный
образ имеет общий закреплённый digest. Native Windows/macOS/отдельный сервер нельзя
объявлять поддержанными без собственной приёмки; переносимость путей этого не доказывает.

### Локальная конфигурация и первичная настройка

Добавить `runtime/config/local.example.json` и `runtime/scripts/configure.sh`.
Configure создаёт локальный JSON по явным аргументам либо запрашивает недостающие значения.
Это отдельное действие: preflight не устанавливает службы и не создаёт секреты.
Windows wrapper принимает конфигурацию/явные параметры distro и пользователя, проверяет
их наличие в WSL и передаёт аргументы без построения shell-команд из строк.
При нескольких distro не выбирает первый или личную Ubuntu автоматически.

Локальные поля: `runtime_kind`, controller/worker distro и accounts, корень профиля,
workspaces/state/logs/bundles, worker и management SSH endpoints, dashboard port/origin,
пути к App key/operator credential. UID/GID на host определяются/проверяются при setup;
значение 2002 не становится требованием. UID внутри image может быть общей документированной
константой при проверенном отображении на host. Порты — проверяемые локальные значения.

Порядок разрешения конфигурации: явные CLI параметры → явно выбранный локальный JSON →
общие безопасные defaults. На Linux config/state/cache могут использовать соответствующие
XDG-каталоги текущей account с fallback от её HOME. Никаких `/home/nataselko`, `D:/...`,
скрытого поиска чужих ключей или shell `eval`. Относительные пути разрешаются от каталога
конфигурации/профиля по документированному правилу, а не от cwd терминала. Пробелы и Unicode
поддерживаются; несовместимые пути/права дают объяснение, а не молчаливую подстановку.

Генератор WORKFLOW разрешает только объявленные параметры размещения и credentials references,
валидирует итог через Symphony, не выполняет выражения/команды шаблона. Правила допуска,
бюджеты и Project берутся из проектного профиля; машинная настройка не создаёт второй
набор бизнес-правил. Смена параметров, входящих в scope, требует restart и существующей
процедуры сверки, а не изменения работающего store.

Скачивание публичного форка не даёт доступа к частному `EmotionStat/app` и agent-runner.
Инструкция перечисляет необходимый доступ к профильному репозиторию и разрешённый способ
controller auth. Каждый разработчик выполняет собственный вход Codex. Приватный App key,
operator sessions и snapshot владелицы не распространяются с шаблоном или «готовым архивом».

Путь нового участника по README: скачать fork в удобный каталог → получить разрешённый
доступ и скачать профиль agent-runner → установить поддерживаемые prerequisites →
выполнить configure со своими distro/путями → подключить разрешённую read-only identity →
выполнить preflight/inspection. До назначения единственным рабочим controller роль
остаётся inspection. Для локальных fixtures доступ к приватному проекту не требуется.

### Несколько установок для одного Project

Переносимость установки не равна разрешению нескольких независимых controller одновременно.
Linux flock защищает только один локальный store; он не предотвращает двойной захват задачи
на разных компьютерах. Чтение одной доски и `max_concurrent_agents=1` этого также не доказывают.

**Подтверждено владелицей:** один назначенный активный controller на проект/репозиторий,
остальные установки используют настройку и inspection. В локальном config явная роль,
по умолчанию `inspection`; рабочий профиль проверяет назначение controller и credentials.
Private key рабочего App и credentials с записью остаются только у назначенного controller.
Для живого чтения другой установки нужен отдельно разрешённый read-only credential;
переключение поля роли в JSON само по себе не даёт GitHub-полномочий. Без credentials
доступны локальные проверки/fixtures, а живое чтение честно отмечается как недоступное.
Смена ответственного компьютера
требует подтверждённой остановки старого worker, сохранения/переноса проверенного состояния
и новых локальных credentials, без сброса незавершённого цикла. Изменение host scope не
обходится ручной заменой hash. Два самостоятельных local store не считаются общей очередью.
Если в будущем понадобятся одновременные controller, потребуется отдельная схема координации/lease с
защитой от старого владельца либо единый controller с несколькими worker. Это не выдаётся
за уже реализованную возможность PR-11 и не входит в выбранный режим.

## 4. Порядок реализации и предполагаемые файлы

### Шаг 1. Зафиксировать версии и конфигурационный контракт

Создать `runtime/config/runtime-lock.json`, `runtime/config/deployment.example.json` и валидатор.
Закрепить digest worker image, версии инструментов и конфигурационных контрактов.
Точный commit Symphony записывается в локальный manifest уже принятой сборки;
собственный будущий merge SHA не записывается в runtime-lock того же PR.
`latest` и автоматический `git pull`
при запуске не использовать. Не записывать выдуманные SHA/digest: заполнить после сборки.

Локальный manifest вне git содержит точные ревизии Symphony и проектного профиля,
digest артефактов, версию формата/config и привязку к локальным параметрам. Он не содержит секретов.
Итоговый manifest исполнения создаётся после merge PR-13: будущий merge SHA невозможно
корректно записать в сам этот PR. Начальная версия допускает только inspection/tests.

В PR-12 `agent-runner/config/runner.example.yaml` обновляется как описание проектного
профиля, без машинных параметров и разрешения knowledge-base из app-only профиля.
Symphony продолжает читать front matter `WORKFLOW.md`; второй набор трактовок полей
tracker/delivery/worker не создаём. Launcher использует JSON со стандартным Python parser.

### Шаг 2. Сначала доказать работоспособность границы

До разработки всего launcher провести маленький технический эксперимент на временных
данных: реальный rootless Podman, pasta, SSH и дерево дочерних процессов.
Проверить совместимость выбранного SSH server с непривилегированным запуском, UID mapping,
read-only root, seccomp и отсутствием capabilities у команд worker.

Набор флагов из прежнего `/bin/sh` canary не объявляем автоматически пригодным для sshd.
Сначала проверяем single-user SSH на высоком порту без PAM/password login. Если выбранный
sshd требует дополнительных привилегий, это отдельный результат эксперимента и пересмотр
профиля до его принятия, а не скрытое добавление `--privileged`/`SYS_ADMIN`.

Одновременно проверить принадлежность настоящего pasta и всех сетевых helper-процессов
нужной cgroup, включая переносы systemd, перезапуск и reparenting. Если адресные ограничения
обходятся или cgroup невозможно удержать, рабочий профиль не принимается; подготовить
отдельное решение по сети вместо глобального изменения firewall рабочей Ubuntu.

### Шаг 3. Собрать worker image

Добавить `runtime/worker/Containerfile`, доверенный entrypoint и SSH config.
Установить Linux bash/sh, Git, CA certificates, Codex и зависимости его запуска;
Node/Python и команды продуктовой проверки сверить с текущими требованиями app.
Ранее установленные версии считаются исходными данными, а не автоматически принятым lock.

Ограничения профиля:

- отдельные mount/PID/IPC/network namespaces, без host networking;
- непривилегированный пользователь для hooks, Codex и тестов; проверка реальных UID/GID;
- read-only root filesystem самого образа: его `/usr`, библиотеки и конфигурация;
  записываемые task workspace и необходимые временные каталоги контейнера;
- нет Windows/WSL/WSLg mounts, controller home, Docker/Podman sockets и SSH agent forwarding;
- явно заданные лимиты памяти, CPU, процессов и временного места, подобранные по машине;
- команды запуска и конфигурация SSH не находятся в записываемой worker области.

### Обязательная граница доступа к файлам

| Ресурс | Доступ процесса задачи |
| --- | --- |
| Рабочая копия назначенной задачи в выделенном volume | Чтение/изменение по правилам задачи |
| Выделенные scratch/tmp/cache внутри границы worker | Чтение/запись, ограниченные ресурсами контейнера |
| Инструменты и библиотеки из закреплённого image | Чтение/исполнение; системная часть image без записи |
| Собственная область авторизации Codex | Только необходимый доступ Codex; вне image/git/task workspace |
| Windows-диски и пользовательские папки Windows | Нет доступа, включая чтение и просмотр содержимого |
| Корень Linux-хоста, его `/etc`, `/usr`, домашние каталоги | Не подключаются в контейнер даже read-only |
| Controller home, GitHub App keys, operator auth, delivery store, SSH keys | Нет доступа через файлы, env, процессы или forwarding |
| Рабочие копии других задач и проектов | Нет доступа |
| Host `/proc`, `/sys`, devices, WSL shared paths и management sockets | Нет подключения, позволяющего доступ к host данным/управлению |

Worker читает системные файлы собственного контейнера для запуска Git, shell и Codex.
Это не файлы установленной на компьютере Windows или Ubuntu. Не обещаем запрет чтения
всех файлов с именем `/etc` или `/usr`: проверяется происхождение mount и его доступность.
Минимальные виртуальные `/proc`/devices относятся к контейнеру; процессы/диски хоста
через них не должны быть доступны. DNS/hosts-конфигурация создаётся для контейнера;
произвольные host-конфиги и домашние каталоги не передаются для удобства настройки.

Launcher использует закрытый список mount-ресурсов. В local config можно выбрать
выделенное место хранения, но нельзя добавить произвольный bind mount, host root/home,
`--privileged`, host namespace, management socket или отключить проверку изоляции.
Пути проверяются после разрешения symlinks, включая компоненты и подмену между проверкой
и использованием. Controller state и secrets не могут оказаться внутри экспортируемого
workspace. Небезопасное пересечение путей блокирует запуск вместо изменения прав хоста.

Ни один hook, startup-файл task account или код репозитория не исполняется на host до
входа в контейнер. Вне него работают только доверенные установочные/управляющие helpers.
Host-account, обслуживающая Podman, сама по себе не является sandbox: агенту не выдаётся
обычная shell-сессия этой account вне контейнера. Transport/export не принимает от агента
произвольные host-пути и не превращается в способ чтения файлов controller.

Проверить фактические чтение/запись/листинг на безопасных файлах-маркерах вне разрешённых
volumes, mount table, обходы через symlinks/`..`/`/proc` и сетевые host endpoints.
Тесты не читают реальные секреты и личные документы. Проверку выполнить из настоящей
SSH session, hook и дочернего процесса, повторить после рестарта и смены task workspace.
Если лишний mount/доступ найден или механизм проверки недоступен, разрешение реальных
задач остаётся закрытым. Установка на другом компьютере проходит те же требования.

Эти проверки доказывают настройки и проверенные пути доступа; контейнерный профиль
не описывается как абсолютная гарантия против любых неизвестных уязвимостей общего ядра.

Не подключать одновременно папки других задач. При новом рабочем интервале можно создать
новый контейнер, сохранив volume той же задачи; это не создаёт новую ветку или цикл.
Срок жизни рабочей копии определяется Gate, а не временем жизни контейнера.

Авторизацию Codex пройти отдельно в новой среде. Хранить её вне image/git/task workspace
в отдельной области с ограниченными правами. Сам Codex должен иметь доступ к своей
авторизации и обновлять её; это не означает доступ к GitHub App или operator credential.
Проверка входа и выполнение платного/квотируемого модельного запроса — разные проверки;
полноценный пробный запрос отмечается явно в отчёте.

### Шаг 4. Ограничить сеть и настроить каналы управления

Добавить `runtime/host/` с установочными шаблонами и скриптом проверки/удаления только
собственных правил. Привилегированная установка выполняется отдельно от ежедневного запуска.

Worker SSH публикуется только на настроенном loopback-порту. Значение 2223 — предложение
для текущей машины, а не требование универсального скрипта. Её старый 2222 не используем
для работы и не удаляем до проверки замены. Controller SSH config задаёт фиксированный host key,
BatchMode, отсутствие forwarding и ограниченный timeout; `StrictHostKeyChecking=no` не нужен.

Для controller → host-helper предлагается отдельный локальный SSH endpoint из config с другим
ключом и фиксированным forced-command. Он принимает ограниченные JSON-команды управления
контейнером, без произвольного shell, пути, образа, volume или Podman API от worker.
Порты сначала проверяются на занятость; 2224 — только предложение текущей установки.
Management endpoint недоступен из рабочего контейнера.

Сетевые правила привязываются к проверенной cgroup worker runtime, а не ко всему UID или
общему WSL OUTPUT. Проверяем IPv4 и IPv6, адреса Windows/WSL gateway, loopback controller,
LAN, link-local, host aliases и management endpoints. Нужные публичные соединения для
Codex/зависимостей и DNS работают; исключение DNS не открывает остальные порты host.
Ответы на разрешённые входящие SSH-соединения должны продолжать проходить.

Удаление правил допустимо после остановки защищаемых процессов. Ошибка применения правил
не приводит к запуску без защиты. После WSL restart правила и фактическое размещение
helper-процессов проверяются заново. Тесты на известных локальных endpoints не сканируют LAN.

### Шаг 5. Сделать реальную остановку и защиту от осиротевших процессов

Добавить `runtime/scripts/worker-control.py` и тесты. Предполагаемые операции:
`prepare`, `start`, `status`, `stop`, `export`. Они связаны с выданным controller
interval, generation и container ID. Повторная команда идемпотентна; старая команда
не может остановить новый контейнер или прочитать workspace другой задачи.

После отмены, паузы, исчерпания бюджета или передачи результата:

1. Symphony сохраняет ограничение и отзывает свой permit — существующее поведение.
2. Transport запрашивает остановку контейнера и относящихся к нему дочерних процессов.
3. Host-helper проверяет фактическое завершение контейнера и отсутствие его рабочих
   процессов. Исчезновение только SSH-клиента или OTP PID успехом не считается.
4. Только подтверждённый результат может быть преобразован в `:stopped` для runtime.
   При timeout/ошибке сохраняются `stop_unconfirmed`, занятость задачи и workspace.

Предлагаемые стартовые технические пределы: 10 секунд мягкой остановки, затем принудительное
завершение и до 10 секунд проверки. Это не добавочный рабочий бюджет агента.
Долгие операции и ожидание не должны блокировать обработку операторской отмены в GenServer;
это отдельно проверяется при подключении transport в PR-13.

На worker host нужен watchdog, независимый от процесса controller: стартовое предложение —
heartbeat раз в 10 секунд, остановка при отсутствии 45 секунд или наступлении выданного
deadline, смотря что раньше. Worker не может сам продлевать этот срок. Проверяем потерю SSH,
аварийный kill controller, падение guardian и sleep/restart WSL. Возврат соединения не
перезапускает задачу автоматически: сначала сверка Gate и старого interval.
Не заявляем мгновенную остановку при разрыве сети; верхняя граница должна быть измерена.

### Шаг 6. Доставить код и забрать результат без GitHub-токена у worker

Подготовить transport для Git-данных. Controller читает разрешённый репозиторий своими
credentials и передаёт worker исходные Git-объекты/пакет без credentials. Продуктовая
логика создания ветки и включения свежего dev остаётся в hooks PR-12.

Обратный путь: после подтверждённой остановки рабочие данные становятся недоступны для
записи старому worker. Доверенный exporter формирует bundle только назначенной ветки и
ожидаемого SHA. Обработку недоверенной `.git` проводить в отдельной ограниченной среде
без секретов, с отключёнными hooks/config helpers и без выполнения кода репозитория.
Не запускать Git над worker-controlled repository прямо в секретной области controller.

Bundle передаётся как ограниченный поток, а не как произвольный путь, выбранный агентом.
Controller создаёт новый собственный файл в приватном Linux-каталоге, проверяет размер,
digest, права и полноту передачи, атомарно завершает запись. Текущий publisher ограничивает
bundle 80 MiB; transport не должен молча принимать больший файл или несколько refs.
Повтор той же операции возвращает тот же подтверждённый результат либо ошибку несовпадения.

Затем существующий PR-09 publisher независимо проверяет SHA, ancestry, digest и разрешённые
файлы. Запрет `.github/**`, submodules/LFS, force/delete и `dev`/`main` не ослабляется.
В PR-11 проверяем это на локальном bare remote; живых push/PR по умолчанию нет.

### Шаг 7. Написать preflight с понятными результатами

`runtime/scripts/preflight.sh` вызывает небольшие проверяющие компоненты и выводит для каждого
пункта `PASS`, `FAIL` или `NOT_READY` с действием для исправления. Не заменяет отсутствующее
доказательство успехом. Отдельно показывает «inspection доступна» и «execution заблокировано».

Проверяет версии/pin, пути/права, конфигурацию, host identity, состояние transport,
изоляцию credentials, Project schema и область App, delivery policy/workflow hashes,
доступность deployment evidence и контракта manual validation.
Состояние controller читает через поддерживаемый интерфейс; не создаёт параллельного
владельца store и не принимает новый пустой store за доказательство здорового dev.

Preflight ничего не устанавливает, не чинит и не удаляет state, не стартует hooks/Codex,
не снимает паузу и не пишет в GitHub. Получение временного read-scoped App token допускается.
При отсутствии работающего диагностического контейнера активные проверки обозначаются
как ещё не выполненные; запуск smoke-контейнера — отдельная явная команда.

**Учёт бесплатного GitHub:** не требовать покупку тарифа как условие PR-11 и не выдавать
недоступную branch protection за включённую. Защиту от действий worker проверяем отсутствием
credentials и конечным publisher. Это не запрещает владельцу или другому токену прямой push
в GitHub. Возможности серверных rules фиксируем честно; ручной review/merge остаётся у оператора.
O3c с настоящими записями требует отдельно выбранного тестового объекта.

### Шаг 8. Сделать launcher и обслуживание

Добавить `runtime/scripts/launch.sh`, `stop.sh`, `status.sh` и `runtime-smoke.sh`;
общую логику вынести в небольшой helper без второго scheduler. Все пути к исполняемым
файлам либо вычисляются от расположения поставки, либо берутся из проверенного config/PATH.

Предлагаемый интерфейс, который ещё предстоит реализовать:

```bash
./runtime/scripts/configure.sh        # первичная настройка собственной установки
./runtime/scripts/preflight.sh
./runtime/scripts/launch.sh           # конечная read-only инспекция
./runtime/scripts/status.sh
./runtime/scripts/stop.sh
./runtime/scripts/runtime-smoke.sh    # явная локальная проверка временного worker
```

Путь к fixture передаётся явно в тестах. Запуск из другого cwd не меняет выбор workflow.
`launch.sh --execute` в PR-11 завершается объяснением незавершённой интеграции, даже если
пользователь вручную поменял JSON. Переключатель не обходит запрет в самом Symphony.

Для будущего длительного controller — один локальный lock на profile/store в Linux,
удерживаемый на всём сроке его жизни. Проверять реальный процесс и generation, а не один
устаревший PID-файл. Второй controller не стартует. После аварии оставшийся worker сначала
останавливается/сверяется; освобождение файлового lock не означает готовность очереди.

Остановка не делает reset ветки и не удаляет workspace/store. Restart повторяет preflight,
сохраняет бюджеты и требует сверки. В PR-11 это проверяется на harness; обычный Projects
controller станет доступен через PR-13. Локальное демо панели остаётся отдельным демо.

Добавить тонкий параметризованный PowerShell launcher для Windows: он вызывает
выбранный WSL distro и Linux script, возвращает exit code и не содержит секретов.
Убрать личные значения из существующего `elixir/docs/github_projects_setup/start-dashboard-demo.ps1`
и проверить вызывающий его CMD. Сейчас там явно заданы `/home/nataselko`, `/mnt/d/symphony/elixir`,
`Ubuntu` и `nataselko`; использовать этот скрипт как общий launcher без исправления нельзя.
Демо остаётся отдельным тестовым сценарием, создаваемым из переносимых fixtures.
Автозапуск с Windows и распределённое управление несколькими компьютерами не входят в PR.

## 5. Документация и проверяемые изменения

В форке обновить `README.md`, `elixir/README.md`, `.gitignore` и операционные README рядом
с `runtime/`; при изменении контрактов — SPEC/WORKFLOW example. В README объяснить
размещение ключей, ручной вход
Codex, установку/снятие только своих служб, start/status/stop и действия при отказе.
Архитектурный канон базы знаний пока не переносим.

В git не попадают private keys, operator credentials, Codex auth, локальные config/manifest/WORKFLOW,

Проверки не печатают секреты и не собирают произвольное окружение в отчёт.

Ожидаемые группы файлов в fork: `runtime/config/`, `runtime/worker/`, `runtime/host/`,
`runtime/scripts/`, `runtime/tests/`, README/ignore и существующий демо-launcher.
В agent-runner остаются только проектные файлы PR-12 и при необходимости тонкий вызов

Имена внутренних helpers могут уточняться при реализации;
контракты и границы PR от этого не расширяются.

## 6. Приёмочные проверки

| Сценарий | Ожидаемый результат |
| --- | --- |
| Запуск без параметров | Конечная инспекция; нет hooks, агентов и GitHub writes |
| Чужое имя account, другой UID/GID, distro и порт | Работает через config без изменения исходников |
| Checkout в другом каталоге/на другом диске, пробелы/Unicode | Пути разрешаются корректно, нет shell-интерполяции |
| Запуск из другого cwd | Тот же явно выбранный профиль |
| Личные папки владелицы отсутствуют | Общий запуск не обращается к ним |
| Неполный config / несколько WSL distro | Понятная ошибка/запрос при configure, без догадок preflight |
| Общие шаблоны и новый clone | Нет личных значений, credentials и состояния прежнего разработчика |
| Нет WORKFLOW, неверный pin, чужой scope | Понятный отказ, без fallback на случайный профиль |
| Второй controller | Отказ до начала исполнения |
| Ошибка SSH/host key/недоступный management helper | Нет локального fallback выполнения |
| Реальные SSH, hooks, Codex и background child | Все команды внутри проверенной границы |
| Windows/controller paths и management sockets | Недоступны из рабочего контейнера |
| Чтение/листинг/запись host-маркеров вне разрешённых volumes | Отказ для SSH, hooks, Codex child и после restart |
| Попытка добавить host root/home или обойти путь symlink/`..` | Отказ конфигурации/transport до исполнения задачи |
| Системные библиотеки контейнера | Инструменты работают, rootfs образа не изменяется |
| Сетевые обращения к controller/Windows/host | Отказ IPv4/IPv6; остальные проекты продолжают работать |
| Нужные публичные соединения и DNS | Работают внутри заданной политики |
| Отмена, timeout, controller crash | Измеренная остановка дерева; неопределённость удерживает блокировку |
| Старая stop/export команда после restart | Не влияет на новый interval/container |
| Подмена/обрыв/слишком большой bundle, опасная Git config | Экспорт/публикация отклонены без исполнения worker кода |
| Возобновление той же задачи | Сохранены её Git-данные; другие workspaces не подключены |
| WSL restart и восстановление служб | Защита проверена до worker; задача сама не продолжается |

Проверки разделить на быстрые Python/shell unit и contract tests, Linux-интеграцию с
настоящим Podman/SSH/сетью и диагностическое read-only чтение GitHub. Выполнить `git diff --check`,
`bash -n`, статическую проверку shell и тесты helpers. Где проверка пропущена — причина и влияние
на готовность. Если меняется Symphony, необходимы его targeted tests и полный `make -C elixir all`.

До принятия отдельно попытаться нарушить ограничения через startup-файлы, symlinks,
переиспользование PID/container ID, фоновые процессы, потерю ответа и несовместимый manifest.
Пройденные старые canary не заменяют эти проверки рабочего профиля. Добавить проверку
на личные path/account/distro literals в общих executable/templates и clean-clone сценарий
по README. Исторические журналы настройки отделены от переносимой инструкции; одинаковое
имя стандартного Linux-каталога или фиксированный digest образа не считать личным параметром.

## 7. Порядок коммитов и критерий завершения

Предлагаемые логические коммиты в ветке fork Symphony:

1. Три уровня конфигурации, configure/manifest/pin и устранение личных привязок демо.
2. Рабочий image, SSH и ограниченная host/network установка после технического эксперимента.
3. Lifecycle helper, watchdog, stop proof и транспорт Git-данных.
4. Preflight, launcher, тесты и эксплуатационная документация.

PR-11 готов, когда эти компоненты воспроизводимо проверены на поддерживаемом WSL2,
включая независимые параметры второй установки без правки исходников,
сохранена работа при остановке и нет открытых дефектов изоляции/экспорта. Отчёт содержит
точные версии и результаты, отдельно от списка ещё не подключённых возможностей.
Владелица получает ветку, коммиты, описание PR и короткую инструкцию проверки.

После принятия PR-11: PR-12 — рабочий WORKFLOW и dev-based hooks; PR-13 — подключение
transport к обычному startup и приёмка всей системы; PR-14 — одна выбранная живая задача.
Известные advisories зависимостей Symphony должны быть рассмотрены и необходимые обновления
проверены до live runtime; PR-11 сам по себе их не устраняет.

## 8. Подтверждения перед настройкой компьютера

Выбор WSL2, GitHub App и единственного оператора сделан для текущей установки;
это не личные defaults для остальных разработчиков. Повторять вопросы о текущей машине не нужно.
Для реализации нужны подтверждённый merge PR-10, доступ к новому distro и готовность
выполнить там отдельный установочный шаг с root. Вход ChatGPT выполняет пользователь установки;
пароли и содержимое private key в чат не передаются. Пути/порты сначала определяем и
проверяем автоматически. Если они конфликтуют с существующей настройкой, предложим конкретную замену.

Техническая опора: [Podman run](https://docs.podman.io/en/latest/markdown/podman-run.1.html)
описывает namespaces, capabilities, network и mounts; сами по себе эти настройки не
подтверждают наш профиль. [WSL configuration](https://learn.microsoft.com/en-us/windows/wsl/wsl-config)
разделяет настройки конкретного distro и общие настройки WSL. При реализации сверять
флаги с фактически установленной версией, а результат — с тестами на этом компьютере.
