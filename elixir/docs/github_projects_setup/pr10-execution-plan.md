## 1. Что получится

В существующем дашборде Symphony появится защищённая панель единственного оператора.
Владелица увидит задачу, PR, результаты проверок и деплоя, состояние среды,
причину закрытой очереди Symphony и конкретное доступное действие.

Через панель можно будет записать ручную проверку dev, сообщить о проблеме,
приостановить работу, запросить отмену, назначить существующую recovery-задачу,
вернуть открытый PR на доработку и явно выдать дополнительный бюджет.
Каждое решение проверяет сервер и сохраняет существующий DeliveryGate.

Две очереди называем по-разному:

- **Очередь задач Symphony** — разрешён ли запуск следующей продуктовой задачи.
- **Cloudflare Queue приложения** — доставка сообщений приложения, которая могла остаться на паузе.

Кнопка в панели не означает запуск агента сама по себе. Сначала фиксируется решение,
затем runtime отдельно проверяет все условия допуска.

## 2. Границы PR

Изменения относятся к Symphony, её тестам, документации и локальному демо панели.
В продукте `EmotionStat/app`, базе знаний и `D:/agent-runner` изменений нет.

В этот PR не входят merge, deployment, управление Cloudflare, создание issue,
изменение `Agent allowed`, новый GitHub OAuth flow или расширение App до `Actions: write`.
Повтор Actions без изменения кода владелица по-прежнему запускает в GitHub.
Панель показывает ссылку на запуск и учитываемые попытки.

Реальное исполнение `github_projects` остаётся отключено startup/reload guards.
PR-11 обеспечивает worker isolation, экспорт Git bundle и доказательство остановки;
PR-12 — рабочий WORKFLOW и hooks; PR-13 — объединённую приёмку допуска.
PR-10 не включает обходы этих ограничений ради демонстрации кнопок.

Для приёмки используем настоящий Gate/Runtime с отдельным тестовым store и управляемыми
ответами observer. Тестовое демо не получает реальные App secrets, не вызывает publisher,
hooks или Codex и явно помечено «Демонстрация — реальные задачи не выполняются».

## 3. Что обнаружено в текущем коде

1. `Orchestrator.snapshot` уже содержит внутреннее поле `delivery`, но Presenter пока
   не выводит его в панель. Создаём безопасное представление, не отдаём сырой store.
2. `DeliveryRuntime.command` предназначен для доверенного controller. Его нельзя
   опубликовать как универсальный HTTP endpoint с произвольными `action` и `args`.
3. Browser pipeline имеет CSRF plug, но операторского входа нет, а JSON refresh
   находится вне этого pipeline. Защита нужна каждому соответствующему пути.
4. В `config.exs` есть известный placeholder signing key и `check_origin: false`.
   Однако `HttpServer.start_link` уже заменяет ключ случайным при обычном запуске.
   Сохраняем это свойство и закрываем альтернативные пути запуска с placeholder;
   не описываем текущий обычный сервер как использующий постоянный известный ключ.
5. Модель имеет `validate_dev`, `complete`, `finish_recovery`, `finish_cancel`,
   но операторского пути, связывающего их со свежими внешними фактами, ещё нет.
6. `validate_dev` требует `environment_ready=true` даже для отрицательного результата.
   Поэтому сообщение о проблеме при неготовой/неизвестной среде требует отдельного
   узкого перехода, который закрывает допуск и не утверждает успешность deployment.
7. `bootstrap` существует только для первого запуска. Подтвердить новый dev без активного
   цикла либо обновить базу при приостановленной до merge задаче сейчас нельзя тем же
   вызовом. Добавляем явное обновление подтверждённой базы, сохраняющее владельца задачи.
8. `environment_ready=false` при унаследованной паузе Queue берётся из неизменяемого
   deployment artifact. Простое повторное скачивание не обнаружит ручное снятие паузы.
9. Открытый PR в `PR ready` не проходит допуск worker по одному `review_resume`:
   Project Status тоже должен разрешать работу. В форме явно покажем это условие.

## 4. Решение, которое нужно подтвердить

**Источник состояния Queue после ручного снятия паузы пока не выбран.**
Вопрос отправлен владелице при подготовке этого плана; ответ не предполагается.

Предложение для MVP: оператор заново проверяет нужные Queue и Scheduler в Cloudflare,
затем сохраняет отдельное ручное подтверждение в Symphony с комментарием.
Автоматическое чтение Cloudflare API потребует отдельного read-only credential,
фиксированных resource IDs и уточнения объёма интеграции.

Раздел 9 ниже описывает предлагаемый ручной вариант, **а не уже согласованное решение**.
Остальные части PR можно реализовывать независимо. До выбора и реализации источника
ветка «Queue оставалась на паузе» сохраняет блокировку и не допускается к пилоту.

Для входа предлагается локальный секрет оператора, описанный ниже. Это техническое
предложение в составе плана; новый GitHub App или OAuth-регистрация не требуются.

## 6. Шаг 2 — добавить вход единственного оператора

### Вход и хранение секрета

- Один principal в доверенной конфигурации controller, например `local:owner`, с именем
  владелицы для отображения. Это локальная подтверждённая credential identity;
  она не выдаётся за проверку GitHub-аккаунта через OAuth.
- Локальная setup-команда создаёт криптографически случайный секрет не менее 32 байт
  в отдельном Linux-каталоге controller вне git, `/mnt` и workspace worker.
  Каталог — `0700`, файл — `0600`, проверяются владелец и отсутствие symlink.
- Секрет вводится в форму входа; не передаётся через URL, query string или localStorage.
  Не попадает в логи, GitHub, отчёты, store цикла и окружение worker.
- App private key и installation token не являются credential оператора.
- Повторный запуск не заменяет существующий секрет. Ротация — отдельное явное действие,
  которое отзывает активные сессии и требует нового входа.

### Сессия и веб-защита

- Случайный идентификатор сессии; сервер проверяет её действительность при запросах,
  подключении LiveView и каждом изменяющем событии. Actor всегда берётся на сервере.
- Предлагаемые сроки: максимум 8 часов сессии и 30 минут без действий оператора.
  Автообновление экрана не продлевает срок бездействия.
- Logout, expiry, ротация и restart отзывают сессию; открытый WebSocket тоже теряет права.
  Сессии и формы могут храниться в памяти controller, delivery decisions остаются на диске.
- Cookie: `HttpOnly`, `SameSite=Strict`; для HTTPS — `Secure`. В MVP допускается HTTP
  только на явно разрешённом loopback origin. LAN/public bind с operator actions не включаем.
- Проверять точные Host и Origin с портом; произвольные forwarded headers не доверять.
  CORS wildcard и `check_origin: false` для операторского режима запрещены.
- Сохранять CSRF protection для входа, выхода, JSON POST и форм. GET не изменяет состояние.
  Скрытая/disabled кнопка не считается контролем доступа.
- Ограничить частоту входа и обновлений, размер payload и длину комментария.
- Закрыть приватные delivery read endpoints, refresh и mutations в операторском профиле.
  Существующий режим observability для остальных trackers не получает операторских прав.
- Без корректных auth settings control routes не запускаются в открытом режиме.

Phoenix требует проверки как HTTP, так и LiveView-событий; это отражено в
[официальной модели безопасности](https://phoenix-live-view.hexdocs.pm/security-model.html).
CSRF для session-authenticated JSON и форм опирается на
[Plug.CSRFProtection](https://plug.hexdocs.pm/1.19.1/Plug.CSRFProtection.html).
Реализацию сверить с закреплёнными в проекте версиями библиотек, не обновлять их автоматически.

Полная недоступность operator credential, store и controller endpoints для worker
доказывается фактическими тестами PR-11. Loopback сам по себе такую границу не создаёт.

## 7. Шаг 3 — единый обработчик операторских действий

Поток: авторизованная форма → проверка конкретного действия → Runtime → DeliveryGate
→ существующий атомарный store. Второго delivery store и второго писателя нет.

Разрешаем конечный список операторских действий. Внутренние `checkpoint`, `effect_sent`,
`observe_ci`, `merged` и произвольный `deployment` недоступны из формы/HTTP.
Клиент не выбирает actor, server time, repo, workflow, branch, бюджеты без ограничений
или внутреннюю команду. Переданные лишние поля отклоняются.

Для формы controller фиксирует:

- operation ID, действие, principal и срок действия формы;
- scope, ID цикла, epoch/revision;
- текущие dev SHA, workflow ID, run ID и attempt;
- PR/head, если действие относится к review;
- версию обязательных критериев и источник readiness.

Форма действует до 30 минут и до любого существенного изменения контекста.
Перед разрешающим действием запускается свежая сверка GitHub. После сетевого чтения
повторно проверяются сессия, отмена, revision и все привязанные факты. Долгое чтение
не блокирует GenServer и возможность отменить задачу.

Изменился SHA, deployment attempt, PR head, scope или cycle — отказ с пояснением
«Данные изменились. Обновите форму и проверьте актуальную версию». Проверенный
комментарий можно сохранить как черновик, галочки не переносятся как доказательство.

Двойной submit с тем же operation ID возвращает сохранённый результат без повторного
расширения бюджета или назначения recovery. Изменённый payload с тем же ID отклоняется.
После потери ответа панель сначала выясняет результат исходной операции.

Состояние GitHub не блокируется транзакцией вместе с локальным store. Свежая проверка
сокращает окно гонки, а последующие admission/watch перед запуском и публикацией снова
проверяют основание. Не обещаем атомарность между GitHub, Cloudflare и локальным файлом.

Пауза, сообщение о проблеме и запрос отмены только ограничивают работу: они должны
сохраняться при недоступном GitHub, если доступен локальный store и известен текущий цикл.
Они не превращают неподтверждённые внешние факты в успешные. Смена самой задачи требует
обновить адресованное ей решение; отмена не должна случайно относиться к преемнику.

Новый универсальный CLI для mutations не создаём. Setup-команда работает с credential,
не редактирует delivery JSON. Будущий управляющий CLI обязан использовать тот же
авторизованный обработчик и единственного владельца store.

## 8. Шаг 4 — ручная проверка dev и завершение цикла

### Положительный результат

Форма показывает конкретную версию dev, deployment run/attempt, время чтения
и отдельно источник готовности среды. Обязательные критерии первой версии:

1. Приложение и нужный API доступны.
2. Контрольный сценарий с тестовыми данными выполнен.
3. Scheduler, Queue и доставка проверены и соответствуют ожидаемому состоянию.
4. Добавлен непустой комментарий о проверке; можно добавить ссылку на evidence.

Точные шаги продуктового сценария уточняются перед пилотом; PR-10 не выдумывает
проверенные бизнес-сценарии. Список критериев имеет версию в доверенном профиле.
Обновление критериев делает старую открытую форму непригодной.

Сервер проверяет deployment и finalizers, текущий dev, readiness, критерии и версию.
Положительное решение проходит следующие варианты:

| Ситуация | Результат |
| --- | --- |
| Первый запуск, активного цикла нет | Bootstrap подтверждённой базы |
| Dev изменился вне цикла | Записать новое подтверждение базы после полной проверки |
| Обычная задача merged | Сохранить validation и завершить её цикл |
| Recovery выполнена, исходная задача уже merged | Завершить восстановление и освободить очередь |
| Recovery выполнена, исходная задача ещё не merged | Восстановить исходного владельца A; задача B не допускается |
| Исходная задача приостановлена до merge, dev восстановлен вручную | Обновить базу, сохранить A; продолжение требует её собственного допуска |
| Задача отменяется после merge | Сохранить validation; завершение отмены также требует остальных доказательств |

Уточнение реализации: validation и допустимое техническое завершение применяются
одной атомарной записью Gate. Авария не оставляет половину перехода; повтор operation ID
не создаёт новый ручной результат. Это устраняет потребность в отдельном механизме
продолжения completion после сохранённой validation. При отказе любого условия
весь переход отклоняется и очередь остаётся закрытой.

Возврат A не запускает её прямо из HTTP. Карточка должна быть разрешена в Project;
если статус всё ещё `PR ready`/`Human review`, панель объясняет необходимое действие
оператора. Автоматический перевод карточек и `Done` в этом PR не добавляются.

### Отрицательный результат и «Обнаружена проблема»

Комментарий обязателен, все успешные галочки — нет. Уточнение реализации: во всех
случаях сохраняется отдельный `environment_problem` и блокировка без подмены deployment
facts. Этот единый переход работает и при успешном deployment, и без подтверждённой
readiness, и без активной задачи; прежняя baseline становится недействительной.

Результат: очередь Symphony закрыта, текущая работа сохранена, отображается причина.
Issue, ветка, PR, recovery и rollback автоматически не создаются. При отсутствии
активного цикла сохраняется запрет новой работы и недействительность старого допуска,
а не фиктивный владелец задачи. Новая успешная проверка требует свежего контекста.

## 9. Шаг 5 — разделить deployment и готовность Queue

На экране всегда три независимых результата:

1. **Deployment** — что завершилось в GitHub Actions.
2. **Среда** — Scheduler/Queue и источник сведений об их состоянии.
3. **Ручная проверка dev** — pending, passed или failed.

Успех deployment с `inherited_pause` отображается как:
«Деплой выполнен. Cloudflare Queue сохранила исходную паузу. Перед проверкой dev
нужно снять паузу и подтвердить текущее состояние». Это не ошибка кода/деплоя.

Если владелица выберет ручной вариант из раздела 4:

1. Оператор вручную снимает паузу в Cloudflare и проверяет правильные dev-ресурсы.
2. Отдельная форма фиксирует, какие Queue/Scheduler проверены, требуемое состояние,
   комментарий, server time и привязку к текущему deployment proof.
3. Controller сверяет неизменность GitHub proof и полноту исходного deployment evidence.
4. Записывается отдельное **ручное evidence**, не переписывается GitHub artifact.
5. Только блокировка `resume_queue_before_dev_validation` может быть удовлетворена
   этим evidence. Ошибки deploy/finalizers, protective pause, неизвестный результат,
   удалённый/истёкший artifact и изменение workflow этим не перекрываются.
6. После этого доступна форма проверки приложения. До её успешного результата
   очередь Symphony всё ещё закрыта. Предлагаемый срок между подтверждением состояния
   Queue и записью проверки dev — не более 30 минут; иначе состояние проверяется заново.

Manual evidence сохраняется рядом с циклом/подтверждённой базой и содержит source,
deployment proof, критерии, actor и время. Повторное чтение старого artifact не должно
ни стирать эту запись, ни выдавать её за свежий ответ Cloudflare API. Новые SHA/run/attempt,
несовместимый scope и восстановление старой копии требуют нового подтверждения.

Observer, admission и завершение цикла используют одинаковую проверку допустимости
этого дополнения. Недостаточно только нарисовать зелёную метку в UI или записать
`environment_ready=true`, которое следующий poll перезапишет старым artifact.

Этот вариант доверяет актуальному свидетельству оператора. Он не обнаруживает
автоматически последующие изменения Cloudflare вне Symphony; источник явно показан.
Если требуется такая автоматическая проверка, выбирается API-вариант с отдельным планом.

## 10. Шаг 6 — recovery, отмена, пауза и review

| Действие | Что проверяет и сохраняет сервер |
| --- | --- |
| Назначить recovery | Остановку, отсутствие неизвестных операций, текущий dev, существующую подходящую карточку, причину и отдельный бюджет |
| Приостановить работу | Actor/reason и постоянный запрет продолжения; действующий worker останавливается |
| Продолжить ту же задачу | Свежий здоровый dev, тот же owner, отсутствие отмены, допустимую фазу и оставшийся бюджет |
| Вернуть PR на доработку | Тот же открытый PR/head/branch, актуальный dev, разрешение карточки, причину и явное добавление бюджета |
| Запросить отмену | ID текущего цикла, operator decision; отзыв допуска и начало остановки |
| Завершить отмену | Подтверждённую остановку, исход внешних операций и факт merge; после merge — deployment и validation |

Recovery выбирается только из текущего repo/Project/item allowlist: открытая issue,
Ready for agent, `Agent allowed=yes`, нужные labels. Клиент не присылает произвольный
repo/ref; controller проверяет item и генерирует новую ветку от текущего dev.
Первоначальный владелец сохраняется как suspended; второй recovery поверх первого запрещён.
Кнопка показывает «Назначена» только после записи, а не после выбора в списке.

Для review владелица возвращает карточку в разрешённый статус на доске, затем использует
«Вернуть на доработку». Панель проверяет это условие и сохраняет прежний открытый PR.
Закрытый/merged PR не переоткрывается. Обновления dev входят обычным merge в task branch
на последующих этапах runner; force push/reset не появляются.

Отмена не означает закрытие PR в GitHub, удаление ветки, остановку уже принятого GitHub
запроса или откат deployment. До merge панель предупреждает о сохранённом открытом PR;
владелица закрывает его вручную, если его больше нельзя сливать. Перед освобождением
допуска повторно проверяются PR и dev, а не только сохранённый флаг `merge_sha`.

Если merge уже произошёл или случился во время отмены, цикл остаётся занятым до проверки
среды. Отмена recovery возвращает исходную задачу в заблокированное состояние.
При `stop_unconfirmed` кнопка подтверждения не заменяет проверку внешних процессов.
Если модель запрещает recovery при pending cancellation, панель объясняет ручное
восстановление среды; не отменяет cancellation и не запускает новую задачу скрытно.

Пауза должна переживать refresh/restart, включая момент, когда активного цикла нет.
Возобновление снимает только операторскую паузу, сохраняя все остальные причины запрета.

## 11. Шаг 7 — бюджеты и неопределённые результаты

На карточке показываются отдельно потрачено, зарезервировано, осталось и неопределённый
расход. Исходные лимиты сохраняются:

| Лимит | Значение |
| --- | --- |
| Первоначальная работа | 60 минут активного времени |
| Исправления CI | Ещё 60 минут суммарно, отдельно от первоначальной работы |
| Циклы исправления | 2 |
| CI-попытки | 6, включая первоначальные запуски и повторы |
| Повторы на одном SHA | 2 |
| Verify приложения | Уже согласованные 20 минут; workflow здесь не меняется |

Ожидание Actions и оператора не тратит активное время. Дашборд показывает, подтверждена ли
остановка worker; текст «ожидание» сам по себе не прекращает учёт времени.

«Добавить бюджет» — отдельная форма с причиной, конкретными положительными приращениями
и предпросмотром итоговых лимитов. Пустое поле означает отсутствие добавления.
Нельзя уменьшить расход, обнулить счётчики, переносить минуты между категориями или
повторным submit получить прибавку дважды. Добавление бюджета само не разрешает работу.

Неизвестный результат публикации/CI остаётся отдельной причиной остановки. UI не предлагает
безусловное «Считать успешным». Проверяемые локальные repair actions используют существующие
ограничения: резерв не возвращается по одному заявлению, что CI якобы не запускался.

Расширенные действия восстановления показываются отдельно от ежедневных кнопок:
восстановление проверенной previous-копии с сохранением повреждённого файла,
разрешение неопределённого интервала после внешней проверки остановки и restart.
Если доказательства или production verifier отсутствуют, действие остаётся недоступным
с понятной причиной. Сброс store или ручное редактирование JSON в интерфейс не добавляются.

## 12. Шаг 8 — построить экран и журнал решений

Верхняя часть: repo/Project, режим, очередь Symphony, причина блокировки, время
последней успешной сверки и индикатор устаревших данных. Далее:

- Текущий owner и recovery при наличии; issue, ветка, PR/head, основная задача.
- Этапы: работа → CI → review/merge → deployment → среда → ручная проверка.
- Ссылка на точный GitHub run/attempt и PR. Статусы cancelled/unknown не зелёные.
- Остатки бюджета и понятные разрешённые действия с объяснением недоступных.
- Журнал: кто, когда, для какой версии принял решение, причина и результат.

Панель на русском, с читаемыми названиями и подписями; технические IDs доступны
в подробностях. Формы работают на узком экране и с клавиатуры, ошибки привязаны к полям.
Фокус после ошибки сохраняется предсказуемо, статус отправки объявляется доступным способом.

Данные выдаются по allowlist: не выводим credentials, permit nonce, bundle paths,
сырой GitHub response, HTML из issue или полное внутреннее содержимое store.
Тексты экранируются; ссылки проверяются. Не загружаем автоматически произвольный URL
из комментария/evidence. Логи auth не содержат введённые секреты.

Audit использует существующий постоянный журнал Gate для принятых решений.
Actor и timestamp назначает controller. Безопасные сведения об отказах идут в журнал
сервера, а не создают новый delivery revision на каждую ошибку входа.

## 13. Шаг 9 — состояние, версии и восстановление

Новые постоянные состояния pause, baseline validation и readiness evidence требуют
явной версии контракта. Предлагается `runtime_contract=3`; конкретная схема и переходы
фиксируются до записи первого нового store. История расхода, владение и отмена сохраняются.

Старый store не удаляется, не переименовывается в пустой и не принимается с новым hash
без проверки. При несовместимости панель объясняет, что требуется согласованный перенос;
автоматический reset не делаем. Отсутствие незавершённой работы проверяется перед bootstrap.
Пустой новый файл сам по себе не доказывает отсутствие чужой активной задачи/PR.

После восстановления backup старые сессии/формы и ручные подтверждения не разрешают
работу. Расход считается консервативно по существующим правилам. Политика/критерии/scope
не подменяются сменой конфигурации без restart и повторной сверки.

## 15. Шаг 10 — проверки и критерии приёмки

### Авторизация

- Прямой HTTP/LiveView вызов без входа отклоняется независимо от видимости кнопки.
- Поддельный actor, чужой operation ID, отсутствующий CSRF, чужой Host/Origin,
  истёкшая/отозванная сессия, старый socket после logout не изменяют state.
- Невалидная конфигурация/placeholder secret не открывают operator mode.
- Секреты не появляются в HTML, JSON, логах и delivery snapshot.

### Цикл и конкурентность

- Успешные Actions без ручной validation не открывают очередь.
- Новый SHA либо attempt при том же SHA делает форму устаревшей.
- Двойной submit не удваивает бюджет и не создаёт вторую recovery.
- Падение после записи решения до ответа сохраняет подтверждённый результат.
- Validation и completion сохраняются атомарно; неуспешная запись не освобождает owner.
- Отрицательное решение работает при незавершённой готовности среды и при отсутствии цикла.
- Пауза и отмена останавливают/запрещают работу даже при недоступном GitHub;
  успешное возобновление требует свежих данных.
- Pre/post-merge cancellation, merge во время отмены, неизвестная публикация,
  неподтверждённая остановка и cancellation recovery не освобождают цикл преждевременно.
- Recovery до merge возвращает A; B не начинает работу. Review сохраняет branch/PR и расходы.
- Начальная validation и обновление baseline без активной задачи не обходят проверку dev.

### Queue — после выбора источника

- `inherited_pause` показывает успешный deployment и отдельную незавершённую readiness.
- Повтор старого artifact не считается новым подтверждением Queue.
- Ручное evidence, если согласовано, строго связано с proof и снимает только допустимый blocker.
- Artifact expired/missing, сломанные finalizers и новый run не перекрываются ручными галочками.
- Допустимое evidence одинаково учитывается UI, observer, admission и завершением.

### Выполнение проверок

Использовать реальные OTP-процессы и store, управляемые часы, управляемые задержки observer.
Ожидать нужное состояние, а не надеяться на порядок планирования или фиксированный sleep.
После целевых тестов выполнить `make -C elixir all`, PR body validation и `git diff --check`.
Порог покрытия и список исключений не ослаблять.

В браузере проверить форму входа и основные сценарии тестового демо на desktop/mobile,
включая stale submit и повторный вход. Fixtures помечены; демонстрация не подтверждает
реальную изоляцию worker или живые GitHub/Cloudflare права.

Существующие advisories зависимостей не считать исправленными этой работой. Отдельно
проверить, не препятствуют ли они безопасному operator runtime; необходимые обновления
зависимостей до live отражаются в самостоятельном объёме, а не исчезают из отчёта.

## 16. Что проверяет владелица перед принятием PR

1. Понятно, какая задача удерживает очередь и почему следующая не запускается.
2. Deployment success, готовность Queue/Scheduler и ручная validation различимы.
3. Форма показывает проверяемую версию; устаревшую форму нельзя подтвердить.
4. «Обнаружена проблема» сохраняет комментарий и блокировку без автоматического recovery.
5. Назначение recovery и отмена объясняют последствия до отправки.
6. Возврат на доработку сохраняет исходный PR и показывает необходимый статус Project.
7. Дополнительный бюджет выдаётся явно; ожидание не представлено как расход активного времени.
8. Logout закрывает права во всех открытых вкладках; App bot не может подтвердить dev.
9. Перезапуск не теряет решения, владельца, паузу, отмену и расход.
10. Панель честно показывает, что до PR-11–PR-13 реальный запуск задач ещё запрещён.

На выходе реализации: отдельная ветка и локальный коммит/коммиты, подробный отчёт проверок,
описание PR по шаблону, инструкция настройки operator credential и сценарий демонстрации.
Push и merge остаются за владелицей. После принятия — PR-11 в `EmotionStat/agent-runner`.
