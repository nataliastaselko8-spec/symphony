# PR13 — подключение изолированного runtime и системная приёмка

Дата: 2026-09-17. Статус: **реализация PR13; приёмка ещё не завершена**.

Основной репозиторий: личный fork `nataliastaselko8-spec/symphony`, база `main`.
Предлагаемая ветка: `agent/feat/projects-runtime-integration`.
Предлагаемый title: `Integrate the isolated GitHub Projects execution lifecycle`.

Зависимости: принятые PR04–PR12; особенно delivery gate/store, observer, lifecycle,
publisher, operator UI, изолированный runtime и проектный профиль.
[Общий план](../github_projects_pr_rollout_plan.md),
[границы интеграции после PR12](pr12-execution-plan.md#13-явные-точки-интеграции-pr-13),
[результаты PR12](pr12-validation.md).

## 1. Результат этапа

После PR13 владелица сможет явно запустить проверенную сборку controller, открыть
дашборд и подготовить её к одному пилотному циклу. После допуска worker получает
код, выполняет hooks и Codex внутри контейнера, останавливается с подтверждением,
а controller принимает результат и обслуживает существующий delivery cycle.

PR13 включает **интеграцию кода**, а не только повторение тестов: сейчас отдельные
компоненты ещё не соединены в рабочий startup. Снятие общего запрета запуска без
закрытия перечисленных ниже разрывов не считается результатом.

Системные сценарии выполняются на тестовых GitHub-ответах и временных repositories;
контейнерная приёмка отдельно использует настоящий Podman/SSH. Выполнение реальной
карточки EmotionStat, её продуктовый PR, merge и deployment относятся к PR14.

По умолчанию установка остаётся в inspection. Скачивание fork, успешный preflight,
выбор роли controller или открытие дашборда сами по себе не запускают задачи.

## 2. Исходное состояние и границы изменений

### Дополнение: модель и уровень рассуждений

- После отдельного входа Codex команда `runtime models` получает `model/list`
  в пустом изолированном контейнере с той же авторизацией. Обрабатывается пагинация;
  список моделей и допустимых `reasoning effort` не зашивается в fork.
- Оператор выбирает **оба** значения через `runtime select-model --model … --effort …`.
  Выбор хранится в приватном `state_root/model-selection.json` этой установки,
  отдельно от проектного шаблона и Git. Изменение допускается только при остановленном launcher.
- Controller сохраняет пару в неизменяемой привязке цикла до первой рабочей попытки.
  Продолжение, исправление и восстановление той же задачи используют ту же пару;
  несовпадение с локальным выбором блокирует запуск, не сбрасывая бюджет.
- Перед первой отправкой задачи app-server повторно проверяет свежий `model/list`,
  явно получает `model` и `config.model_reasoning_effort` в `thread/start`, затем
  должен подтвердить именно эти `model` и `reasoningEffort`. Каждый `turn/start`
  содержит ту же пару как `model` и `effort`.
- Дашборд различает выбранную пару и подтверждённую app-server. До подтверждения
  фактически применённые параметры не заявляются. Нет выбора, модель недоступна,
  уровень не поддерживается или ответ отличается — видимая блокировка без подмены.
- `reasoning effort` («усиление») не добавляет прав, времени или CI-попыток.
  Выбор в desktop-окне Codex на worker не переносится. Реальную пару выбирает
  владелица при подготовке пилота; реализация не назначает модель автоматически.

Источники контракта: [app-server](https://learn.chatgpt.com/docs/app-server)
и JSON Schema установленного Codex CLI 0.154.0 (`ThreadStartResponse`, `TurnStartParams`).

При подготовке плана локальная Symphony находилась на чистой ветке
`agent/fix/worker-bundle-transfer`, HEAD `f998eec`; кодовый companion PR12 —
`1f6944c`. Принятие этих изменений в удалённый `main` здесь не проверялось.
Начинать реализацию следует с проверки актуальной базы после действий владелицы,
без переноса незамеченных локальных изменений и без создания PR в upstream.

PR12 прошёл локальную приёмку: 36 шагов проверки app, hooks/handoff и runtime smoke.
Одобренный предел отдельного файла — **256 MiB**, предел Git bundle — **80 MiB**.
В PR13 эти пределы не повышаются. Подробные SHA/image ID и результаты — в отчёте PR12;
итоговые pins PR13 будут другими и появятся после сборки/принятия изменений.

| Область | Изменения PR13 |
| --- | --- |
| Symphony | Startup/activation, transport, lifecycle wiring, launcher, dashboard status, тесты и инструкции |
| agent-runner | Минимальный companion: совместимость с новым runtime, параметр pilot, profile checks и точные pins |
| app | Продуктовый код и workflow deployment не меняются; для контейнерных проверок используется отдельная копия принятого кода |
| knowledge-base | Не меняется; итоговая синхронизация остаётся PR15 |

Companion нужен явно: текущие template/checks runner требуют `item_ids: []`, а lock
закрепляет прежнюю Symphony и `execution_enabled: false`. Нельзя незаметно обходить
эти проверки в локальном файле. Изменения двух репозиториев будут показаны отдельно.
Push и merge выполняет владелица; tags/releases не создаются этим этапом автоматически.

## 4. Шаг 1 — единый контракт активации и переносимости

Сначала зафиксировать контракт, затем подключать эффекты:

1. Разделить **готовность controller/дашборда** и **допуск задачи**. Неизвестное
   состояние dev, пустой pilot filter или отсутствие Codex login должны быть видимой
   причиной закрытой очереди, а не лишать оператора интерфейса подготовки.
2. Некорректные scope, manifest, credentials paths, версия store или несовместимый
   runtime не допускают исполнительный startup. Конечная диагностика объясняет причину.
3. Добавить версионированный activation/manifest contract: точный Symphony commit,
   digest запускаемого артефакта, revision проектного профиля, digest WORKFLOW,
   принятый image ID, версии runtime/config и привязка к проекту/локальной установке.
4. Старый inspection manifest не становится исполнительным после обновления кода.
   Переход — явная локальная операция; delivery store, budgets и незавершённый цикл
   сохраняются. Несовместимое состояние требует проверенного восстановления.
5. Один и тот же валидатор используется CLI, `start_link`, обычным OTP startup,
   маршрутом Burrito и reload. Нет обхода через альтернативную точку входа,
   простой `execution_enabled: true` или hot reload restart-only параметров.
6. Все параметры компьютера берутся из local config вне git. Ни личные WSL names,
   ни UID, домашние папки, буквы дисков, SSH aliases и внешние порты в код не вшиваются.

Внутренний `/workspace/repo` — контракт контейнера. Это не путь к папке владелицы.
Один активный controller на проект остаётся операционным правилом. Локальный flock
защищает одну установку, но не выдаётся за блокировку между компьютерами.

## 5. Шаг 2 — конечный pilot filter и защита от следующей задачи

Добавить в общий renderer типизированный локальный параметр списка Project item IDs.
Для первого rollout разрешены **пустой список или ровно один item**:

- пустой список: controller может показывать состояние, запуск карточек запрещён;
- один item: дополнительно проверяются repository/project, статус Ready, `Agent allowed`
  и все обычные условия допуска; фильтр не заменяет их;
- observer продолжает видеть весь необходимый scope; фильтр ограничивает выбор работы,
  а не скрывает изменения dev, deployment, PR или решения оператора;
- незавершённый цикл сохраняет владение даже при изменении карточки/фильтра;
- завершение единственного пилота сохраняется в существующем durable delivery state.
  Перезапуск launcher или повторное чтение карточки не разрешает второй обычный цикл.

Recovery допускается только явным операторским решением в рамках удерживаемого цикла.
Он не расходует «вторую нормальную задачу» и не освобождает очередь до проверки dev.
Смену пилота после начала работы нельзя провести простой заменой ID в config.
Остановка после пилота и процедура следующего rollout описываются отдельно, без reset store.

## 6. Шаг 3 — привязанный transport и получение кода

Подключить существующий ограниченный протокол guardian к controller. Не создавать
второй scheduler, собственную трактовку gate или универсальное удалённое исполнение shell.

Последовательность начала/продолжения работы:

1. Delivery gate проверяет свежие данные и резервирует активный бюджет; сохраняется
   намерение операции и binding `cycle / branch / interval / generation` до эффекта.
2. Controller через существующий GitHub credential provider получает код разрешённого
   repository для точного ожидаемого dev SHA. Токен чтения остаётся на controller.
3. Служебный Git создаёт и проверяет bundle с нужной историей без checkout/исполнения
   кода продукта на controller. Git hooks/helpers и случайный global config не используются.
4. Проверяются refs, SHA, целостность и лимит 80 MiB. Если dev изменился относительно
   допуска, работа не начинается по устаревшему разрешению: требуется reconciliation.
5. `prepare` доставляет bundle на worker; `start` запускает принятый image с оставшимся
   бюджетом, а не с новым полным часом. Controller получает проверенный endpoint и cwd.
6. Далее controller посылает heartbeat и проверяет свежую готовность runtime.

Новая задача начинается от текущего допущенного dev. Продолжение сохраняет task base,
существующую ветку, её head и незакоммиченные файлы; свежий dev доставляется отдельным
seed для согласованного merge. Конфликт сохраняется для решения, без reset/clean.
Recovery получает новую назначенную ветку от текущего dev по существующей политике gate.

Каждый ответ проверяется по binding. Потеря ответа после prepare/start/stop/export
требует status/readback и сверки сохранённого намерения; повтор вслепую запрещён.
Метаданные transport хранятся в controller-owned state с существующими требованиями
атомарности. Они описывают ресурс и операцию, не становятся вторым delivery store.

## 7. Шаг 4 — один workspace и запуск агента внутри контейнера

Для Projects lifecycle принимает подтверждённый transport путь `/workspace/repo`.
Обычный `Workspace` не создаёт второй пустой checkout. Hooks, Codex, локальные тесты
и exporter используют один repository и один binding. Поведение других tracker не меняется.

Подключить management SSH и task SSH как разные каналы:

- management принимает только разрешённые действия протокола;
- task SSH ведёт в конкретный контейнер, использует его проверенный host key и
  отдельный ключ доступа; endpoint передаётся структурированно для данной попытки;
- запретить forwarding, отключение проверки host key и глобальную смену SSH alias
  ради очередного контейнера; модель не выбирает host/порт/ключ;
- App server и все hooks получают этот binding до выполнения команд. При отсутствии
  подтверждения контейнера никакого fallback на shell controller или worker host нет.

В контейнере доступны только image, task volume, выделенная Codex auth area и временные
каталоги. Диски Windows, home controller, host `/etc`/`usr`, WSLg/interop и сокеты
Docker/Podman не монтируются. Контейнер видит собственные `/etc`/`usr` из image.
Существующие ограничения сети, namespaces, capabilities и ресурсов сохраняются.

Инструменты PR09 привязываются к реальному handle цикла. Worker не получает GitHub/App
credentials. Publish в task branch выполняет controller; merge, push в dev/main,
произвольные GitHub-запросы и выдача себе допуска через tools не появляются.

## 8. Шаг 5 — запуск host runtime и отдельная авторизация Codex

Закрыть путь от инструкции до реально доступного guardian. Предусмотреть воспроизводимую
установку/запуск ограниченной host-службы с явными параметрами текущей машины и проверкой
принятого runtime/image. Привилегированная установка выполняется оператором отдельно;
обычный launcher не получает универсальный sudo и не перенастраивает другую Ubuntu/Docker.

Preflight проверяет настоящий management endpoint, версии/образ, ресурсы, свежесть
network readiness и соответствие binding. Старый smoke report не заменяет текущую
готовность после reboot, suspend или изменения firewall. Отсутствие readiness закрывает допуск.

Для Codex нужен отдельный login в изолированном профиле. Реализовать ограниченную
bootstrap-процедуру: контейнер без product task и GitHub credentials, интерактивный вход
оператора, сохранение только выделенной auth area с закрытыми правами. Не копировать
в контейнер целиком `.codex`/home из прежней Ubuntu. В логах — только статус входа.

Проверить сохранение обновлённых credentials между сессиями: текущий guardian копирует
`codex-auth.json` при старте, поэтому нельзя перезаписывать свежую auth area устаревшей
копией. При потере входа очередь блокируется с понятным действием «повторить вход».
Секреты и одноразовые коды не включаются в PR/отчёт и не запрашиваются текстом в чате.

## 9. Шаг 6 — остановка, watchdog и восстановление

Вначале закрыть допуск/отозвать разрешение на эффекты, затем останавливать процессы.
Долгие SSH/stop/export операции выполнить через ограниченные асинхронные задачи:
GenServer владельца delivery cycle должен отвечать на status/cancel и во время сетевого timeout.

Подтверждение остановки включает контейнер, SSH/Codex/hooks и дочерние процессы.
Завершение Elixir task, закрытие SSH или остановка launcher отдельно этого не доказывают.
Ответ `stopped` принимается только для ожидаемых cycle/interval/generation.

Сохранить heartbeat примерно каждые 10 секунд и существующий watchdog потери controller
45 секунд. Он отсчитывает отсутствие подтверждения, а не обещает остановку ровно
через 45 секунд от клика. Сетевой supervisor и его deadline остаются отдельной защитой.

При неизвестном результате — `stop_unconfirmed`, очередь закрыта, workspace сохранён,
активное время учтено консервативно. Поздний ответ от старой попытки не останавливает
новую. При перезапуске сначала сверяются store, resource state и действительные процессы;
повторный агент без такой сверки не запускается.

Отмена не откатывает уже отправленный GitHub-запрос. Если она совпала с push/созданием
PR, controller сначала выясняет фактический результат и показывает его оператору;
нельзя объявлять «ничего не опубликовано» только по локальному timeout/отмене.

Экспортировать результат только после подтверждённой остановки. Controller проверяет
bundle/head и передаёт его существующему publisher. Неопределённый результат push/PR
восстанавливается через readback, не через повторную публикацию наугад.

## 10. Шаг 7 — launcher и понятный дашборд

Сохранить интерфейс `configure / render / pin / preflight / launch / status / stop`:

| Действие | Планируемое поведение |
| --- | --- |
| `launch` | Прежняя конечная inspection, без выполнения карточек |
| `launch --execute` | Явный запуск интегрированного controller при корректном activation contract; фактический допуск отдельно решает gate |
| `preflight` | Отдельно показывает готовность controller, worker и причины запрета задачи; ничего сам не устанавливает |
| `status` | Проверяет реальный процесс и readiness, показывает цикл/фазу, а не только существование PID |
| `stop` / Ctrl+C | Закрывает новый допуск, останавливает worker, сохраняет state; сообщает подтверждённый результат или неизвестность |

Передавать Symphony только необходимое окружение: в том числе App ID, Client ID,
Installation ID и ссылку на private key. Не передавать окружение целиком; worker эти
параметры не получает. Проверить Windows wrapper и запуск из произвольного cwd.

В дашборде показать: роль/режим, готовность worker, причину закрытия очереди,
активный цикл и этап, оставшиеся бюджеты, ход остановки и ссылку на PR/Actions.
Существующая статическая надпись о выключенном запуске заменяется реальным состоянием.

Проверить всю существующую операторскую цепочку:

- первоначальное подтверждение текущего dev без искусственной task;
- пауза очереди, отмена задачи, продолжение после review и разрешённый recovery;
- «деплой выполнен» отдельно от «среда готова к ручной проверке»;
- ручное подтверждение Queue и его срок 30 минут, затем проверка dev;
- отказ устаревшей форме при смене SHA/run/attempt/version;
- отрицательный результат сохраняет блокировку и требует решения оператора.

`Actions: read` сохраняется: повтор CI без нового кода запускает оператор через GitHub,
Symphony наблюдает и учитывает новую попытку. Новые права App автоматически не добавляются.
После завершённого единственного пилота launcher безопасно останавливается; результат
остаётся в store/status, чтобы рестарт не разрешил следующий обычный запуск.

## 11. Бюджеты остаются согласованными

| Ограничение | Значение / учёт |
| --- | --- |
| Начальная работа | 60 минут активной работы |
| Автоматическое исправление | Отдельные 60 минут суммарно, не более двух циклов |
| CI за автоматический цикл | Не более 6 попыток, включая первичные и повторы |
| Инфраструктурные повторы одного SHA | Не более 2; неизвестная причина не объявляется сетевой автоматически |
| GitHub verify | 20 минут, app workflow здесь не меняется |
| Локальный verification | До 20 минут, но остаток активного бюджета может остановить раньше |

Prepare, hooks, установка зависимостей и локальные тесты входят в активный бюджет.
Ожидание GitHub Actions и оператора — нет. Reservation сохраняется до эффекта;
рестарт, rework и новая попытка container start не обнуляют время и счётчики.

### Хранение и место на диске — дополнение владелицы

Рабочая папка сохраняется во время CI/review/deployment/rework/recovery. Только
подтверждённое окончательное успешное завершение delivery cycle разрешает запустить
срок хранения тяжёлых данных: по умолчанию 7 суток. Небольшой итоговый отчёт хранится
отдельно от workspace; его наличие и целостность проверяются перед удалением.
Отменённые/аварийные циклы автоматически не удаляются: отдельное операторское решение
должно явно учитывать возможность неопубликованной работы.

Transport bundles, seed/archive и ключи поколений удаляются после прекращения их
необходимости для восстановления, вместе с проверенной очисткой завершённого цикла.
Очистка не определяется только возрастом файла или завершением процесса.
Для image допускаются только явно зарегистрированные ресурсы данной установки,
не текущий принятый image и не используемые контейнерами; общий `podman prune` запрещён.

Добавить bounded logs/rotation и контроль места controller/worker перед допуском
и периодически во время работы. Начальные переносимые пороги: предупреждение ниже
10 GiB, блокировка нового допуска ниже 5 GiB, с явной локальной настройкой.
При работающем агенте низкий остаток показывается оператору и закрывает новые запуски;
ошибка записи состояния требует остановки по действующей политике. Данные активной
или неопределённо остановленной задачи ради освобождения места не удаляются.

Проверки: CI-wait/restart не приводят к очистке; completed + 7 дней допускает только
свои данные после записи отчёта; cancelled/crash удерживаются; symlink/path escape,
чужой image и занятый ресурс отклоняются; low-disk виден и закрывает новый допуск.

## 12. Шаг 8 — программа приёмки

Сначала узкие тесты контрактов и настоящих OTP-процессов, затем общие gates и
packaged acceptance. Проверки не требуют merge/deploy реального продукта.

| Сценарий | Ожидаемый результат |
| --- | --- |
| Inspection / неверный manifest / альтернативный startup | Нет worker и GitHub writes; конечная диагностика или явный отказ |
| A → работа → PR → review → merge → deploy → manual dev | Одна цепочка владения; B не запускается во время ожиданий |
| Empty/foreign/multiple pilot items | Нет незаявленного допуска; наблюдение текущего delivery cycle сохраняется |
| Fresh dev при новой/продолженной работе | Правильный seed; исходная task base, head и dirty worktree не теряются |
| CI failed, manual rerun, rework | Правильные counters/budgets; без слепого rerun и ухода на B |
| Failed deploy или отрицательная dev-проверка | Обычная очередь закрыта, только явно разрешённый recovery |
| Deployment success + inherited Queue pause | Деплой успешен; ручная проверка среды ожидает отдельного действия |
| Stale form / истёкшие 30 минут | Подтверждение отклонено, нужна актуальная проверка |
| Cancel в prepare, dependency install, turn, verify, handoff | Отзыв effects, подтверждённая остановка либо явная неопределённость; результат сохранён |
| Cancel после merge | Уже выполненный merge/deployment не считается отменённым; dev остаётся под контролем gate |
| Crash/timeout между intent и ответом | Status/readback; нет второго контейнера, повторного push или потерянного бюджета |
| Restart на фазах CI/review/deploy/manual/recovery | Владение и ожидания восстанавливаются до допуска новой работы |
| Потеря/повреждение/старый backup store | Закрытый допуск; восстановление не принимается без проверки |
| Controller/guardian loss, suspend, firewall loss | Watchdog и подтверждаемая остановка; старый readiness не принимается |
| Второй local launcher / pilot completed + restart | Нет параллельного или следующего обычного цикла |
| Другая установка/пути/UID | Те же контракты, без личных defaults и секретов в generated artifacts |
| Host paths/sockets/private networks | Ограничения PR11 сохраняются во время настоящих hooks/Codex-процесса |

Уровни доказательств фиксировать раздельно:

1. **Автоматические integration tests:** fake GitHub и управляемый test worker/app-server,
   реальные gate/store/runtime процессы, временные repositories; воспроизводимые сбои.
2. **Packaged startup:** реально собранный исполняемый артефакт, внешний WORKFLOW,
   запуск из другого cwd, корректное завершение dry-run и реальный launcher/control path.
   Тестовые внешние сервисы подключаются только доверенным harness; production manifest
   не получает произвольный GitHub URL или возможность подменять правила gate.
3. **Настоящий runtime:** принятый project image, Podman/SSH, seed/import, hooks,
   протокол Codex startup, stop/export, сеть/файлы/watchdog. При необходимости проверки
   app — только в контейнерной копии. Docker build app по-прежнему `CI_ONLY`.
4. **Live prerequisites:** чтение действительной доски и прав App без мутаций; отдельный
   login выполняет оператор. Проверка реальных writes только на согласованном объекте
   O3c/пилота, без пробного push в dev/main. Отсутствие такого evidence отмечается явно.

Успешный fake-сценарий не считается реальным выполнением модели или продуктовым пилотом.
Для поставляемого Linux entrypoint нужен реальный запуск, а не только parser test.
Для Burrito проверить маршрут activation через Application/CLI; если соответствующий
binary не собран и не принят, его исполнительный режим не объявлять поддержанным.

Финальные checks: `git diff --check`, полный `make -C elixir all`, изменённые Python
runtime tests, profile/renderer tests agent-runner, container/system acceptance и
проверка PR body. Провести отдельный adversarial review lifecycle/restart/cancel и
границ credentials. Открытый воспроизводимый дефект блокирует готовность.

## 13. Шаг 9 — упаковка, pins и передача результата

Проверять весь комплект: executable + runtime helpers + профиль + image. Один только
SHA Symphony не подтверждает, что рядом установлены соответствующие Python scripts.

   companion agent-runner и проверить совместимость; профильные pins проходят review.
3. После принятия профиля собрать/проверить итоговый image и создать локальный manifest
   O7 с действительными SHA/digest. Использование moving `main` вместо pin запрещено.
4. До PR14 завершить setup/readiness/login/начальную dev-проверку, выбрать единственную
   существующую issue и её критерии. Этот выбор не требуется для написания PR13.

Основные точки изменений:

## 14. Как владелица принимает PR13

PR13 готов, когда одновременно выполнено следующее:

1. Все перечисленные startup/transport/cwd/heartbeat gaps закрыты кодом и тестами.
2. Launcher запускает принятый комплект; inspection и чужой профиль не включают worker.

6. Полный тестовый delivery cycle, негативные сценарии и настоящий runtime прошли приёмку.

8. Указаны отдельно кодовая готовность, принятие/публикация версий и live prerequisites.
   Пока последние не завершены, запуск реальной задачи запрещён.
