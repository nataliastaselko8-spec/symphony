# Второй пилот Symphony — отчёт этапа 4

Дата: 2026-09-22. Статус: выполнен в исходниках.
Основание: [этап 4 плана](second_pilot_implementation_plan.md#этап-4-добавить-выбор-следующего-пилота).

## Результат и выбранный подход

`Select-Pilot -Issue NUMBER` поддерживает выбор следующей задачи после доказанного
завершения предыдущей и подтверждённого Stop. Установка, её авторизация и принятые
версии сохраняются. Следующая задача получает отдельный профиль и состояние.
Команда выбора не запускает агента.

Раньше команда разрешала только первый выбор и его повтор, считала любую историю
worker препятствием и имела единственную резервную копию Windows descriptor.
Снятие только `pilot_already_selected` оставило бы возможность потерять связь
со старой работой или не закончить переключение после сбоя между Windows и WSL.

Расширены существующие команды и блокировки. Проверку завершения выполняет Elixir
через настоящий Snapshot replay, а Python готовит отдельные файлы. Windows меняет
активный descriptor последним. Второй scheduler или отдельная база не добавлены.

## Что реализовано

| Часть | Реализация и назначение |
| --- | --- |
| Проверка прошлого цикла | Новый `DeliveryGate.Pilot` проверяет snapshot с прежним scope, точную выбранную карточку, completed, отсутствие holds и незавершённых операций |
| Финальный статус | При наличии status journal требуется подтверждённый production_ready с доказательствами завершённого цикла; pending/conflict/unknown/failed запрещают выбор |
| Старый completed | Корректный журнал без status sync сохраняет отметку `legacy_not_recorded`; старая карточка не изменяется |
| Подтверждение Stop | Сохранённое подтверждение связано с hashes конфигурации и worker metadata; отсутствующий, старый или изменившийся результат требует повторного Stop |
| История worker | Metadata и binding должны совпадать с завершённым циклом, веткой и repo; неизвестный или чужой worker не принимается |
| Новая карточка | Ровно одна открытая карточка указанной issue в принятом Project/repo, Ready for agent, Agent allowed=yes и допустимые остальные ограничения |
| Подготовка профиля | Отдельные config, WORKFLOW, manifest и state root; исходный журнал, budget, workspace и baseline не сбрасываются |
| Модель и авторизация | Выбор модели/effort и актуальный каталог сохраняются; ссылки на существующие credentials, host и pins не меняются |
| История переходов | `pilot_history` и отдельные Windows-записи вместо перезаписи единственного backup; старый `installation.before-pilot.json` сохраняется |
| Прерывание и повтор | Сохранённое намерение позволяет закончить тот же переход; изменённые исходные данные/файлы отклоняются |
| Конкурирующие команды | Выбор и manager используют блокировку установки; descriptor перечитывается после её получения; Start не проходит незавершённое переключение |

Повтор текущего выбора возвращает тот же профиль. Возврат к завершённой issue из
истории не создаёт новый цикл. Путь отменённого, повреждённого или незавершённого
пилота остаётся отдельным восстановлением; новая задача не обходит это состояние.

## Порядок переключения и сохранённые файлы

1. Проверить Stop и исходный журнал, затем прочитать карточку-кандидата.
2. Сохранить Linux-намерение `pilot-selection.json` с идентификатором перехода,
   исходными доказательствами и hashes модели.
3. Подготовить и проверить отдельный профиль, workflow, manifest и состояние.
4. В Windows сохранить `pilot-selection.pending.json` и неизменяемую запись
   `pilot-history/<transition-id>.json` с предыдущим и следующим descriptor.
5. Атомарно заменить `installation.json`, затем убрать завершённую pending-запись.

При сбое повторяется тот же `Select-Pilot`. До смены descriptor повтор сверяет
Linux-файлы и исходные доказательства. После смены descriptor он заканчивает
сохранённый переход, не создавая другую историю. Если потерян ответ ещё до Windows
pending, Linux-намерение запрещает запуск старого профиля и выбор другой задачи.

В новом state root нет прежних `delivery.json` и `worker.json`. Переносится только
проверенная binding-запись остановленного worker: это позволяет распознать оставшийся
контейнер, сохранив отсутствие активной задачи в новом профиле. Каталоги последующих
пилотов создаются рядом, без увеличения вложенности и длины имён при каждом выборе.

Elixir запускался в обычной Ubuntu WSL с Elixir 1.19.5 / OTP 28.5, Windows-тесты —
в Windows PowerShell 5.1. Шесть ExUnit-пропусков относятся к live E2E.
`test_pilot_replay.py` выполнялся с `SYMPHONY_PILOT_REPLAY=1`: реальные Python → mix →
Elixir → Store подтвердили legacy completed, отказ при pending final status,
допуск при confirmed final status и отказ повреждённому журналу. Байты исходного
журнала после чтения остаются прежними.

В тестах подготовки профиля используются настоящие приватные файлы, manifest,
flock и controller-проверки принадлежности worker; внешние GitHub/SSH/WSL-сервисы
заменены контролируемыми ответами. PowerShell-проверка конкуренции использует
отдельный процесс и настоящую Windows-блокировку установки.

При проверке пограничных сценариев отдельно учтены потеря ответа Linux до Windows
pending, устаревший descriptor перед получением блокировки и потеря принадлежности
остановленного контейнера при создании чистого state root.

`mix deps.get` продолжает сообщать security advisories существующих зависимостей;
этап 4 не обновлял их. Успешный quality gate не означает устранения этих предупреждений.

GitHub-карточки и issue #132 не изменялись. Commit и push не выполнялись.

обновления нужен новый подтверждённый Stop; прежний boolean-only результат Stop
не считается доказательством для нового механизма выбора.

и пройти живой цикл; новое подтверждение исходного dev остаётся обязательным.
