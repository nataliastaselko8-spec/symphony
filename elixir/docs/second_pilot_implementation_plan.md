## Цель и выбор подхода

Повторно запустить установленную Symphony на одной новой задаче EmotionStat/app и пройти путь от допуска карточки до `Ready for production`. Доска должна отражать подтверждённые события, включая ошибки и продолжение работы. Review, merge в dev и ручная проверка приложения остаются действиями человека.

Уточнение владелицы: сначала внести фиксы, затем опробовать их на **новой пилотной задаче**. Issue #132 не перезапускается, её карточка не используется для испытаний и не требует обязательного исправления в рамках этого плана. Номер новой задачи будет выбран перед живым пилотом.

Выбран вариант: расширить существующие controller, delivery store, сохранённые операции и Windows launcher. Controller уже знает состояние цикла, PR, CI и deployment, поэтому он должен отвечать и за отражение этого состояния в Projects. Отдельный сервис синхронизации, новая база данных и дополнительный агент создадут второго владельца состояния без необходимости.

Один пилот остаётся одной явно выбранной задачей. Выбор следующего пилота создаёт отдельный профиль и состояние после подтверждённого завершения предыдущего. История старого пилота сохраняется; обновление программы не обнуляет задачи, бюджеты и авторизацию.

План детализирует открытые работы ENG-027, ENG-028, соответствующую часть ENG-026/ENG-008 и следующий ограниченный rollout OPS-002. Action Register базы знаний остаётся каноническим реестром открытой работы; этот файл — технический порядок реализации и приёмки. Он не закрывает перечисленные пункты сам по себе.

## Общие условия реализации

- Один controller владеет циклом и записями в GitHub; GitHub credentials не передаются worker.
- Событие и намерение обновить доску сохраняются согласованно в существующем store. После сбоя намерение можно восстановить без догадок по тексту агента.
- Подтверждение записи требует чтения результата. Неизвестный ответ не означает ни успеха, ни разрешения повторить push/создание PR.
- Синхронизация статуса не запускает worker и не выдаёт новый допуск.
- Завершение продуктовой работы и подтверждение финального статуса доски различаются. Незавершённая синхронизация переживает complete, Stop и restart и блокирует выбор следующего пилота.
- Это правило применяется к операциям новой реализации. Для исторического completed без механизма полной синхронизации миграция сохраняет факт «финальный статус не синхронизирован старой версией», не создаёт задним числом новую задачу или обязательную запись в старую карточку. Уже существующие неопределённые публикации нельзя объявлять историческим исключением.
- Сохраняются существующие проверки scope, владельца, budgets, pause, worker stop, SHA и deployment evidence.
- Изменение схемы store и fingerprint требует явной совместимости или проверяемой миграции; нельзя переписывать pins и удалять store ради запуска.

**Для чего:** не строить обновление на предположении, что установленная версия совпадает с checkout, и определить границы работы до изменения stateful-кода.

**Работы:**

1. Прочитать metadata действующей установки, revisions/image ID, выбранную модель, описание scope и состояние manager/controller/worker. Секреты в отчёт не включать.
2. Проверить, что прежний цикл завершён, worker остановлен и не осталось неопределённой публикации или recovery. При расхождении сверить относящиеся к нему факты GitHub. Не перезапускать #132 и не менять её карточку. Текущий dev проверить отдельно: историческая validation не доказывает здоровье более нового dev.
3. Проверить схему Project, наличие всех нужных статусов и права GitHub App. Не создавать новые колонки без необходимости.
4. Зафиксировать таблицу ниже, правила ручного конфликта и совместимость новой схемы состояния со старой.
5. До изменения работающей установки подтвердить Stop и подготовить восстанавливаемую резервную копию состояния. Только чтение и проектирование не требуют остановки.
6. Провести разбор отказов: complete до записи GitHub, закрытие issue после merge, падение до project_start, повтор выбора пилота и сбой обновления между Windows и WSL.

**Выход:** отчёт исходного состояния без секретов, таблица переходов, план миграции. Неопределённый старый цикл сначала требует восстановления; новая задача его не вытесняет.

## Этап 2. Добавить сохранённую синхронизацию статусов — выполнен

Реализованы журнал намерений, атомарная команда события, отдельная синхронизация controller, readback, ограниченные повторы и отображение результата. Старый журнал воспроизводится без изменения; расширение mapping требует явного обновления scope. Все события существующего runtime будут подключены на этапе 3. Подробности и проверки — [отчёт этапа 2](second_pilot_stage2_report.md), контракт — [status sync](github_projects_status_sync.md).

**Для чего:** доска отражает решения controller, даже если агент завершился или GitHub временно недоступен.

**Где:** `delivery_gate/{state,command,effects,snapshot,settings}.ex`, `delivery_runtime.ex`, `github_projects/{settings,write_client,publication}.ex` и соответствующие тесты.

**Как:**

1. Расширить конфигурацию ролей статусов: добавить review, dev validation и readiness к production; реальные IDs получать из схемы Project. Обновить строгую валидацию и версию контракта при необходимости.
2. На основе текущих durable effects добавить операцию синхронизации, создаваемую доверенным controller из lifecycle-события. Не открывать агенту произвольную запись статуса.
3. Сохранять идентичность операции, cycle/item/repo, версию события, ожидаемый исходный и целевой статусы, причину, применимые PR/SHA/run/attempt и результат сверки. Не требовать PR/run от события начала работы.
4. Обеспечить обработку операций вне working, в том числе после переноса в last_cycle. Не снимать существующие ограничения публикации ради записи статуса.
5. Статус блокировки и комментарий об ошибке обрабатывать независимо: отказ комментария не должен удерживать карточку в Agent working.
6. До записи сверять актуальные факты и статус. Если цель уже достигнута — подтвердить без повторной mutation; при неизвестном результате сначала читать; при конфликте показать его оператору.
7. Использовать существующий цикл сверки, ограниченные повторы и backoff с учётом rate limit. В панели отображать target/observed/pending/error и время последней успешной сверки.
8. Не проигрывать устаревшие переходы поверх новых фактов. Явная доработка может вернуть карточку назад; порядок колонок не является версией состояния.

**Проверка:** реальные Gate/OTP-процессы и временный store; управляемый GitHub API. Сбой до отправки, после mutation до ответа, после ответа до сохранения; restart после complete; повтор события; временный отказ, rate limit, отзыв прав; ручной конфликт. Отдельно проверить, что синхронизация не запускает агент и не создаёт повторный PR.

**Готово, когда:** намерение и подтверждение сохраняются, финальная запись не теряется, а конфликт и неопределённость видны оператору. Цель задержки — до 60 секунд при доступном GitHub и свежих подтверждённых фактах; это измеряемый критерий приёмки, а не гарантия во время сбоя API. Общую транзакцию с GitHub и отсутствие гонки ручного изменения обещать нельзя.

## Этап 3. Подключить все события и действия оператора

**Статус:** выполнен в исходниках для профиля с семью ролями; [реализация, проверки и ограничения](second_pilot_stage3_report.md). Миграция установленного профиля остаётся этапам 5–6.

**Для чего:** синхронизация охватывает весь путь, а не только успешную публикацию.

| Событие | Статус | Условие |
| --- | --- | --- |
| Начало или разрешённое возобновление работы | Agent working | Подтверждён допуск и начало работы; повтор project_start не дублирует переход |
| Публикация / ожидание CI | Agent working | PR/run показаны в отчёте; PR ready ещё не выставляется |
| Готовность PR | PR ready | Worker остановлен, native linkage подтверждена, полный актуальный CI успешен |
| Оператор начал review | Human review | Явное сохранённое действие; открытие страницы не считается review |
| Возврат на доработку до merge | Agent working | Та же ветка/PR, проверены база, разрешение и бюджет |
| Назначенный PR merged в dev | Dev validation | Merge подтверждён; в отчёте отдельно указано ожидание deployment |
| Deployment успешен и ручная validation положительна | Ready for production | Совпадают SHA/run/attempt; выполнены нужные проверки приложения/Queue/Scheduler |
| Требуется решение человека | Needs human decision | Причина и следующее действие известны; работа и владение сохранены |
| Оператор разрешил продолжение | Статус подтверждённого этапа | Ошибка устранена, разрешение и остальные условия перепроверены |

**Где:** `delivery_runtime.ex`, `delivery_gate/*`, `operator/{policy,decision,control,view}.ex`, страницы и контроллеры operator UI, observer/ownership и профиль agent-runner.

**Работы:**

- Подключить аварии worker, потерю auth, невозможность commit, исчерпание бюджета, окончательный отказ публикации, провал deployment и ручной validation к сохранённой блокировке.
- Отличать обычное ожидание CI/deployment от ошибки; сохранить допустимые автоматические исправления CI в текущем бюджете.
- Добавить явное действие «Начать review» и согласовать существующий возврат на доработку с доской.
- Поддержать продолжение из Needs human decision без ручного возврата в Ready. Само исчезновение ошибки не отменяет pause и не означает решения оператора.
- Разделить проверку допуска новой работы и запись подтверждённого post-merge результата. Закрытую issue не открывать автоматически; закрытие не считать доказательством completed. Для post-merge записи требовать сохранённую связь с назначенным PR и соответствующие доказательства; удалённая/архивная карточка требует явной обработки конфликта.
- Не превращать любое чтение чужого открытого PR или старой карточки в присвоение новой задаче.
- Проверить observer/ownership при исторических данных на fixtures. Для текущей #132 специальное исключение не требуется: live статус Ready for production не входит в блокирующие статусы. Не вводить общий обход блокировок для старых карточек и не изменять #132 ради тестирования.

**Проверка:** каждая строка таблицы; падение до project_start/project_block; отказ комментария; красный/устаревший CI; новый head/base; повтор deployment attempt; отрицательная validation; revoke Agent allowed; stale форма; закрытие issue вручную и после merge.

**Готово, когда:** обычные действия человека выполняются через предусмотренные команды/UI, а перемещать карточку для компенсации внутреннего решения Symphony не требуется. Production и Done не включаются.

**Готово, когда:** в тестовой установке можно последовательно выбрать два пилота, сохранив доказательства первого; допуск всегда ограничен одной карточкой.

## Этап 5. Согласовать профиль и проверки

**Для чего:** runtime, инструкции агенту и CI используют один принятый контракт.

**Где:** agent-runner `worker/profile-lock.json`, `.github/workflows/profile-ci.yml`, `WORKFLOW.template.md`, `scripts/profile_check.py`, `scripts/checks/verify.py`, README/AGENTS и тесты. Не терять существующие незакоммиченные правки.

**Работы:**

1. Оставить profile-lock единственным источником принятого Symphony SHA; CI получает ref из него. Проверять формат и фактический checkout SHA.
2. До окончательного pin запускать отдельную явно обозначенную проверку совместимости с development checkout. Она не выдаёт этот checkout за принятую поставку и не отключает release-проверку точной ревизии.
3. После завершения изменений Symphony, включая механизм обновления/миграции этапа 6.1, закрепить итоговый commit, проверить профиль, затем закрепить profile revision и собрать образ. Не менять lock на каждый промежуточный commit. Это отложенная релизная часть этапа 5: положительная development-проверка её не закрывает.
4. Согласовать результаты локальных проверок: passed, failed, skipped/unavailable с причиной. Ошибка реально выполненного теста не становится skip.
5. Сделать однозначным назначение полного локального verify/handoff-check: дополнительная диагностика; доступные целевые проверки и честный отчёт обязательны, полная проверка CI определяет PR ready.
6. Обновить роль статусов, фактический процесс запуска и устаревшие упоминания PR13 guard. Сеть команд агента остаётся выключенной.

**Проверка:** profile unit tests, renderer/Elixir contract, pin validation; сценарии отсутствующих offline-зависимостей и реального провала теста; проверки приложения только в task image; полный hosted CI нового PR.

**Готово, когда:** инструкции, проверки и публикация согласованы; точный принятый SHA проверяется из одного источника, а skip явно отражён в отчёте и PR.

**Результат реализации 2026-09-22:** профиль переведён на семь ролей; CI читает SHA из lock и проверяет checkout; строгий pin и отдельный development-режим проверены. 42 профильных теста и реальный renderer/Elixir contract успешны. В отдельном task image успешно проверены hooks, offline-отчёт, handoff-check и остановка с сохранением работы. Итог приложения — `incomplete_local`: 2 шага passed (включая 40 CI-helper tests), 22 отсутствующие зависимости и Docker CI явно отмечены как skipped. Итоговый release pin, чистая profile revision, release image и hosted CI остаются до сборки комплекта этапа 6; подробности — [отчёт](second_pilot_stage5_report.md).

**Уточнение после этапа 6:** release pin, чистая profile revision, image и bundle закреплены и прошли локальную приёмку. По решению владелицы agent-runner пока остаётся локальным; hosted profile CI отложен до его публикации. Для текущего локального комплекта остаётся hosted CI Symphony после самостоятельной публикации владелицей. Это не отменяет полный CI продуктового PR на этапе 7.

## Этап 6. Собрать, обновить и проверить комплект

**Решение владелицы от 2026-09-22:** автоматический контроль свободного места на физических Windows-томах включён в обязательный объём этапа 6. Реализовать и проверить его до итоговых pins, release image и bundle. Вариант допуска второго пилота только с ручной проверкой места исключён. Статус этой доработки — реализована и прошла локальную приёмку на итоговом bundle; результаты в отчёте этапа 6.

### 6.1. Подготовить обновление и комплект

**Для чего:** следующий пилот проверяет установленные воспроизводимые версии, без ручной замены служебных файлов.

**Где:** `tools/wsl` setup/bundle/provision/operator/launcher/manager, runtime config/manifest/storage/controller и управляющий канал, операторская панель, документированная процедура обновления и тесты.

**Работы:**

1. Проверить существующий путь обновления; если его нет, реализовать отдельную явную операцию обновления из проверенного bundle. Повтор завершённого Setup сейчас не является обновлением.
2. Подготовить новую версию отдельно; проверить hashes, source revisions, image ID/labels и совместимость до переключения установки. Менять действующую версию только после подтверждённого Stop.
3. Для изменения store выполнить версионированную миграцию с резервной копией и журналом результата. Сохранить scope/identity/бюджеты и связь со старым циклом; не назначать произвольный новый fingerprint старому состоянию.
4. Для исторического completed без новой записи status sync сохранить результат как legacy completed с известным ограничением синхронизации. Не создавать mutation задним числом и не запускать старую задачу. Если завершение не подтверждается либо остаётся неопределённая публикация, остановить переход с конкретной причиной; новую задачу не использовать для обхода незавершённой работы.
5. Сохранить App/Codex auth, модель, settings, store, workspace и результаты. Не копировать секреты в комплект или отчёт.
6. Проверить rollback до начала новой работы. После записи состояния новым runtime откат должен учитывать совместимость схемы и внешние действия; слепое восстановление старого snapshot запрещено.
7. Реализовать автоматический контроль физического диска Windows по подразделу ниже; включить его контракт, совместимость и проверки в механизм обновления.
8. После реализации обновления и контроля диска завершить релизную часть этапа 5: закрепить Symphony → проверить и закрепить профиль → собрать и принять image. Собрать комплект из чистых закреплённых ревизий, образа и артефактов, записать manifest/hashes. Старые 6 исправлений пилота и новая защита по месту должны входить в установленную ревизию.

**Проверка:** чистая установка и обновление тестовой копии прежней установки; прерывание на границах переключения; повтор обновления; несовместимые pins/schema; сохранение auth/model/state; реальный startup Codex, Git add/commit, stop/export и grants публикации.

**Готово, когда:** чистая установка и обновлённая установка получают одинаковую целевую реализацию с автоматическим контролем Windows-диска без ручных подмен; старые доказательства доступны и незавершённые операции не потеряны.

#### Обязательная часть 6.1: автоматический контроль диска Windows

**Для чего:** свободное место внутри WSL может превышать остаток на Windows-томе, где хранится её VHDX. Допуск и работа должны учитывать оба ограничения. Детальный контракт — [раздел 9 плана установщика](../../tools/wsl/installer-plan.md#9-контроль-свободного-места-на-физическом-диске-windows).

1. Windows manager определяет фактические тома хранения VHDX controller и worker по проверенной конфигурации установки, без фиксированных букв диска и путей. Измеряет доступный пользователю остаток; для двух сред на одном томе это один общий запас.
2. Передаёт измерения через существующий доверенный управляющий канал с версионированным форматом, идентификатором тома, привязкой к установке/запуску и ограниченным сроком свежести. Worker не получает Windows mounts, системные API или дополнительный доступ к хосту.
3. Controller учитывает минимум свободного места внутри соответствующей WSL и на её Windows-томе. Общий запас одного тома не складывается для двух сред; уже занятые VHDX байты повторно не вычитаются. Проверки выполняются при Start, перед допуском задачи, периодически во время работы и после sleep/resume.
4. Сохраняет настраиваемые пороги: по умолчанию ниже 10 GiB — предупреждение, ниже 5 GiB — запрет новой задачи и штатная остановка активного worker с сохранением workspace, коммитов, цикла и бюджета. Не объявляет задачу завершённой и не очищает её автоматически.
5. При ошибке измерения, неверной привязке или устаревших данных показывает «состояние диска неизвестно» и закрывает допуск. Активный worker останавливается с сохранением работы при утрате действительного подтверждения в пределах установленного срока свежести; восстановление места не снимает другие паузы и delivery gates.
6. Панель отдельно показывает реальный остаток Windows и виртуальное пространство WSL, время измерения и причину warning/blocked/unknown. Для общего тома не отображает один запас как два независимых; размеры VHDX не называются квотой или резервом.
7. Проверяет обновление старой установки и поведение при отсутствии нового формата измерений. Новый runtime не должен считать такую установку готовой по диску до получения свежего действительного подтверждения. Изоляция, авторизация, модель и сохранённая работа остаются частью приёмки обновления.

**Проверка:** контролируемые измерения без заполнения реального диска пользователя; большой свободный объём WSL при малом остатке Windows и обратный случай; общий/разные тома; нестандартный путь установки; границы 10/5 GiB; уменьшение места во время задачи; ошибка, неверная привязка и устаревание измерений; restart и sleep/resume; сохранение незавершённой работы и отсутствие обхода других пауз. На реальной установке сверить показания с Windows и проверить Start/Stop и неизменность изоляции.

**Готово, когда:** установленный комплект автоматически учитывает физический диск при допуске и работе, показывает достоверные значения/причины и сохраняет работу при остановке. Ручное измерение используется для сверки реализации, а не заменяет её приёмку. Периодическая проверка не резервирует место от других программ.

### 6.2. Интеграционная приёмка до новой продуктовой задачи

**Для чего:** воспроизвести ошибки до живого пилота и убедиться, что проверенный код совпадает с установленным комплектом.

1. Во время реализации — целевые тесты изменённых модулей. Перед итоговой поставкой — `make -C elixir all`, runtime Python tests, Windows installer/manager/pilot tests, profile tests и profile_check для принятого SHA.
2. Проверить связный путь на управляемых GitHub-ответах: A завершена → final sync подтверждён → Stop → выбор B → baseline → работа → PR/CI → review → merge → deployment → validation → final sync.
   Отдельный сценарий совместимости: историческая A completed без полной синхронизации → миграция с сохранением evidence → выбор B, без запуска A и без записи в её карточку.
3. Отдельно проверить реальные границы среды: SSH/Podman isolation, отсутствие credentials controller у worker, login/model, filesystem, stop/export; потерю manager, закрытие терминала и sleep/resume без неразрешённого продолжения.
4. Проверить schema/grants и чтение GitHub на целевом Project. Изменяющие сценарии выполнять на явно выделенных тестовых карточках; не использовать соседние продуктовые задачи как fixtures.
5. Принять обязательный автоматический контроль Windows-диска из этапа 6.1: подтвердить измерения manager → controller → dashboard, пороги, свежесть, остановку с сохранением работы и поведение после обновления/restart/sleep. Приложить результаты тестов и сверку с Windows. Без этой реализации и приёмки комплект не допускается ко второму пилоту; разовая ручная проверка не заменяет защиту. Это закрывает только соответствующую часть ENG-026 после подтверждения, а не весь пункт о распространении installer.
6. Провести заключительный разбор смежных lifecycle-путей; воспроизводимые потери состояния, дубликаты публикации и ложная готовность блокируют пилот.

**Готово, когда:** приложены результаты и конкретные непроверенные сценарии; нет незакрытых дефектов основного пути и восстановления; автоматический контроль Windows-диска прошёл обязательную приёмку. Исторические зелёные прогоны не заменяют проверку новой поставки.
