# Второй пилот Symphony — отчёт этапа 3

Дата: 2026-09-22. Статус: этап выполнен в исходниках. Основание: [этап 3 плана](second_pilot_implementation_plan.md#этап-3-подключить-все-события-и-действия-оператора).

## Главный результат и обоснование

События controller и решения оператора подключены к сохранённой синхронизации GitHub Projects.
Теперь полный профиль может отражать весь путь задачи, включая сбои, review, доработку,
merge и ручную проверку dev. Раньше рабочие статусы в основном зависели от команд агента
и успешного выполнения шагов publisher: авария агента или ошибка комментария могли
оставить карточку на прежнем этапе.

Владельцем переходов остаётся controller: он уже проверяет бюджет, остановку worker,
назначенный PR, CI и deployment. Событие и намерение обновить доску сохраняются одной
записью существующего Gate. Для этого не нужны отдельный сервис, база или новый агент.
Отдельная сверка с GitHub подтверждает результат чтением и сохраняет неопределённость
при потере ответа. Общей транзакции между GitHub и локальным журналом нет.

Функциональность реализована в исходниках для профиля с **семью ролями статусов**.
Старый профиль с четырьмя ролями сохраняет прежнее поведение. Действующая установка
не обновлялась, новая задача не запускалась, issue #132 не изменялась.

## Что подключено

| Событие | Результат и условия |
| --- | --- |
| Начало работы | Допуск, интервал бюджета и намерение Agent working сохраняются согласованно; project_start не дублирует запись |
| Подготовка PR и ожидание CI | Agent working сохраняется; статус готовности требует актуального полного успешного CI |
| Передача PR | PR ready после остановки worker, проверки назначенного PR и native linkage с issue |
| Начало review | Отдельное действие «Начать review»; проверяются открытый PR, head/base и CI; открытие страницы ничего не меняет |
| Доработка после review | Возврат в Agent working; сохраняются ветка, PR и расход бюджета, новый бюджет задаётся явно |
| Подтверждённый merge | Dev validation; ожидание deployment отличается от готовности к ручной проверке |
| Успешная ручная проверка | Ready for production только для совпадающих SHA, deployment run/attempt и подтверждённых критериев |
| Ошибка или решение остановить работу | Needs human decision с сохранённой причиной и прежним владельцем задачи |
| Явное продолжение | До merge — работа той же задачи; после merge — проверка dev, без запуска worker |

Production deployment и Done в этот этап не входят.

## Как реализовано

- Новый `delivery_gate/lifecycle.ex` оборачивает события runtime, observer и оператора.
  Целевой статус выводится из сохранённого состояния. Произвольный target не принимается.
  Старые команды журнала проигрываются по прежним правилам; историческим completed
  не создаётся задним числом запись в GitHub.
- Runtime регистрирует начало работы до исполнения agent tools. Пока статус сверяется,
  инструменты публикации получают `status_sync_pending`; повторять нужно тот же запрос.
  После смены рабочего статуса controller проверяет остальные условия допуска и обновляет
  контрольные данные worker. Несовпадение вызывает остановку и сохранённую блокировку.
- В новых операциях publisher признак `status_owner: controller` исключает прежний шаг
  записи статуса. `project_block` сохраняет блокировку независимо от комментария.
  Аварийный выход, потеря допуска/свежести наблюдения, исчерпание бюджета, обычный выход
  без handoff и окончательный отказ публикации проходят через тот же механизм.
- Ошибка deployment и отрицательная ручная validation требуют решения человека.
  Более поздний успешный deployment обновляет доказательства, но сам не снимает блокировку.
  Обычное ожидание CI, ограничение частоты запросов и разрешённые исправления CI сохраняют
  существующие правила бюджета и повторов.
- Панель получила действия «Начать review», «Проверка dev не пройдена» и
  «Повторно сверить статус доски». Проверяются сессия, actor, версия журнала и свежие
  факты Project/PR/CI/deployment; повтор той же принятой формы идемпотентен.
- Повторная сверка открывает ограниченную серию проверок. После доказанного отказа
  записи, например HTTP 403, можно повторить mutation после восстановления прав.
  Неизвестный результат уже отправленной mutation сохраняет запрет повторной отправки.
  Это действие не подтверждает публикацию и не пересоздаёт PR.
- Observer допускает post-merge результат для закрытой issue только при сохранённом
  назначенном PR, доказанном merge SHA и его включении в dev. Ручное закрытие issue,
  чужой PR и историческая завершённая карточка не присваивают новую задачу controller.
- В `D:/agent-runner/WORKFLOW.template.md` уточнены controller-managed `project_start`
  и ожидание `status_sync_pending`. Пины и конфигурация установленного профиля пока прежние.

## Проверки

Тесты выполнялись в обычной Ubuntu WSL с Elixir 1.19.5 / OTP 28.5, реальными
Gate/Runtime/Auth-процессами, временными приватными store и управляемыми ответами API.
Они не запускали Codex и не меняли реальные карточки GitHub.

| Проверка | Результат |
| --- | --- |
| Полный `make -C elixir all` | Успешен: format, specs, Credo, 615 ExUnit-тестов (0 ошибок, 6 пропусков), покрытие 100%, Dialyzer без ошибок |
| Python в составе `make all` | Delivery store: 8; git publisher: 9; runtime: 74; все успешны |
| Целевые lifecycle/status-sync тесты после исправления паузы | 31 тест, 0 ошибок |
| Итоговый lifecycle runtime-набор, включая обработанный отказ комментария | 10 тестов, 0 ошибок |
| Unit tests agent-runner | 31 тест, 0 ошибок, 2 пропуска |
| `profile_check.py --symphony /mnt/d/symphony` | Не прошёл: `symphony_revision_not_pinned`; текущий checkout не совпадает с прежним profile-lock |
| `git diff --check` Symphony и agent-runner | Успешен |

Шесть ExUnit-пропусков относятся к отключённым live E2E; новый lifecycle-набор выполнялся полностью.
Два пропуска agent-runner относятся к publisher/renderer integration без `SYMPHONY_SOURCE`.
Отдельная проверка точного pin действительно завершилась ошибкой; она не заменена skip
и не отключена. Согласование принятого SHA и полный контракт профиля относятся к этапу 5.

При получении зависимостей `mix deps.get` сообщил security advisories для текущих версий
зависимостей. Это не остановило установленный quality gate; успешный `make all` не означает
устранения этих предупреждений. Версии зависимостей в этапе 3 не менялись.

Новые сценарии проверяют аварийный выход без project_block, выход без handoff,
отказ комментария, путь публикации и review, сохранение ветки/PR при доработке,
закрытую issue после merge, отрицательную validation, новый deployment attempt,
явное продолжение и итоговый статус после complete. Существующие проверки покрывают
красный/устаревший CI, смену head/base, отзыв допуска, stale формы и replay.

При проверке пограничных сценариев найдены и исправлены две ошибки:

1. После записи Agent working и сбоя контрольного чтения использовался прежний исходный
   статус карточки. Теперь блокировка опирается на сохранённый подтверждённый статус.
2. Операторская пауза останавливала обработку старого намерения Agent working и мешала
   следующему Needs human decision. Теперь разрешены отмена устаревшего неотправленного
   намерения и чтение результата отправленного. Тесты проверяют оба случая после restart,
   включая отзыв Agent allowed; новая рабочая mutation и автопродолжение запрещены.

Отдельно проверен медленный ответ при старте: контрольный tick не меняет версию журнала
посреди сверки, публикация ожидает подтверждения статуса, после ответа worker продолжает
работу с обновлёнными контрольными данными.

## Что остаётся по плану

1. **Этап 4:** безопасный выбор другой пилотной задачи с отдельным состоянием и историей.
2. **Этап 5:** согласовать семь ролей, профиль, offline-проверки, CI и точные принятые версии.
3. **Этап 6:** собрать комплект, выполнить проверяемое обновление с миграцией scope/store,
   проверить изоляцию, реальные Codex/commit/stop/export и сценарии восстановления.
4. **Этап 7:** пройти путь на новой выбранной задаче через реальную доску и измерить задержку
   синхронизации. Review, merge и ручное подтверждение приложения остаются за оператором.

Изменение карты статусов меняет scope fingerprint. Нельзя включить семь ролей в старой
установке простой правкой YAML и подменой fingerprint в store: миграция предусмотрена
этапом 6. Неизвестные исходы публикации и ручные конфликты доски по-прежнему требуют
сверки доказательств; универсального принудительного сброса не добавлено.
