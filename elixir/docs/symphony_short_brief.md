# Symphony для EmotionStat: краткий доклад

Состояние по документам и проверенной ревизии форка `6508642` на 21 сентября 2026 года.

**Основной механизм реализован, первый пилот прошёл до проверенного результата в dev. Сейчас требуется довести систему до воспроизводимой установки и устойчивой регулярной работы.**

## Зачем дорабатывали Symphony

Исходная Symphony OpenAI предоставляет основу: получает задачи, создаёт рабочие каталоги, запускает Codex и управляет повторными попытками. Для EmotionStat понадобился более полный процесс: брать только разрешённую карточку GitHub Projects, сохранять состояние после сбоев, ограничивать доступ агента и удерживать задачу до проверки результата в dev.

Форк позволяет сохранить готовую основу и добавить эти правила непосредственно в управление исполнением. Инструкции агенту сами по себе не обеспечивают сохранение состояния, разграничение прав и проверку завершения.

## Как настроена система

На Windows используются две выделенные среды WSL. В первой работает **controller**: Symphony, состояние задач, GitHub App и панель оператора. Во второй запускается **worker** — контейнер Podman, внутри которого Codex изменяет код и выполняет проверки.

Отдельный репозиторий **agent-runner** содержит настройки EmotionStat: шаблон workflow, подготовительные скрипты, команды проверок и рецепт сборки образа — Containerfile. Код приложения хранится в app, архитектура и правила — в базе знаний.

Установщик подготавливает окружение. Есть команды Setup, Start, Stop, Status и Doctor. Задача запускается после явного выбора пилота и разрешения исполнения. Codex проходит отдельный вход; авторизация сохраняется на worker и подключается к контейнеру. GitHub credentials остаются у controller.

## Что доработано и для чего

| Доработка | Практическое назначение |
| --- | --- |
| Интеграция GitHub Projects | Выполнять только явно разрешённую задачу с нужной доски |
| Постоянное состояние и бюджеты | Сохранять незавершённую работу, учитывать время и ограничивать повторы |
| Разделение controller и worker | Изолировать выполнение кода от управляющих доступов и файлов Windows |
| Публикация через controller | Проверять результат и создавать PR без передачи GitHub-токена агенту |
| Проверка CI, deployment и ручная validation | Отличать завершение агента от работоспособного результата в dev |
| Панель, установщик и закреплённые версии | Упростить управление и воспроизводить проверенную конфигурацию |

## Что уже сделано

Реализованы основные компоненты форка, проектный профиль, контейнерная среда и Windows-установщик. В материалах разработки сохранены результаты модульных, интеграционных и контейнерных проверок.

Первый реальный пилот — issue №132 и PR №133 — прошёл через CI, ручное слияние, deployment и проверку dev. **Потребовались технические вмешательства**, поэтому это ещё не подтверждение полностью штатного прохождения. Выявленные исправления внесены в код; итоговый комплект с ними требует отдельной приёмки.

Документация перенесена в базу знаний: созданы шесть заметок, схемы архитектуры, описание этапов и результатов пилота. Связанные документы согласованы, оставшиеся работы внесены в Action Register.

## Что предстоит выполнить

1. **Согласовать профиль и версии.** Устранить расхождение Symphony SHA между profile-lock и CI, обновить устаревшие инструкции и согласовать проверки при недоступных зависимостях.
2. **Завершить синхронизацию доски.** Карточка должна отражать фактический этап после merge, проверки dev и ошибок, включая продолжение прерванной задачи.
3. **Принять итоговый установочный комплект.** Проверить чистую установку, обновление, сохранение авторизации и состояния, сон Windows, потерю manager и восстановление. Добавить контроль физического свободного места Windows.
4. **Подтвердить готовность процесса.** Проверить обязательные CI/review-правила на GitHub, завершить процедуры восстановления и хранения журналов; затем решить вопрос о следующем ограниченном запуске.
5. **Отдельно развивать дополнительные возможности.** Доставка базы знаний и навыков в worker, поддержка macOS/Linux-серверов и облачное размещение пока остаются предложениями.

Ближайший приоритет — согласованный комплект, корректные статусы и проверка работы после сбоев. Успешный dev-пилот не означает готовность production или разрешение автоматической очереди задач.
