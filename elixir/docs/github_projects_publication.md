# PR-09: публикация результата задачи

Controller получает запрос от текущего worker, сохраняет намерение в delivery store,
подтверждает остановку worker и только затем публикует результат. Завершение инструмента
`project_handoff` означает принятие запроса, а не готовность PR к review.

## Доступные инструменты

| Инструмент | Что разрешено |
| --- | --- |
| `project_context` | Читать свою задачу, ветку, PR и бюджеты |
| `project_start` | Запросить `Agent working` для уже допущенной задачи |
| `project_report` | Обновить один постоянный комментарий в issue |
| `project_block` | Остановить работу и запросить решение оператора |
| `project_prepare_pr` | Сохранить SHA, заголовок и описание кандидата |
| `project_handoff` | Передать подготовленную операцию controller |

Привязка инструмента содержит внутренний permit текущего процесса, задачи и интервала.
Модель не передаёт repository, item ID, ветку, URL, токен, номер PR или actor оператора.
Переданный через аргументы чужой контекст не заменяет controller binding.
Merge, deployment, rerun, изменение `Agent allowed`, подтверждение dev и расширение
бюджета отсутствуют в наборе инструментов и в конечном GitHub write client.

## Порядок публикации

1. Сохранить запрос и остановить worker. При неподтверждённой остановке публикация
   остаётся закрытой. Существующий verifier по умолчанию не подтверждает остановку
   внешних процессов после исполнения hooks/Codex.
2. Получить свежее наблюдение: задача разрешена, репозиторий принадлежит этому циклу,
   dev соответствует подтверждённому deployment run и ручной проверке. Для recovery
   требуется закреплённая текущая база recovery. Старый успешный запуск на том же SHA
   не заменяет подтверждение нового запуска.
3. Зарезервировать CI до публикации. Проверить неизменяемый bundle на controller,
   записать digest и базовый SHA, затем отправить только закреплённую ветку `agent/...`.
4. Создать обычный PR в `dev` либо найти уже созданный PR той же задачи. Сохранить
   номер сразу для наблюдения CI. Заголовок/описание существующего PR не обновлять:
   это могло бы запустить лишний `edited` workflow. Закрытый PR не пересоздавать.
5. Дождаться проверок конкретного head SHA и тестового merge commit с текущим dev.
   Обновить постоянный отчёт, подтвердить native issue–PR relation, выставить
   `PR ready` и повторно прочитать результат перед внутренним `handoff`.
6. Сохранить владение задачей во время review, merge, deployment и проверки dev.
   Освобождение очереди и операторские решения остаются в delivery gate.

Комментарий имеет маркер цикла и item, проверяемого автора текущего App и сохранённый ID.
Чужой или дублированный комментарий не перезаписывается. PR содержит ссылку на issue,
а связь устанавливается `addCloseIssueReferences`, без зависимости от closing keywords
для ветки `dev`. Проверка поддержки этой операции реальным App входит в O3c.

## Ошибки CI и ручные повторы

Автоматическое исправление разрешается только при подтверждённом провале шага
`check_*` из закреплённого verify workflow, кроме проверки самого CI gate.
Это классификация по проверенным jobs/steps, а не по догадке из текста ошибки.
Ошибки установки зависимостей, timeout, cancellation, неизвестный результат и
неподтверждённый merge commit не считаются доказанной ошибкой кода.

При текущем `Actions: read` повтор без изменения кода запускает оператор в GitHub.
Controller распознаёт следующий `run_attempt` того же `run_id` и SHA, сохраняет
внешнее наблюдение и учитывает попытку в прежнем бюджете. Пропуск неизвестных попыток,
незавершённая предыдущая попытка или новый несогласованный workflow не дают успех.
После двух повторов на SHA либо шести CI-попыток цикл требует решения оператора.
Начальная работа и исправления имеют отдельные бюджеты по 60 минут; исправлений
не более двух. Ожидание CI и оператора не расходует активное время worker.

## Журнал и восстановление

`cycle.effects` — часть существующего JSON store и replay journal. У операции есть
неизменяемые payload, ID и последовательность шагов. Перед запросом сохраняется
`sent`, после проверки ответа и чтения GitHub — `confirmed`. Неизвестный результат
не разрешает повторную отправку. Controller читает GitHub и ищет постусловие;
если его нельзя доказать, задача остаётся занятой.

Отмена запрещает новые отправки, сохраняет исход и позволяет дочитать уже отправленный
запрос. Она не обещает откат запроса, уже принятого GitHub. Смена dev, разрешений или
связей может потребовать операторского разбора даже для такой сверки.
Сбой после последнего внешнего шага до `handoff` восстанавливается повторным чтением.
Восстановление store из backup по-прежнему требует явного решения оператора.

В PR-09 `runtime_contract` в scope повышен до `2`; PR-10 повышает его до `3`
для [операторских решений](operator_dashboard.md). Store предыдущего контракта автоматически
не мигрирует и не обнуляется. Несовместимый store блокирует запуск; перенос незавершённого
цикла требует отдельного согласованного восстановления. Формат контейнера snapshot
остаётся версией 1, совместимость выполнения определяется scope.

## Git и credentials

Python helper работает только на Linux, принимает один framed JSON-запрос, копирует
bundle из закрытого controller-owned каталога в новый временный bare repository.
Проверяются единственный ref, SHA, ancestry от базы и прежнего head, digest, размер,
`git fsck`, отсутствие submodules и LFS pointers. Изменения `.github/**`, `.gitmodules`
и `.lfsconfig` отклоняются. Worker configuration, hooks, credential helpers,
environment и remotes не используются. Checkout файлов проекта не выполняется.

Push использует фиксированный GitHub remote, один refspec, обычную fast-forward
проверку и собственный controller hook для сверки advertised old SHA. Force, deletion,
mirror и push в `dev`/`main` отсутствуют. Проверяется удалённый SHA после push.
Память, размер вывода/файла и CPU Git-процесса ограничены, операция имеет timeout.

Installation tokens получаются отдельно: `contents_write` для Git,
`publication` для Issues/PR и `projects_write` для поля Status. В них нет
`Actions: write`, Administration или Workflows. Токен передаётся только доверенному
Git child через askpass environment; не записывается в аргументы, bundle или store.
GitHub permissions сами по себе не ограничивают запись отдельной веткой:
это обеспечивает конечный controller publisher и будущая изоляция worker.

## Граница готовности

PR-09 не включает live Projects execution. Нет production export transport из Podman,
проверенного внешнего stop verifier и операторских кнопок. Внутренний Runtime принимает
доверенный `export_candidate(cycle, sha)`; он обязан вернуть controller-owned immutable
bundle без путей или конфигурации, выбранных worker. Production exporter и изоляция —
PR-11, WORKFLOW/hooks в agent-runner — PR-12, операторские команды/авторизация — PR-10.
До этих этапов нельзя заменять stop verifier тестовым `:stopped` и включать рабочие задачи.

Проверки: `make -C elixir all`, включая Elixir lifecycle/fault tests и Python-тесты
реального Git publisher на локальном bare remote. Они не заменяют O3c с реальным App,
нативной связью issue–PR, автоматизациями Project и фактическими Actions приложения.
