# Панель оператора — PR-10

Панель добавляет локальный вход единственной владелицы, ручную проверку dev,
паузу, сообщение о проблеме, отмену, recovery, возврат PR на доработку и добавление
бюджета. Решения сохраняет существующий `DeliveryGate`; второй store не создаётся.

**Исполнение реальных задач GitHub Projects остаётся отключено.** Этот PR проверяется
на настоящих Auth/Runtime/Gate с тестовыми наблюдениями. Изоляция и остановка реального
worker относятся к PR-11, WORKFLOW/hooks — к PR-12, общая приёмка — к PR-13.
Публикация кода, merge, deployment, создание issue и управление Cloudflare через панель
не выполняются. App сохраняет `Actions: read`: повтор запуска делает оператор в GitHub.

## Посмотреть интерфейс сейчас

Из Ubuntu WSL, под учётной записью разработчика/controller, в `D:/symphony/elixir`:

```bash
cd /mnt/d/symphony/elixir
export PATH="$HOME/.local/bin:$PATH"
unset MIX_BUILD_PATH
export MIX_DEPS_PATH="$HOME/.cache/symphony-pr06/deps"
export MIX_BUILD_ROOT="$HOME/.cache/symphony-pr10/build"
MIX_ENV=test mise exec -- mix run --no-start docs/github_projects_setup/operator-demo.exs
```

Эти cache-пути соответствуют текущей среде разработчика. На другой машине можно их
не задавать и предварительно выполнить `mise exec -- mix setup`. Каталоги сборки
`dev` и `test` должны быть разными: `MIX_BUILD_ROOT` сохраняет это разделение,
общий `MIX_BUILD_PATH` для обоих окружений может ломать тестовые протоколы LiveView.

Открыть [локальное демо](http://localhost:4081/). Скрипт печатает URL, **публичный
тестовый пароль** и путь отдельного временного store. Вставить этот пароль в форму
входа. Он подходит только для тестового демо, не для рабочего профиля.

Начальный сценарий: PR уже merged, deployment успешен, ожидается ручная проверка.
Отметить три пункта, написать комментарий и сохранить. Цикл завершится в тестовом
store; появится запись в журнале. Можно поставить паузу без активной задачи и
проверить, что обновление страницы её сохраняет. Вторая вкладка позволяет проверить
отказ старой форме после решения в первой. Выход отзывает права текущей сессии во
всех использующих её вкладках; для следующего действия нужен новый вход.

Остановка демо — `Ctrl+C`, затем `a`, если оболочка BEAM предлагает меню.
Каждый запуск создаёт новый каталог `/tmp/symphony-operator-demo-*`; это сознательно
новый тестовый цикл. Скрипт не загружает рабочий WORKFLOW, не читает App key,
не запускает Codex/hooks/publisher, не меняет GitHub или Cloudflare.
Тестовые ссылки на `ExampleOrg/app` не являются ссылками на приложение EmotionStat.

## Credential для будущего рабочего controller

Это отдельный секрет входа в панель. Ни PEM GitHub App, ни installation token,
ни сессия Codex его не заменяют. Выполнять под **controller**, не `symphony-worker`:

```bash
install -d -m 700 "$HOME/.config/symphony/operator"
mise exec -- mix operator.setup --path "$HOME/.config/symphony/operator/login-token"
```

Команда создаёт случайный секрет не менее 256 бит, файл `0600`, не печатает его и
не перезаписывает существующий. Для входа прочитать файл локально и вставить значение
в форму. Не передавать его в чат, Git, WORKFLOW, worker environment или аргументы запуска.

Проверяются Linux-путь вне `/mnt`, private directory текущего UID, обычный файл,
отсутствие ссылок и размещения внутри Git checkout. Настройка приложения дополнительно
отклоняет путь внутри `workspace.root`. Эти проверки не доказывают сетевую/OS-изоляцию:
worker не должен видеть credential, controller home, store или endpoint. Это обязательная
проверка PR-11, включая mounts и дочерние процессы.

Конфигурация будущего профиля controller:

```yaml
server:
  host: 127.0.0.1
  port: 4080
  operator:
    principal: local:nataliastaselko
    credential_path: /home/nataselko/.config/symphony/operator/login-token
```

Использовать точный абсолютный путь своего controller. Порт задаётся явно в профиле;
origin входа в этом примере — `http://127.0.0.1:4080`, а не `http://localhost:4080`.
Отсутствующий/пустой `server.operator` оставляет прежний observability-режим без
операторских прав. Добавление этого блока **не включает Projects execution** и не
обходит startup/reload guards. Рабочий launcher появится в agent-runner.

Ротация: остановить controller, создать новый credential по новому пути, обновить
конфигурацию и перезапустить. Старые сессии и формы не переживают restart. Простая
замена содержимого файла работающего процесса не является ротацией: hash загружен
при старте. Principal, путь, origin и критерии также меняются только через restart.

## Сессия и авторизация

- Один principal `local:...`, до восьми сессий. Actor берётся с сервера.
- Сессия: максимум восемь часов, 30 минут без действий. Автообновление не продлевает срок.
- Форма: 30 минут, максимум 20 форм на сессию, конкретный operation ID и версия store.
- Не более пяти неудачных входов в минуту и десяти операторских запросов свежих данных
  в минуту на сессию. Пауза, проблема и отмена не ждут сетевого чтения.
- HTTP только на loopback, точные Host/Origin и порт; `HttpOnly`, `SameSite=Strict`,
  CSRF для входа/выхода/POST и LiveView. LAN/public bind и отключённый Origin запрещены.
- HTTP/API и подключение LiveView требуют входа; каждое изменяющее событие и результат
  долгого чтения повторно проверяют сессию. Скрытая кнопка не является защитой.
- Длина комментария — до 2048 байт; HTTP body и WebSocket frame ограничены 64 KiB.
  В HTML/API выдаётся проекция разрешённых полей, а не raw store. Секреты фильтруются из логов.

Это локальный HTTP-профиль, не готовая публикация через HTTPS/reverse proxy. Не открывать
его в LAN, через tunnel или общий прокси без отдельного изменения модели доступа.

## Что делает каждая кнопка

| Действие | Сохранённый результат |
| --- | --- |
| Приостановить работу | Постоянная пауза даже без активной задачи; отзыв допуска worker |
| Обнаружена проблема | Комментарий и постоянный запрет, прежнее подтверждение базы недействительно |
| Запросить отмену | Удержание владельца и запрос остановки; PR/ветка/deployment остаются |
| Снять операторскую паузу | После свежей сверки и подтверждённой остановки снимается только эта пауза |
| Подтвердить ручную проверку dev | Три критерия и комментарий для точного SHA/run/attempt |
| Назначить recovery | Существующая разрешённая карточка Ready из того же Project/repo и отдельный явный бюджет |
| Продолжить ту же задачу | Сохранённый владелец, проверенная база и актуальный допуск карточки |
| Вернуть PR на доработку | Тот же открытый PR/head/ветка; карточку оператор сначала возвращает в Ready |
| Добавить бюджет | Только явное положительное приращение; счётчики расхода не обнуляются |
| Завершить отмену | До merge нужны закрытый/отсутствующий PR, проверенный dev и подтверждённая остановка |

Перед разрешающим действием выполняется полная свежая сверка observer. Изменения
dev SHA, run/attempt, PR head, scope, epoch/revision или watch digest отклоняют старую
форму. Открыть её заново и проверить новые данные. Пауза/проблема/отмена требуют
актуальной локальной версии, но сохраняются и при недоступном GitHub.

Двойная отправка того же operation ID и payload возвращает записанный результат.
Повтор с другим payload отклоняется. После потери ответа повторить ту же форму;
после restart войти заново и свериться с журналом. Forms не восстанавливаются с диска,
но решения остаются в store. В панели показываются последние 50 принятых решений.

GitHub и локальный store не образуют общей транзакции. Допуск и публикация ещё раз
сверяют факты после операторского решения; успешная кнопка сама не запускает агента.

Снятие операторской паузы не требует уже исправленного deployment и не удаляет
ожидающую публикацию. Оно требует свежего полного наблюдения и подтверждённой
остановки worker; проблемы среды, неизвестные результаты, cancellation и бюджеты
по-прежнему проверяются отдельно. Поэтому пауза не создаёт взаимную блокировку с recovery.

## Проверка dev, отмена и recovery

Обязательны три пункта: доступность приложения/API; контрольный сценарий с тестовыми
данными; проверка Scheduler, Queue и доставки. Конкретный бизнес-сценарий утверждается
до пилота. Контракт критериев — `local-v1` в scope fingerprint.

При готовом merged-цикле validation и соответствующее завершение (`complete`,
`finish_recovery` или `finish_cancel`) применяются **атомарно одной записью Gate**.
Окна «validation сохранена, completion потеряна» не возникает. Ошибка любого условия
не сохраняет половину перехода. До merge можно обновить подтверждённую базу у
приостановленного владельца/открытого review, сохраняя саму задачу и её бюджет.
Без активного цикла положительная validation требует полной проверки и отсутствия
открытых PR; она также не снимает операторскую паузу.

«Обнаружена проблема» всегда сохраняет отдельный `environment_problem`, даже если
deployment был успешным. Это позволяет сообщить о проблеме без положительных галочек,
без готовой среды и без активной задачи. Новая положительная validation очищает проблему,
но не операторскую паузу. Recovery назначается отдельно, второй recovery запрещён.
После исправления исходная незамерженная задача возвращается владельцу; следующая не стартует.

Отмена не закрывает PR, не удаляет ветку и не откатывает merge/deployment. Если merge
уже произошёл, завершить отмену можно через ручную validation текущего dev. Неизвестная
публикация и `stop_unconfirmed` сохраняют owner/интервал. Панель не позволяет объявить
их успешными или вернуть резерв по одному заявлению оператора. Проверенный restore
previous-копии и разрешение неизвестного интервала через UI пока недоступны: нужен
production stop verifier PR-11. Сброс или ручное редактирование JSON не предлагаются.

## Queue и оставшийся вопрос

Deployment success, готовность среды и ручная validation отображаются отдельно.
При `inherited_pause` deployment может быть успешным, но среда ещё не подтверждена.
Повторное чтение старого artifact не подтверждает ручное снятие паузы.

**Ветка со снятием паузы Queue не завершена.** Нужно выбрать: новое ручное подтверждение
оператора после проверки в Cloudflare либо автоматическое чтение через отдельный
read-only credential. До выбора и реализации панель явно сохраняет блокировку.
Галочки основной формы не заменяют это доказательство. Этот сценарий не готов к пилоту.

## Хранение, бюджеты и проверки

`runtime_contract=3`, `operator_contract=local-v1`; формат оболочки snapshot остаётся 1.
Scope старого store не подходит автоматически. Данные не удаляются и не мигрируют
в пустой цикл. После restore baseline недействительна, расход учитывается консервативно.
Сессии/формы держатся в памяти, решения — в существующем журнале с checksum/flock/fsync.

Лимиты сохраняются: 60 минут основной работы, отдельно 60 минут исправлений,
два цикла исправления, шесть CI-попыток и до двух повторов на SHA. Verify приложения —
20 минут, workflow здесь не меняется. Панель показывает расход, незакрытый резерв и
свободный остаток **вне резерва**; ожидание не расходует активное время только после
подтверждённой остановки worker. Увеличение лимитов не даёт самостоятельного допуска.

Проверки: реальные OTP-процессы и Linux store; auth/CSRF/Host/Origin/expiry/revocation;
устаревшие SHA и attempts, конкурентная пауза во время чтения, повтор решения, рестарт,
непроверенное хранилище, остановка worker и сохранение неизвестного интервала;
LiveView-форма проходит весь путь до Runtime/Gate. Полный gate — `make -C elixir all`.
Результаты конкретного прогона фиксируются в [отчёте PR-10](github_projects_setup/pr10-validation.md).

Существующие advisories зависимостей не исправляются этим PR. Предупреждения Hex
содержат в том числе проблемы HTTP/WebSocket parsing и исчерпания ресурсов в Phoenix,
Plug и Bandit. Loopback/auth не устраняют ошибки парсеров до авторизации: live-профиль
требует отдельного обновления и повторной проверки зависимостей до PR-13/пилота.
