# Управление жизненным циклом задачи — PR-08

PR-08 соединяет сохранённый цикл PR-06, наблюдения PR-07 и пути запуска Symphony.
Ветка: `agent/feat/delivery-runtime-gate`, база `main` (`befb159`) личного форка.
Проверка выполняется на управляемых worker и GitHub fixtures. Обычный startup,
CLI и reload по-прежнему запрещают исполнение `github_projects`. Пилот не включён.

## Один владелец и порядок запуска

`DeliveryGate` остаётся единственным владельцем JSON store. `DeliveryRuntime` управляет
процессами, временем и наблюдениями; вторую копию состояния для принятия решений не хранит.
В общей группе `AgentRuntimeSupervisor` используются `one_for_all`: Gate, supervisor задач,
runtime и scheduler перезапускаются вместе. Новый epoch отменяет старые разрешения.

1. Полный observer проверяет доску и репозиторий. Фильтр пилота не скрывает чужую работу.
2. Для новой задачи нужны открытая разрешённая issue, `Ready for agent`, свободный цикл
   и подтверждённый оператором текущий dev с совпадающим deployment proof.
3. Controller сохраняет owner, цикл и назначенную ветку `agent/task-<id>` от проверенного dev.
4. После записи выполняется новая сверка. Worker создаётся в состоянии ожидания разрешения.
5. `DeliveryGate.begin_work/7` сохраняет интервал и резерв времени, затем выдаёт одноразовый
   nonce, связанный с PID. До активации worker не исполняет ни hooks, ни команды.
6. `worker_check/3` разрешает одну активацию и последующие проверки только этому PID.
   Receipt повторённой команды не является разрешением запуска.

Агент проверяет допуск перед подготовкой workspace, hooks, стартом app-server и каждым turn.
Исчезновение карточки, отзыв разрешения, отмена, изменение внешних фактов или ошибка store
закрывают продолжение. Поздний запрос старого worker отклоняется без остановки его преемника.

## Ожидание, наблюдение и время

После нормального завершения worker закрывается активный интервал; repo остаётся занят.
Scheduler не использует для Projects прежний автоматический retry после `DOWN`.
Если фаза позволяет работу, новый допуск продолжает ту же задачу. CI/review/deployment/
validation/cancellation удерживают owner без постоянно работающего агента.

Observer применяется отдельно от worker. Принимается только результат для текущего
scope, epoch, revision и содержимого состояния. Изменение одного лишь временного режима
сверки не меняет fingerprint. За проход записывается один новый факт, затем выполняется
новое чтение. Повтор уже записанного результата CI/deployment не увеличивает revision
или расход. Противоречащий окончательному результату факт отклоняется.

| Ограничение | Реализация |
| --- | --- |
| Первоначальная работа | 60 минут активного времени |
| Исправления CI | Отдельные 60 минут суммарно, до двух зарезервированных циклов |
| CI | До шести попыток; до двух инфраструктурных повторов на SHA |
| Checkpoint | Каждые 10 секунд, накопленное время монотонных часов |
| Рабочее наблюдение | Период 30 секунд, deadline чтения 30 секунд, свежесть 60 секунд |
| Полная сверка при остановленном worker | Deadline 5 минут, один проход одновременно |

Рабочее наблюдение перечитывает текущие dev, Project, PR и указатели запусков; повторно
не скачивает ZIP deployment evidence. Изменение digest останавливает работу до полной
сверки. Свежесть считается от начала запроса: медленный или поздний ответ не продлевает
допуск на неопределённое время. Ошибка откладывает следующее чтение минимум на 30 секунд;
оба вида чтения учитывают `Retry-After`. Остановка worker не сокращает эту задержку.

Подготовка, hooks, Codex и локальные проверки входят в активный интервал. Ожидание Actions
и оператора вне интервала не расходует время. Deadline действует независимо от новых turns.
После неизвестного завершения интервала PR-06 сохраняет консервативный резерв. Смена
коммита, новая сессия и restart не обнуляют счётчики. Классификация инфраструктурных ошибок,
публикация и фактические rerun остаются PR-09; этот PR их самостоятельно не выполняет.

## Остановка, отмена и возврат к работе

Controller сначала сохраняет блокировку/отмену, отзывает допуск и завершает OTP worker.
Отдельный монитор связывает его жизнь с runtime даже при аварийном `kill` controller.
Общий supervisor завершает дочерние задачи при падении scheduler или Gate.

**Завершение OTP процесса не доказывает остановку всех внешних команд.** После начала
workspace/hook/app-server runtime отмечает внешние эффекты. По умолчанию такой worker
после выхода получает `stop_unconfirmed`: интервал и owner остаются заняты, новые worker
и cleanup запрещены. Сам по себе выход SSH, закрытие Port или `normal DOWN` не снимают запрет.

Доверенный transport может предоставить `stop_verifier` для проверки остановки; в PR-08
он проверяется управляемыми тестами. Реальный SSH/Podman launcher, остановка контейнера/
группы процессов и подтверждение их отсутствия относятся к PR-11. Пока этого нет, нет
производственного пути автоматического продолжения после внешних эффектов. Поле `host`
сохраняется для transport, но не заменяет доказательство остановки.

Для неподтверждённой остановки операторская запись `resolve_interval` не является
разрешением продолжить живой runtime. Необходимы внешнее доказательство остановки,
разрешение неопределённости и restart со свежей сверкой. Нельзя выдавать worker доступ
к внутренним API controller или подменять verifier постоянным успехом в рабочем профиле.

Отмена сохраняется как `cancelling`. До merge завершение требует остановки и разрешения
неизвестных операций; после merge дополнительно обязательны deployment и ручная validation.
Архивирование, `Done` или исчезновение карточки сами не завершают цикл и не удаляют файлы.

`review_resume` — внутреннее явное решение оператора: текущие PR/head, проверенный dev,
actor, reason и положительное расширение текущего бюджета. Оно возвращает ту же задачу,
ветку и PR в `reserved`, сохраняя расходы. Обычный `resume` не получил обхода review.
Назначенный recovery использует свою ветку от текущего dev и сохраняет suspended owner.
Кнопки и аутентификация оператора — PR-10.

## Контекст hooks

Hooks получают переменную окружения `SYMPHONY_DELIVERY_CONTEXT`: JSON версии 1 размером
не более 16 KiB. Поля:

- `schema_version`, `repo`, `project_number`;
- `cycle_id`, `version` (`epoch`, `revision` до открытия интервала);
- `item_id`, `issue_id`, `branch`, `interval_id`;
- `task_base_sha` — сохранённая база ветки; `expected_dev_sha` — dev текущей сверки;
- `mode`: `new`, `continue` или `recovery`.

Контекст одинаков для local/SSH. В фиксированную shell-команду попадает только Base64;
JSON, кавычки, Unicode и специальные символы не интерполируются как команды. Временный
файл не используется, поэтому нет пути его подмены symlink. Требуется POSIX `base64 -d`.
Контекст не содержит App credentials или nonce допуска и сам не даёт права публикации.
Launcher в agent-runner должен проверить base SHA до создания ветки; его git-операции
в этот PR не входят. Исполняемый продуктовый `WORKFLOW.md` остаётся в agent-runner.

## Workspace и reload

Защита стоит перед destructive cleanup и `before_remove`, в том числе в прямых вызовах
`Workspace`, failed create и обработке retry. Startup terminal cleanup для Projects
пропускается. При неизвестном/занятом цикле файлы сохраняются. Автоматически удалить
можно только workspace последней подтверждённо завершённой задачи при свежей сверке;
другие папки требуют отдельного решения. Проверка пути остаётся обязательной.

Scope, store path, repo/Project/base, identity App, фильтры, observer policy, workspace
root и worker mapping требуют restart. Некорректный или исчезнувший workflow также
закрывает допуск. Последний корректный файл остаётся доступным для диагностики, но
не отменяет `restart_required`. Автоматическое обновление installation token не меняет scope.

В fingerprint добавлены `runtime_contract=1`, `item_ids`, `required_labels` и manual
validation mode. Поэтому store PR-06/07 имеет несовместимый scope. **Автоматической
миграции нет.** Старые current/previous/lock сохраняются, загрузка возвращает
`recovery_required`. Нельзя удалять или менять hash ради открытия очереди. До пилота
нужен отдельный согласованный перенос проверенного состояния либо явное подтверждение
отсутствия незавершённых циклов для первой инициализации. Read-only inspection store не трогает.

## Что доступно для диагностики

`DeliveryRuntime.status/1` и поле `delivery` внутреннего `Orchestrator.snapshot/2` содержат
состояние Gate, owner/task, фазу, бюджет, worker interval/status, причину остановки,
наблюдение и его возраст, `restart_required`, `execution_enabled: false`.
Логи остановки содержат issue/interval IDs. Полноценной новой панели и operator API пока нет.

Для локального `remove_recorded` в Projects сохраняется проверка текущего workspace root;
сохранённый путь не разрешает удалить одноимённую папку за его пределами. Remote transport
до PR-11 не считается доказанным механизмом изоляции путей или остановки процессов.

`deployment success`, readiness по артефакту и ручная validation остаются отдельными
состояниями. `resume_queue_before_dev_validation` не превращается в ошибку кода.
После снятия паузы старый артефакт не обновляется; источник свежего состояния Queue
остаётся решением до PR-10/пилота. Этот PR не обращается к Cloudflare.

Проверки: реальные OTP процессы и Linux store, контролируемые часы, сбои записи/чтения,
одноразовые разрешения, отмена/late watch, supervisor restart, ожидание CI/deployment,
review return, recovery, workspace/reload и сохранение startup guard. Общий gate:
`make -C elixir all`. Реальные GitHub mutation, Codex, SSH/Podman и app deployment
не выдаются за проверенные этими тестами.

Итог 2026-09-16: `make -C elixir all` прошёл в Ubuntu WSL2 — 473 Elixir tests,
0 failures, 6 skipped, 100% измеряемого покрытия; 8 Python tests; format/specs,
Credo и Dialyzer без ошибок. PR body и `git diff --check` прошли. Исключения покрытия
и порог не менялись. Существующий lockfile сообщает advisories зависимостей; их
обновление остаётся отдельной работой до live runtime.
