# Постоянное состояние цикла репозитория — PR-06

PR-06 добавляет `DeliveryGate`, хранилище и внутренний контракт controller.
Исполнение `github_projects` по-прежнему запрещено проверками CLI, application
startup и reload. PR-08 подключает модуль к внутреннему lifecycle scheduler;
HTTP API и инструменты worker его напрямую не экспонируют. Сам Gate не делает сетевых запросов.

GitHub observer относится к PR-07; запуск, остановка worker и измерение времени —
к PR-08; публикация и разрешённые повторы — к PR-09; аутентификация оператора и
панель — к PR-10. Изоляция worker проверяется в PR-11. Эти тесты не включают пилот.

PR-10 добавляет [операторский контракт](operator_dashboard.md): постоянные пауза и
сообщение о проблеме, версионные решения, атомарные validation/завершение и аннулирование
baseline после restore. Текущий scope использует `runtime_contract=3`, оболочка snapshot
остаётся версии 1. Несовместимый store не мигрирует и не сбрасывается автоматически.

## Один владелец цикла

Цикл закрепляется за карточкой/issue до запуска worker. Он содержит ID цикла,
основного владельца и текущую задачу, этап, ветку, исходный/head/merge SHA, PR,
deployment с workflow/run/attempt, ручную проверку, причины блокировки, отмену,
recovery, приостановленную работу и бюджеты.

Основной путь: `reserved → working → awaiting_ci → awaiting_review →
awaiting_deployment → awaiting_validation`. Возможны `needs_human_decision` и
`cancelling`. После проверенного завершения состояние становится `idle`, а
завершённый цикл сохраняется в `last_cycle`. Это не меняет статус карточки GitHub.

Завершение worker при передаче PR не освобождает цикл. `Done`, архивирование,
удаление карточки, закрытие issue/PR без merge и timeout не являются командами
освобождения. Новая обычная задача ждёт завершения или явной корректной отмены.

## Настройки и файлы

Подготовлены дополнительные поля конфигурации:

```yaml
delivery:
  state_path: /home/CONTROLLER/.local/state/symphony/example-app/cycle.json
  base_branch: dev
```

Это не переключатель исполнения. `Config.delivery_settings/1` разбирает настройки
без создания файлов, чтения ключа App и запросов токена. Scope включает организацию,
номер Project, repo, целевую ветку и отпечаток управляющих настроек, включая identity
App/installation. Сами токены, PEM и путь ключа не сохраняются. Ротация credentials
той же identity не сбрасывает состояние; смена identity меняет контракт.

Путь должен быть абсолютным Linux-путём вне workspace и Git checkout. Для выбранного
профиля используется постоянная файловая система controller WSL2. Windows-диски
`/mnt/...` отклоняются; сетевое или временное хранилище для рабочего состояния
использовать нельзя. Каталог принадлежит controller с правами `0700`, файлы — `0600`.
Символические ссылки, hardlink-файлы и общедоступные каталоги отклоняются.

| Файл | Назначение |
| --- | --- |
| `cycle.json` | Snapshot и SHA-256 содержимого |
| `cycle.json.previous` | Предыдущая корректная версия |
| `cycle.json.lock` | Постоянный файл kernel lock и отметка инициализации |
| `cycle.json.tmp-*` | Временная запись; после аварии не признаётся snapshot |
| `cycle.json.quarantine-*` | Повреждённый файл, сохранённый при восстановлении |

Snapshot содержит `schema_version: 1`, scope, revision, состояние и ограниченный
журнал принятых команд. Каждая запись имеет ID, ожидаемую revision, действие,
аргументы и серверное время. При загрузке журнал воспроизводится и сравнивается
с состоянием: подмена отдельного счётчика или этапа не принимается. Checksum
обнаруживает повреждение, но не является подписью против владельца controller.

Ограничения пилота: 20 000 записей и 16 MiB сериализованного файла. При достижении
предела новое действие не подтверждается; история не очищается автоматически.
Перед длительной эксплуатацией потребуется отдельная процедура архивирования
с сохранением состояния и idempotency. Observer должен сохранять новые факты,
а не каждое чтение одного и того же состояния GitHub.

## Запись и единственный писатель

Один GenServer обрабатывает переходы. Приватный Linux-процесс из
`priv/delivery_store.py` держит `flock` и выполняет только операции файлового
хранения по локальному stdio. Он использует стандартную библиотеку Python 3,
не исполняет shell-команды и не обращается к сети. Его текст включён в Elixir-модуль
при компиляции, поэтому escript не зависит от расположения исходного `.py`.

Порядок: проверить команду и версию → рассчитать переход → сохранить previous →
записать и синхронизировать временный файл → атомарно заменить current →
синхронизировать каталог → подтвердить запись. Ошибка или потерянный ответ не
разрешают продолжение. После неопределённого результата сначала перечитываются
диск и внешнее состояние; слепой повтор действия запрещён.

Второй процесс с тем же файлом не получает lock. Это защита одного компьютера;
разные копии файла на разных хостах не образуют общий controller. Launcher должен
закрепить один путь за repo. Нельзя удалять `.lock` ради обхода блокировки или
повторной инициализации.

## Внутренний API

`DeliveryGate.start_link(settings: options)` запускает только владельца состояния.
Подключение к supervisor и runtime reload реализовано в [PR-08](delivery_runtime.md).
Обычный startup Projects остаётся закрытым.

- `status/1` возвращает состояние, режим допуска и version `{epoch, revision}`.
- `reconcile/4` принимает подтверждённый controller scope и текущий dev SHA для
  этой version. После restart и каждого изменения нужна новая сверка. Открытый
  интервал worker или неизвестная CI-попытка не позволяют её завершить.
- `execute/5` принимает version, ID команды, действие и ограниченные JSON-аргументы.
  Результат — **receipt записи, не токен запуска**: нужно проверить полученную фазу
  и лимиты. Например, достижение лимита сохраняет `needs_human_decision`.
- `admission/3` проверяет version, сверку, базу, владельца, бюджет и соответствие
  файла памяти. Для явно назначенного recovery подходит текущая сломанная dev.
- `check_settings/2` возвращает `restart_required` при другом пути или scope;
  живое хранилище не переключается. PR-08 вызывает эту политику из runtime reload.
- `restore_backup/4` выполняет явное восстановление с actor и причиной.
- `begin_work/7` сохраняет рабочий интервал до выдачи одноразового допуска связанному PID;
  `worker_check/3` проверяет активацию/продолжение. Nonce не восстанавливается из receipt.
- `review_resume` возвращает текущий PR/head к работе по решению оператора с дополнительным
  бюджетом; расходы, ветка и PR сохраняются. Детали и изменение scope описаны в PR-08.

Новая instance получает новый epoch. Команды старой instance отклоняются. Повтор
принятой команды с тем же ID, содержимым и исходной revision не списывает бюджет
и возвращает `replayed: true`. Другой payload под тем же ID отклоняется. Replayed
receipt не разрешает повторный запуск или публикацию; после restart читается статус.

`actor`, критерии и сведения о deployment в этом API — данные доверенных компонентов.
Они сами не доказывают личность человека, остановку процесса или успех GitHub.
PR-07 проверяет repo/workflow/ref, SHA/run/attempt, полноту результатов и среду;
PR-08 — фактический жизненный цикл worker; PR-10 — серверную авторизацию оператора.
Этот API нельзя напрямую выставлять в HTTP, worker CLI или agent tools.

## Бюджеты и неопределённый расход

Исходные пределы: 60 минут первоначальной работы, ещё 60 минут на исправления,
2 цикла исправления, 6 PR CI-попыток, 2 инфраструктурных повтора на одном SHA.
Между фазами бюджеты не переносятся. Расширение сохраняет actor, причину и добавленные
величины. Внешние ручные запуски учитываются отдельно и не увеличивают лимиты.

`start_work` сохраняет уникальный интервал и резерв доступного времени.
`checkpoint`/`stop_work` принимают накопленное время, не дельту: повторное значение
не списывается дважды, уменьшение запрещено. Локальные команды и тесты входят
в активное время. Ожидание Actions/оператора требует остановленного worker;
фраза агента «жду» не закрывает интервал.

Незакрытый интервал после аварии сохраняет блокировку. При подтверждённом точном
расходе и остановке применяется `stop_work`. Если точное время утрачено, явный
`resolve_interval` консервативно списывает весь резерв интервала либо подтверждённое
превышение. Это не возвращает потерянные минуты; дополнительное время выдаёт оператор.
Признак `accounting_uncertain` сохраняет отличие такого расчёта от точного измерения;
добавление бюджета не стирает этот признак и журнал решений.

CI сначала резервируется, затем связывается с run/attempt. Неизвестная попытка
не возвращается в бюджет. Новый SHA, отмена, restart и повтор события не обнуляют
счётчики. В review проходит последний согласованный успешный CI для указанного
head SHA; успех шестой попытки допустим.

Для достоверно не отправленного запроса предусмотрена явная команда
`confirm_ci_not_started` с actor и причиной. Она снимает неопределённость, сохраняя
расход попытки. Единичный ответ «run не найден» недостаточен: будущий controller
должен исключить ещё выполняющийся запрос или задержку появления запуска.

PR-06 не классифицирует сетевые ошибки, не выдерживает задержки и не запускает
Actions. При текущем App с Actions read повтор выполняет оператор. Автоматический
rerun, его разрешение и задержки 1/3 минуты относятся к PR-09.

## Отмена и recovery

`request_cancel` сохраняет решение и `cancelling`, но не останавливает процесс
самостоятельно. Пока worker не остановлен и неизвестные попытки не разрешены,
цикл занят. Модуль не удаляет workspace или коммиты.

До merge `finish_cancel` требует свежего подтверждения проверенной текущей dev.
После merge нужны соответствующие успешные deployment, готовая среда и положительная
ручная проверка. Отмена задачи не отменяет уже внесённый код.

Recovery назначается явно: новая карточка/ветка от текущей dev и отдельные бюджеты,
указанные оператором. Исходная работа сохраняется, обычная очередь закрыта. После
recovery и проверки dev исходный merged цикл завершается. Если основной PR ещё
не merged, возвращается его владелец с блокировкой до сверки новой базы. Отмена
recovery возвращает блокировку основному владельцу.

## Восстановление и приёмка

Нет файла и следов инициализации — нужен явный bootstrap после полной сверки;
автоматического `idle` нет. Утрата ранее созданного файла, неизвестная схема или
иной scope означают `recovery_required`.

Восстановление previous сохраняет повреждённый файл, записывает решение и меняет
epoch. Копия может отставать: доступные бюджеты незавершённого цикла консервативно
считаются исчерпанными, старое подтверждение dev сбрасывается. Сохраняются известные
значения и нижние границы неопределённого расхода (`ci_floor`, `fix_floor`,
`retry_floor`). Нужны внешняя сверка и явное дополнительное разрешение оператора;
восстановление не выдаёт бесплатных попыток. Без корректной копии этой версии
автоматическое восстановление отсутствует.

Проверки входят в `make -C elixir all`: Elixir-тесты модели, процессов и файлов,
покрытие, Python-тесты lock/fsync/replace. Моделируются аварии до/после replace,
ошибка backup, ошибка fsync после replace, потеря helper, устаревшая команда,
два писателя, повреждение и отмена. Тест завершения процесса не доказывает поведение
при физической потере питания: долговечность зависит от файловой системы и диска.

Приёмка реального controller/worker, GitHub, формы оператора и первой задачи
остаётся в следующих PR по [плану rollout](github_projects_pr_rollout_plan.md).
