# Полный установщик Symphony для Windows / WSL2

Дата: 2026-09-18. Статус: код мастера, комплекта и фонового manager реализован;
автоматические тесты описаны в [verification.md](verification.md).
Системная приёмка первой чистой установки остаётся отдельным запуском оператора.
Существующие ОС, службы, credentials и рабочие задачи при реализации не изменены.

**Решение владелицы от 2026-09-18:** автоматическое получение и распространение
установочного комплекта отложены до завершения первого пилотного запуска и разбора
его результатов. Сейчас меняется только план. Текущий Setup требует готовый локальный
комплект; сценарий «скачать fork и выполнить Setup без передачи комплекта» ещё не
реализован. Подробности отложенного этапа — в разделе 8 ниже.

## Подтверждённый результат

**Уточнение от 2026-09-18:** после обновления WSL и исправления определения
ControlGroup владелица выбрала повторную установку с нуля. Неудачная установка
удаляется только по отдельному подтверждению после проверки отсутствия задач.
Перенос её конфигурации и credentials в новый экземпляр не выполняется.
Приёмка smoke обязана удерживать обе среды одновременно и проверять реальные
лимиты CPU, памяти и процессов внутри контейнера. Результаты — в verification.md.

Владелица выбрала две отдельные среды WSL: Controller и Worker. Обычная Ubuntu
других проектов и Docker Desktop остаются вне управления установщика. Имена сред,
папка хранения и порты выбираются при установке; личные значения не входят в код.
Дополнительное решение владелицы: её компьютер проходит ту же чистую установку,
что и компьютер другого разработчика. Перенос и принятие старых сред под управление
исключены из этого этапа. Создаются две новые среды и новая локальная конфигурация.
Начальная поддерживаемая платформа — Windows x64 с WSL2. Другие платформы нельзя
объявлять поддержанными без отдельной приёмки.

Пользователь предоставляет подготовленный локальный комплект, запускает
`Symphony.cmd Setup`, проходит мастер и получает готовую установку.
`installation.json` генерируется автоматически, вручную его писать не нужно.
После настройки `Start` запускает службы и открывает панель, возвращая управление
терминалу. Закрытие терминала не останавливает установку. `Stop` подтверждает остановку
controller и worker и сохраняет незавершённую работу. `Status` показывает состояние,
`Doctor` выдаёт диагностику с конкретным следующим действием.

Setup не выдаёт агенту продуктовую задачу. После установки открывается режим просмотра.
Одна активная установка на Project остаётся явным организационным правилом:
нынешний локальный flock не является межкомпьютерной блокировкой. Передача рабочей
роли требует остановки прежнего controller и сохранения delivery store.

## Что пользователь предоставляет один раз

- Папку для установки и выбранный профиль проекта. Остальные значения мастер предлагает.
- Доступ к разрешённому профилю и комплекту поставки. Публичный fork не даёт доступа
  к закрытому agent-runner или репозиториям проекта.
- GitHub App IDs и локальный файл PEM для установки controller с соответствующими
  полномочиями. Мастер проверяет владельца, installation и доступные ресурсы через API.
  Ключ оператора не включается в общий комплект и не раздаётся другим разработчикам.
  Для режима просмотра требуется разрешённый владельцем доступ для чтения.
- Подтверждение Windows UAC и перезагрузку, если потребуется включение WSL.
- Вход в Codex через браузер и выбор модели с уровнем рассуждений из полученного списка.
- Явное назначение рабочей роли при переходе от просмотра к исполнению.

Установщик показывает эти шаги в мастере и затем продолжает автоматически. Человеку
не приходится копировать shell-команды, IDs SSH-ключей или системные конфигурации.

## 1. Основа поставки и исправление runtime

До выдачи нового комплекта исправить обнаруженный вложенный prepare.lock в
maintenance.login / Models / cleanup при сохранённом worker.json. Проверить
параллельный prepare, повторный stop, сохранение данных и восстановление после падения.
Изменение runtime требует новой принятой ревизии и обновления совместимого профиля;
старые manifest нельзя переписать для обхода проверки хеша.

Добавить версионированный manifest поставки: поддерживаемая архитектура, runtime
contract, точные commits Symphony и профиля, digest артефактов, зависимости и рецепт
сборки. Moving branch или тег latest не считается принятой версией.

Для первого установщика использовать единый проверенный комплект с архивом worker image,
исходниками/артефактом Symphony и профилем. Загрузка в Podman сверяет итоговый image ID.
Нынешний профиль ссылается на конкретный локальный base image ID; новая сборка на
другом ПК не обязана дать тот же ID. Поэтому нельзя обещать простую независимую
пересборку без поставки принятого образа либо новой процедуры приёмки результата.

Комплект не содержит состояние установки, пользовательский home, credentials, delivery
store или workspaces. Установщик не читает старое хранилище Podman для поиска образа.
Тот же комплект должен устанавливаться без старых Ubuntu и без доступа к ним.

Для текущего пилота комплект готовится локально, agent-runner остаётся локальным
по решению владелицы. Для других разработчиков потребуется доступная им поставка
разрешённого профиля. Распространение и автоматическое скачивание комплекта входят
в отложенный этап после первого пилота (раздел 8); источник и способ доступа будут
выбраны по его результатам. Публикация частного профиля или контейнера не входит
в автоматические действия установщика.

## 2. Мастер и возобновляемое выполнение

Общий код мастера — в Symphony; правила EmotionStat — в agent-runner; параметры
компьютера — вне Git. Основное локальное хранилище мастера:
`%LOCALAPPDATA%\Symphony\installations\<installation-id>` с доступом владельца.
Текущий `.runtime-local/installation.json` не импортируется. Его наличие не должно
подменять чистую установку продолжением старой. Новые параметры генерирует мастер.

Перед изменениями показать конкретный план: какие среды/каталоги будут созданы,
какие общие предпосылки Windows/WSL уже доступны, какие версии устанавливаются.
Мастер создаёт installation ID и журнал шагов без секретов. Этапы имеют состояния
pending/running/verified/needs-input/failed; verified подтверждается текущей проверкой,
а не только записью о прошлом успехе.

Повторный Setup продолжает незавершённую настройку. Он не создаёт дубли пользователей,
ключей, образов и служб и не сбрасывает состояние задачи. При сбое сохраняются точный
этап и понятная причина. Обновление версии — отдельная операция с проверкой
совместимости и сохранением прежнего состояния, а не скрытая переустановка.

## 3. WSL и две среды

Проверить версию Windows/WSL, архитектуру, виртуализацию, свободное место, доступность
источников и занятые имена/порты. Не менять общесистемный default distro или общий
`.wslconfig` ради отдельной установки.

При отсутствии WSL запустить необходимый системный шаг с UAC. Перед требуемой
перезагрузкой сохранить checkpoint; повторный Setup продолжает установку.
Регистрировать отдельные Controller и Worker из проверенного образа дистрибутива.
Если имя уже занято неизвестной средой — предложить другое, не перезаписывать её.

Создать непривилегированные accounts, служебные каталоги и приватные разрешения.
UID определяется свободным диапазоном, не копируется с компьютера владелицы.
В Worker включить systemd, отключить Windows automount и interop. Проверить
фактические mounts и возможность запуска Windows-программ после перезапуска.
Перезапускаются только принадлежащие установке среды, после подтверждённой остановки.

Важно: разные WSL-дистрибутивы не считаются независимыми виртуальными машинами.
Сетевая фильтрация остаётся ограниченной cgroup; общие правила других проектов
не изменяются. Изоляция агента обеспечивается также контейнером и проверяется отдельно.

## 4. Автоматическая подготовка controller и worker

Controller: установить Git, SSH, Python и закреплённые Erlang/Elixir; получить
принятый checkout и профиль, собрать или установить проверенный артефакт Symphony.
Все пути задаются manifest и результатами обнаружения. Отсутствие инструмента
устраняет установщик, а не инструкция пользователю установить его вручную.

Worker: установить и проверить Podman, pasta, uidmap, openssh-server, iptables-nft,
ip6tables-nft, cgroup v2 и необходимые возможности systemd. Настроить subuid/subgid
без пересечения диапазонов и пользовательский manager. Импортировать принятый образ
в rootless Podman под worker account. Runtime установить отдельной root-owned копией.

Создать отдельную пару SSH-ключей, ограниченный management endpoint на свободном
loopback-порту, конфигурацию служб и точное закрепление публичного ключа. Передача
пакетов выполняется через Windows→WSL без включения Windows mounts в worker.

GitHub App PEM импортировать в закрытый каталог controller; исходный пользовательский
файл автоматически не удалять. PEM, installation tokens и пароль панели исключаются
из логов, аргументов процессов, временных публичных файлов и комплекта worker.

Сгенерировать installation.json, Linux config, WORKFLOW, manifest и пароль панели.
Включать исполнения задач только отдельным действием после приёмки, не в Setup.

## 5. Чистая установка на компьютере владелицы

Использовать тот же мастер, пакет зависимостей, артефакты и проверки, что получит
другой разработчик. Установка должна пройти при остановленных старых Ubuntu;
наличие установленных в них инструментов, образов, ключей или config не учитывается.
Новые среды получают новые installation ID, accounts, ключи, state и отдельный
Codex login. Модель и reasoning effort выбираются заново через мастер.

Подготовленный комплект поставки и существующий GitHub App допустимы как явно
выбранные входные данные, доступные любому уполномоченному оператору. Выбор PEM
через мастер — стандартное предоставление credentials, а не копирование старой
установки. Имена дистрибутивов, домашние каталоги и GitHub IDs компьютера владелицы
в общий код не включаются.

Перед допуском новой рабочей установки проверить, что прежний controller и worker
остановлены и нет незавершённого delivery cycle. Если такие данные обнаружены,
их нужно разобрать отдельно: новая установка не служит обходом удержания задачи
или её бюджета. Начальная роль новой установки — просмотр.

Старые среды не удалять ради имитации чистого ПК. Проверить независимость новой
установки с остановленными старыми средами; общую Ubuntu не останавливать без
проверки работающих в ней других проектов. Удаление старой выделенной среды
возможно отдельной операцией после инвентаризации, проверки отсутствия нужных данных
и предъявления владелице точного имени удаляемого ресурса. Без необходимости
очистки установка создаёт новые ресурсы рядом с существующими.

Свободные имена и порты выбирает мастер. Чужая или старая служба не перехватывается;
не применять общий kill, поиск только по имени host.py, глобальное удаление образов
или unregister по предполагаемому имени. Очистка управляет только подтверждёнными
ресурсами конкретного installation ID.

## 6. Запуск без открытых терминалов

Добавить один фоновый Windows-процесс управления на installation ID. Он запускается
после явного Start, хранит проверяемую привязку к своему процессу и удерживает обе
WSL-среды работающими. Одних systemd services для этого недостаточно.
Канал управления доступен владельцу Windows-установки и поддерживает readiness/stop.

Start проверяет pins и готовность, запускает host/management/controller, ждёт доступности
панели, открывает браузер и возвращает управление. Повторный Start показывает
существующую панель. Службы не дублируются. Неуспешный запуск показывает диагноз,
а не сообщение о готовности.

Stop сначала закрывает допуск и подтверждает остановку controller и task container,
затем останавливает только свои вспомогательные службы и Windows manager. Ошибка
подтверждения сохраняет данные и сообщает, что требуется восстановление.
Не применять wsl --shutdown, global firewall flush, общий prune или unregister.

После падения менеджера, закрытия Windows-сессии, сна или перезагрузки допуск остаётся
закрыт до сверки состояния. Автоматическое продолжение задачи после входа в Windows
по умолчанию выключено. Start выполняет восстановление, не создаёт новую задачу
вместо сохранённой. Требуется тест реального закрытия всех терминалов и сна/пробуждения.

## 7. Авторизация, модель и окончательная приёмка

Мастер проводит Codex login в принятом изолированном контейнере, показывает пользователю
ссылку/код и ждёт подтверждения. Затем получает model/list, предлагает доступную
модель и reasoning effort, сохраняет выбор локально. Скрытая подмена модели запрещена.

Проверка GitHub использует read-запросы: installation, разрешённые репозитории,
Projects и требуемые поля. Создание PR, изменение Agent allowed или запуск workflow
не являются проверкой доступа в Setup.

Автоматический smoke использует фиктивный репозиторий. Он проверяет отсутствие
доступа контейнера к Windows/home/controller keys/host sockets, сетевые ограничения,
реальный SSH/pasta транспорт, stop/recovery и сохранение данных. Сохраняется отчёт
с версиями, результатами и причинами NOT_READY, без credentials.

Установка считается законченной, когда пройдена проверка среды, доступны dashboard
и разрешённые данные проекта, выбранная авторизация/модель готовы для рабочей роли,
а Stop и повторный Start подтверждены. Для режима просмотра отдельно показывается,
что исполнение задач не активировано. «Установлено», «авторизовано» и «исполнение
разрешено» — разные состояния интерфейса.

## 8. После первого пилота: получение комплекта другим разработчиком

**Статус: запланировано, реализация отложена по решению владелицы.** Сначала провести
первый пилотный запуск, разобрать его результаты и необходимые исправления, затем
уточнить этот этап и выделить отдельный PR в Symphony. Номер PR пока не назначается;
существующие PR-14/PR-15 не перенумеровываются. Этот этап не блокирует первый пилот
с подготовленным локальным комплектом и не означает разрешения публикации сейчас.

**Цель:** разработчик получает fork и запускает `Symphony.cmd Setup`; мастер сам
получает совместимые установочные компоненты. Не нужны файлы с компьютера владелицы,
её личные пути или ручная сборка worker image на каждом новом компьютере.

**Работы после пилота:**

1. Учесть результаты пилота и закрепить принятые версии Symphony, runtime, профиля
   и worker image. Выбрать хранилище выпусков, способ доступа и подтверждения
   происхождения manifest. Контрольная сумма без доверенного источника не удостоверяет
   издателя; проверка должна охватывать manifest и каждый скачанный компонент.
2. Подготовить воспроизводимую процедуру сборки и распространения версионированного
   комплекта. Общие компоненты Symphony отделить от закрытого профиля EmotionStat;
   доступность производных образов определить по их содержимому. Публичный fork
   не предоставляет доступ к частным репозиториям или профилю.
3. Добавить получение выбранного совместимого выпуска в Setup: загрузку, локальный
   кеш, проверку целостности и совместимости до импорта WSL, понятный прогресс и
   продолжение после сбоя загрузки. Несовместимые версии не подменять незаметно.
4. Получать закрытый профиль только с разрешённым доступом разработчика. Авторизацию
   GitHub/Codex, GitHub App credentials, модель и reasoning effort запрашивать или
   настраивать для конкретной установки; секреты и состояние задач не включать
   в общий комплект. Правило одного активного раннера на Project сохраняется.
5. Сохранить `-Bundle` и `-BundleSha256` как дополнительный способ указать заранее
   полученный комплект. Текущая `.runtime-local/` остаётся вне Git: размещение
   локальной сборки в ней не является распространением через fork. Не добавлять
   установочные образы, credentials или локальные настройки в историю Git.
6. Обновить инструкцию для нового разработчика и проверить путь от чистого clone
   до Setup, панели и подтверждённого Stop без доступа к компьютеру владелицы.

**Приёмка:** установка на другом чистом компьютере получает все компоненты из
разрешённых источников; личные настройки вводятся в мастере. Проверены отсутствие
доступа к закрытому профилю, обрыв загрузки, повреждённый компонент, несовместимый
выпуск и повторный Setup. Дополнительный путь с локальным комплектом сохраняет
проверки. До этой приёмки автоматическое получение комплекта не объявляется готовым.

## 9. Контроль свободного места на физическом диске Windows

в исходниках; приёмка закреплённого установленного комплекта продолжается.**
Результаты: [отчёт этапа 6](../../elixir/docs/second_pilot_stage6_report.md).
**Решение от 2026-09-22:** раздел включён в обязательный объём
[этапа 6 второго пилота](../../elixir/docs/second_pilot_implementation_plan.md#этап-6-собрать-обновить-и-проверить-комплект).
Реализация и тесты предшествуют итоговым pins/image/bundle; установленная защита
должна пройти приёмку до допуска второго пилота. Ручная проверка места служит сверкой
показаний и не заменяет автоматическую защиту.

При подготовке пилота обнаружено, что dashboard и runtime показывают свободное
пространство файловой системы внутри WSL, но не учитывают остаток на Windows-томе,
где хранятся VHDX. Виртуальная вместимость WSL может превышать физически доступное
место. Текущий `ready` не доказывает готовность по этому дополнительному условию.
Этот пункт фиксирует следующую доработку; сам по себе он не меняет работающую
установку и не переносит отложенное распространение комплекта из раздела 8.

**Реализация:**

1. Windows manager определяет тома хранения controller/worker VHDX по проверенной
   конфигурации конкретной установки и их фактическому расположению. Получает
   свободное место, доступное текущему пользователю Windows. Буква диска, пути,
   имена сред и объём диска не зашиваются. Если обе среды находятся на одном томе,
   его свободное место является одним общим запасом, а не двумя независимыми.
2. Передавать измерения controller через существующий доверенный управляющий канал
   manager с версионированным форматом, привязкой к установке/запуску, идентификатором
   тома и проверкой свежести. Worker не получает доступ к Windows-файлам, дискам,
   системным API или дополнительным mounts; граница изоляции сохраняется.
3. Для каждого хранилища учитывать минимум свободного места внутри WSL и доступного
   места на соответствующем Windows-томе. Общий остаток тома не складывать между
   controller и worker и повторно не вычитать уже занятые байты VHDX. Проверять место
   при Start, непосредственно перед допуском задачи, во время работы и после
   sleep/resume. Периодические измерения не являются резервированием пространства:
   другие программы также могут расходовать этот общий запас.
4. Сохранить текущие настраиваемые пороги: меньше 10 GiB — предупреждение; меньше
   5 GiB — запрет новых задач и штатная остановка активного worker. Рабочую папку,
   delivery cycle и неопубликованные изменения сохранять; не завершать задачу и
   не очищать её автоматически. При ошибке измерения, несовпадении привязки или
   устаревших данных показывать «состояние диска неизвестно» и закрывать допуск.
   Для потери данных во время работы использовать ограниченный срок свежести
   управляющего канала, затем останавливать worker с сохранением работы. Возврат
   свежих положительных измерений не отменяет остальные delivery/operator gates.
5. В панели отдельно показывать физический Windows-том и его общий свободный
   остаток, время последнего измерения и причину warning/blocked/unknown.
   Пространство внутри WSL подписывать как виртуальное и отображать отдельно.
   Для одного общего тома не повторять его остаток как два независимых ресурса;
   для разных томов показывать отдельные значения. Размеры файлов VHDX, если
   выводятся, не называть зарезервированным пространством или квотой агента.
6. Обновить текущую установку через проверенную совместимую версию с подтверждённой
   остановкой и сохранением авторизации GitHub/Codex, выбора модели/effort,
   конфигурации, delivery store и workspaces. Изменения Linux runtime проходят
   обычную приёмку и закрепление ревизий/артефактов; не подменять вручную прежние
   pins ради обхода проверки целостности. Удаление установки, переустановка WSL
   или уменьшение виртуальных дисков не являются способом исправления.

**Объём:** Windows manager/diagnostics и формат управляющего канала; controller
storage readiness, допуск и heartbeat; операторская панель; совместимость версии
и инструкция обновления. Код продукта и knowledge-base в эту доработку не входят.

**Приёмка:** тесты с контролируемыми значениями свободного места, без заполнения
реального диска пользователя. Проверить большой виртуальный диск при малом
остатке Windows; обратное соотношение; один общий и два разных тома; иной путь
установки; границы 10/5 GiB; падение остатка во время задачи; отказ/устаревание
измерений, restart и sleep/resume; сохранение незавершённой работы и отсутствие
автоматического обхода других пауз после восстановления места. На реальной
установке сверить отображаемый остаток с Windows, сохранность авторизации и
настроек, Start/Stop и неизменность изоляции worker.

## Разбиение реализации на проверяемые изменения

1. **Runtime и комплект поставки:** исправить nested locks, тесты сохранённой задачи,

## 10. Явный выбор первого и следующего пилота

Установка с `pilot_item_ids: []` сама не переходит к продуктовой задаче после
изменения карточки на доске. Команда `Select-Pilot -Issue NUMBER` после
подтверждённого Stop проверяет issue в заданном репозитории и Project: ровно одна
открытая карточка, Ready for agent, Agent allowed=yes и остальные ограничения.
Исходный журнал проверяется через Snapshot replay с прежним scope. Первый выбор требует
начального состояния; следующий — completed назначенной задачи и подтверждённый финальный
статус. Активная задача, recovery, отменённый цикл, неизвестная публикация, незавершённая
синхронизация, пауза или проблема среды запрещают переход. История worker допустима при
совпадении с завершённым владельцем и сохранённым подтверждением Stop. Для legacy completed
без status journal сохраняется отметка `legacy_not_recorded`, без изменения старой карточки.

Для пилота создаются отдельные config, workflow, manifest и state directory.
Исходные файлы и журнал не переписываются; ключи/авторизация сохраняются, выбранная
модель и её каталог копируются с проверкой актуальности. Подтверждение исходного
dev выполняется заново в новой области допуска. Windows descriptor публикуется
атомарно последним, после записи истории перехода. Прежняя единственная резервная копия
сохраняется; новые записи находятся в `pilot-history`. Linux intent и Windows pending-запись
позволяют повторить тот же переход после прерывания. Повтор выбора текущей задачи идемпотентен;
смена карточки разрешена только после завершения, без сброса рабочего цикла.

При новом выборе передаётся выбранная модель и проверенная запись принадлежности
остановленного worker, но не активная задача и не baseline validation. Проверки этапа 4:
[отчёт](../../elixir/docs/second_pilot_stage4_report.md). Обновление действующей установки
остаётся отдельным этапом подготовки второго пилота.

Отдельное `Start -Execute` передаёт разрешение через manager до Linux launcher.
Обычный Start не запускает выбранный пилот. Переход проверяется без продуктового
запуска, включая прерывание подготовки, сохранение старых файлов, отказ при
незавершённой работе, недопустимой карточке и изменённых подготовленных файлах.

### Согласованное изменение политики проверок

Это отдельное решение владелицы, а не автоматическое ослабление проверок при ошибке:
команды агента остаются без публичного интернета; перед PR выполняются доступные
локальные проверки, недоступные проверки явно перечисляются в отчёте/PR. Полный
`verify`, включая Docker build, обязателен в GitHub CI на текущем candidate SHA до
`PR ready` и merge. Красный, отсутствующий или устаревший CI не подтверждает готовность.
Закрепить эту политику в версии профиля agent-runner и проверить её вместе с комплектом.

### Своевременная синхронизация доски на всех этапах

**Уточнение владелицы 2026-09-18: проверить весь цикл, включая ошибки до PR.**
Статус: частично реализовано; общая синхронизация ниже ещё требует реализации.
`WriteClient.status` сейчас поддерживает только working/blocked/handoff. Изменение
карточки в начале работы и при штатном `project_block` зависит от запроса агента;
аварийный выход worker и внутренний `block` сами не создают такую запись в GitHub.
Ошибки публикации сводятся к `publication_result_unknown`, карточка может остаться
в `Agent working`. После `PR ready` переходы `merged`, `deployment`, `validate_dev`,
`complete` меняют только store. Эти пробелы нельзя закрыть одной записью после merge.

**Целевое поведение после реализации:** controller отвечает за статус карточки по
подтверждённому состоянию цикла, в том числе если агент упал до вызова инструмента.
Нельзя требовать от оператора перетаскивать карточку ради синхронизации с уже
принятым решением. Готовность и ошибка не определяются только текстом ответа модели.

| Подтверждённое событие | Статус карточки и пояснение | Граница автоматизации |
| --- | --- | --- |
| Оператор разрешил новую задачу | `Ready for agent` | Выбор задачи и `Agent allowed` остаются решением оператора; Symphony не выдаёт разрешение сама |
| Началась работа над допущенной задачей, либо возобновлена разрешённая работа | `Agent working` | Controller сохраняет и подтверждает переход независимо от вызова `project_start`; повтор инструмента не дублирует запись |
| Готовится публикация или PR уже создан, обязательный CI ещё идёт | `Agent working`; в постоянном отчёте и dashboard указать «публикация» / «ожидается CI», ссылку PR/run | Существующая доска не имеет отдельной колонки ожидания CI; новый статус не добавляется, `PR ready` преждевременно не выставляется |
| Полный CI успешен для текущего кандидата и базы, PR и связь issue подтверждены | `PR ready` | Worker остановлен; один лишь факт создания PR не достаточен |
| Оператор явно начал review | `Human review` | Сохранить явное действие оператора; не считать открытие страницы, назначение reviewer или наличие PR началом review |
| Разрешена доработка до merge, либо начался допустимый автоматический цикл исправления CI | `Agent working`, тот же PR и ветка | Проверить владельца, scope, текущую базу и бюджет; новый PR не создавать |
| Подтверждён merge назначенного PR в `dev` | `Dev validation` | В отчёте различать ожидание deployment и ожидание ручной проверки; merge не доказывает готовность среды |
| Актуальный deployment успешен, положительная проверка оператора принята для того же SHA/run/attempt | `Ready for production` | Одного зелёного deployment недостаточно; production не запускается, `Done` не выставляется |
| Нужен человек: ошибка окружения/прав, аварийная остановка, исчерпан бюджет, окончательный отказ публикации, провал deployment или ручной проверки | `Needs human decision` с конкретной причиной и следующим действием | Сохраняются workspace, ветка, коммиты и владение циклом; соседняя задача не запускается |
| Проблема устранена и принято допустимое решение о продолжении | Статус подтверждённого этапа: `Agent working`, `PR ready` либо `Dev validation` | Не возвращать в работу автоматически только по исчезновению ошибки; операторские паузы и решения сохраняются |
| Production-этап и все его проверки завершены | `Done` только по отдельному процессу выпуска/решению оператора | Текущий dev-пилот не наблюдает и не подтверждает production; внутренний `completed` не равен `Done` |

**Сроки — критерии будущей приёмки, не обещание текущей версии:** после принятия
локального события намерение обновить доску сохраняется сразу. При работающем
controller и доступном GitHub запись и контрольное чтение завершаются не позднее
60 секунд после подтверждения этапа. Внешние события проверяются с настраиваемым
интервалом, по умолчанию 30 секунд; тест измеряет отдельно задержку обнаружения и
задержку записи. Dashboard обновляет состояние автоматически, без обязательного F5.
Переходы не должны ждать завершения следующего этапа или целиком всей задачи.

При недоступном GitHub нельзя обещать изменение удалённой карточки за этот срок:
dashboard сразу показывает фактический этап, ожидаемый и последний подтверждённый
статус доски, время последнего успеха, ошибку и следующий повтор. Задержка записи
более 60 секунд заметно помечается. Повторы учитывают backoff/Retry-After; после
восстановления связи выполняется сверка без ручного повторения решения оператором.
`Human review` и прочие ручные перемещения не перезаписываются запоздалым событием.

### Ошибка до создания PR: текущее поведение и требуемое исправление

**Сейчас:** профиль предписывает агенту исправлять реальные ошибки доступных локальных
проверок и вызывать `project_block`, если требуется человек или недоступная возможность.
Штатный `project_block` сохраняет запрос, останавливает worker, обновляет постоянный
комментарий и переводит карточку в `Needs human decision` при успешных проверках и API.
При аварийном завершении runtime блокирует цикл и сохраняет работу, но запись статуса
доски не гарантирована. При ошибке push/создания PR результат сохраняется для сверки;
`publication_result_unknown` может оставлять карточку в `Agent working`. Повторные
сверки не означают автоматическое повторение уже отправленного запроса создания PR.

**Нужно реализовать и проверить:**

- [ ] Исправимые ошибки кода/локальных тестов агент исправляет в той же задаче и ветке
  в пределах оставшегося бюджета; повторяет затронутые проверки. Реальный провал
  проверки не маркируется как skip/success. Невозможность исправить или исчерпание
  бюджета переводит задачу в `Needs human decision`.
- [ ] Недоступные offline-зависимости обрабатываются по согласованной политике:
  явный skip в PR, без выдачи сети агенту, полный CI обязателен. Ошибка окружения,
  запрещающая саму работу/коммит (например, `.git` read-only), потеря авторизации или
  аварийный выход worker — отдельная блокировка, а не попытка менять продуктовый код.
- [ ] Сохранять блокировку и намерение обновить карточку из controller даже без живого
  агента и независимо от успеха комментария. Неудачная запись отчёта не должна
  бесконечно удерживать уже известную блокировку за статусом `Agent working`.
- [ ] Различать явный отказ GitHub, временную ошибку чтения и неизвестный результат
  записи. Для отказа показать этап и безопасную причину; для неопределённого push/PR
  сначала сверять точные branch/SHA/связь с циклом. Не найденный PR при неполном или
  неуспешном чтении не является доказательством отсутствия; запретить слепой повтор.
  Если результат нельзя достоверно установить за 60 секунд безуспешной сверки,
  показать `Needs human decision` (когда GitHub доступен), сохранить незавершённую
  операцию и продолжать только безопасные чтения, без новой публикации/нового worker.
- [ ] Отчёт об ошибке содержит этап, причину, что сохранено, что заблокировано,
  ссылку PR при её наличии и конкретное доступное действие оператора. Ошибка
  синхронизации доски отображается отдельно от причины остановки задачи.
- [ ] Продолжение из `Needs human decision` не требует ручного возврата карточки в
  `Ready for agent`: после решения оператора controller сверяет допуск и сам
  возвращает статус этапа. Устранить нынешнее ограничение resume только Ready/Working
  для этого пути; сохранить проверки той же issue/repo/scope, отзыва разрешения,
  паузы, бюджета и незавершённых операций. До merge сохраняются ветка, коммиты и
  существующий PR. Recovery после merge остаётся отдельной явно назначенной задачей.

### Реализация и приёмка синхронизации

- [ ] Закрепить полную таблицу этапов в контракте и версии профиля. Схема сейчас
  содержит четыре write-role; добавить необходимые роли и проверку соответствующих
  опций Project, не зашивая IDs. Не добавлять скрытую зависимость от несуществующих
  полей или новой колонки на доске. При отсутствии опции показать конкретную ошибку.
- [ ] Записи выполняет controller через сохраняемые операции, привязанные к версии
  цикла и repo/item/PR/SHA/run/attempt; успех подтверждается контрольным чтением.
  Учитывать lifecycle-события и operator actions, а не только инструменты модели.
  Отделить право отразить состояние своей карточки от разрешения запускать агента:
  ожидание review и запись блокировки не должны требовать статуса Ready/Working.
- [ ] Перед записью повторно сверять факты и ожидаемый исходный статус. Конфликт
  ручного перемещения показывать оператору; порядок столбцов не заменяет проверку
  версии (разрешённая доработка возвращает в `Agent working`). Устаревшее событие
  не откатывает новый статус. GitHub не даёт общей транзакции с нашим store:
  покрыть гонку между чтением/записью и не обещать невозможность такого конфликта.
  Не открывать заново закрытые/архивные/удалённые карточки и не считать их завершением
  цикла без доказательств merge/deployment/validation.
- [ ] Сохранять незавершённую синхронизацию через restart и подтверждённый Stop;
  различать «цикл завершён» и «статус доски подтверждён». Не терять операцию при
  переносе cycle в last_cycle и автоматическом завершении пилота. При плановой
  остановке выполнить доступную сверку; при недоступном GitHub сохранить pending
  для следующего Start, не держать процессы бесконечно и не сбрасывать проверку dev.
- [ ] Проверить каждую строку таблицы и время перехода, включая: падение до
  `project_start`/`project_block`, read-only `.git`, красный локальный тест, допустимый
  offline skip, исчерпание бюджета, отказ/потерю ответа push и PR, красный/устаревший
  CI и повторный CI, решение начать review/вернуть PR, merge, pending/failed deployment,
  ручной pass/fail, новый SHA/run attempt, ручной конфликт статуса, обрыв связи,
  rate limit, restart после `complete` и повторное событие без дубликатов/ложного `Done`.

### Оставшаяся работа и критерии завершения

- [ ] Оформить исправления Symphony/runtime и согласованное изменение agent-runner
  в проверяемые коммиты/PR с регрессионными тестами. Сохранить различие между ошибками

- [ ] Провести целевые и полные проверки итоговых ревизий, включая `make all`, тесты

  сценариев; прежний зелёный прогон не заменяет приёмку изменённого комплекта.
- [ ] Собрать комплект из закреплённых ревизий и артефактов, обновить manifest/хеши
  штатным процессом. Подтвердить, что чистый Setup получает все исправления и не
  требует ручной подмены модулей, служебных файлов или профиля.
- [ ] Проверить обновление существующей установки после подтверждённого Stop:
  сохранить GitHub/Codex-авторизацию, модель, конфигурацию, store, бюджеты и workspace;
  проверить Start/Stop и восстановление. Переустановка WSL и сброс цикла не требуются.
- [ ] Реализовать и принять автоматический контроль Windows-диска по разделу 9
  в обязательном объёме этапа 6: измерения/свежесть, допуск, остановка с сохранением
  работы, dashboard и поведение после sleep/resume. Включить изменения в итоговые
  pins и комплект; ручная проверка места не заменяет эту приёмку.
- [ ] Проверить публикацию и восстановление: при явном отказе показывать конкретный
  этап и безопасную причину; при неизвестном результате сначала читать GitHub и
  сверять identity/branch/SHA, не повторять запись вслепую и не создавать дубликат PR.
  Отдельно покрыть обрыв ответа и restart между созданием PR, связью issue и статусом.
- [ ] Подтвердить проход из установленного комплекта: выбранная разрешённая задача →
  работа → commit → push → PR → полный CI → native linkage → `PR ready` → review →
  ручной merge → `Dev validation` → deployment → ручная проверка → `Ready for production`.
  Проверить своевременные статусы и ветки ошибок из таблицы выше, без ручных
  исправлений окружения, повторов API-запросов и перетаскивания карточки вместо
  синхронизации. Обычные решения оператора о допуске, review/merge и ручной проверке
  dev остаются частью процесса; production и `Done` этим прогоном не подтверждаются.
  Следующая живая задача требует отдельного решения о rollout; тесты не расширяют
  текущий pilot filter и не разрешают автоматически взять соседнюю карточку.

**Закрытие раздела:** итоговые версии вошли в проверенный комплект, пройдены чистая
установка и обновление с сохранением данных, приложено evidence самостоятельного
прохода. До этого статус — «исправлено в текущей установке, выпуск и приёмка не
завершены». Распространение комплекта остаётся отдельным открытым пунктом раздела 8.
Учёт Windows-диска из раздела 9 включён в обязательную реализацию и приёмку этапа 6
второго пилота; до выполнения этой работы следующий пилот не допускается.

## Обязательные сценарии тестирования

Чистая установка; WSL отсутствует; требуется перезагрузка; сбой сети/пакетного менеджера;
повторный Setup; недостаток диска; занятое имя/порт; несовместимый образ/хеш;
отсутствие доступа к профилю; GitHub permission denied; незавершённый Codex login;
недоступная выбранная модель; русский путь и пробелы в PowerShell 5.1;
два одновременных Start; закрытие всех окон; sleep/resume; авария manager;
неподтверждённый stop; сохранённая незавершённая задача; отказ перехвата неизвестной
службы; независимость от старых сред и их Podman storage; отсутствие изменений
в чужих дистрибутивах. Отдельно проверить, что старый installation.json не импортирован,
в общих файлах нет персональных путей, а повторный Setup той же новой установки
сохраняет её собственные state, credentials и модель.
