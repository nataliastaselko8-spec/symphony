# Установщик Symphony для Windows / WSL2

Мастер создаёт **две новые среды**: `Symphony-Controller-<id>` и
`Symphony-Worker-<id>`. Он устанавливает зависимости, собирает controller,
загружает проверенный worker image, создаёт пользователей, ключи и конфигурацию.
Старые Ubuntu, Docker Desktop и `.runtime-local/installation.json` не принимаются
под управление. Личные пути, UID и GitHub IDs не встроены в установщик.

Первый профиль поддерживает Windows 11 x64, WSL2 и Ubuntu 26.04.
Нужны интернет для пакетов/Linux toolchain, не менее 20 GiB свободного места
и разрешённый владельцем комплект проекта. Установка WSL может потребовать UAC
и перезагрузку Windows. Состояние сохраняется перед этим шагом.

## Первая установка

Из папки **той ревизии Symphony, для которой подготовлен комплект**:

```powershell
.\Symphony.cmd Setup
```

Мастер запросит:

1. Файл `bundle.json` и его SHA256, полученный от владельца проекта доверенным каналом.
2. Каталог установки, GitHub App ID, Client ID, Installation ID и путь к PEM.
3. Подтверждение показанного плана создания двух новых сред.
4. Вход в Codex через браузер и явный выбор модели и reasoning effort из доступного списка.

PEM передаётся через бинарный stdin в закрытый каталог controller, не в аргументах
процесса. Worker его не получает. Исходный PEM не удаляется. Новый Codex login
выполняется в изолированном контейнере; старая авторизация не копируется.

Мастер сам создаёт `installation.json`, Linux config, WORKFLOW, manifest и пароль
панели. Он проверяет доступ GitHub чтением и выполняет настоящий тест контейнерной
изоляции с фиктивной задачей, без продуктового задания. Отчёт сохраняется рядом
с локальной конфигурацией. Исходники задачи позднее подготавливает controller;
контейнер получает только рабочую копию и свои инструменты.

Для проверки Windows Interop мастер передаёт небольшую копию системного `cmd.exe`
как тестовый файл. В контейнере попытка вывести безвредный маркер должна завершиться
отказом; отдельно проверяются запреты host-vsock и совместимых ABI. Диски Windows
не монтируются. Наличие общей записи `WSLInterop` у другой Ubuntu само по себе не
является ошибкой; настройки выделенной среды и контейнерная граница проверяются отдельно.

Параметры можно передать явно:

```powershell
.\Symphony.cmd Setup -Bundle "E:\release\bundle.json" -BundleSha256 HASH -InstallRoot "E:\Symphony"
```

`-SkipLogin` пропускает вход в Codex и выбор модели. Панель будет доступна,
а готовность worker останется отдельным незавершённым шагом. После установки:

```powershell
.\Symphony.cmd Login
.\Symphony.cmd Select-Model -Model MODEL_FROM_LIST -Effort EFFORT_FROM_LIST
```

## Повседневные команды

| Команда | Результат |
| --- | --- |
| `Symphony.cmd Start` | Запускает скрытый Windows manager, ждёт панель, открывает браузер и возвращает управление |
| `Symphony.cmd Open` | Открывает уже работающую панель |
| `Symphony.cmd Token` | Показывает пароль панели только в локальном терминале |
| `Symphony.cmd Status` | Показывает состояние установки, manager и controller |
| `Symphony.cmd Doctor` | Дополнительно проверяет pins, приватные файлы и доступность worker |
| `Symphony.cmd Stop` | Подтверждает остановку controller и worker и сохраняет работу |
| `Symphony.cmd Models` | После Stop обновляет доступные модели через изолированный контейнер |
| `Symphony.cmd Select-Model -Model … -Effort …` | После Stop сохраняет проверенную пару модели и уровня |

Start не требует оставлять терминал открытым. Повторный Start открывает существующую
панель. Setup, manager и обслуживание защищены общей Windows-блокировкой; runtime
сохраняет Linux flock и проверяет владение задачей. После падения manager
controller получает EOF либо теряет heartbeat и запускает процедуру остановки.
Старый stop-запрос не действует на новый процесс. Неподтверждённая остановка блокирует
следующий Start до явного Stop и сверки состояния. Автозапуск после входа в Windows
не устанавливается.

**Начальная установка работает с пустым фильтром карточек:** продуктовые задачи
не запускаются. Допуск пилота и передача рабочей роли выполняются отдельно по PR14.
Между компьютерами действует правило одного активного раннера на Project;
локальная блокировка не заменяет распределённое владение.

## Настройки и продолжение после сбоя

По умолчанию: `%LOCALAPPDATA%\Symphony\installations\<id>`. В каталоге:

- `setup.json` — комплект, этап и ограниченный журнал установки;
- `installation.json` — адреса/пути/IDs, без содержимого ключей;
- `isolation-report.json`, `readiness-report.json` — результаты проверок;
- `manager.json` — конкретный процесс, поколение и результат остановки;
- `controller.stdout.log`, `controller.stderr.log` — по 8 MiB максимум;
- `controller`, `worker` — диски новых WSL-сред;
- `installer` — проверенные копии вспомогательных программ.

Каталог закрыт Windows ACL для текущего пользователя и SYSTEM. Секреты находятся
в Linux controller/worker auth volume. Не публикуйте локальный каталог и логи.

После обычного сбоя повторите `Symphony.cmd Setup`: ID, keys и существующая
конфигурация сохраняются. Завершённый Setup проверяет свои файлы и не запускает
переустановку. Повреждённый частичный WSL import, изменённый checkout/config или
неизвестная служба требуют разбора; установщик не удаляет их ради продолжения.
Обновление принятой версии является отдельной операцией.

После первой успешной сборки controller установщик сохраняет root-owned запись
`/var/lib/symphony-installer/<id>/controller-build.json`: ревизию исходников,
версии инструментов и SHA256 исполняемого файла. Повторный Setup сверяет запись
и использует те же байты без новой сборки. Это сохраняет привязку `deployment.json`.
Изменение/удаление принятого исполняемого файла или потеря записи после создания
манифеста останавливают установку; автоматической перепривязки нет. Прерванную
первую сборку до сохранения записи и манифеста можно выполнить повторно.

Для другой установки укажите `-Installation` с полным путём к её `installation.json`.
Для продолжения незавершённого мастера укажите `-InstallRoot` с каталогом конкретного ID.
Для отдельной чистой установки укажите `-InstallRoot` с родительским каталогом без
`setup.json`: мастер создаст новый ID и две новые среды, повторно запросит GitHub App
и вход в Codex. Старые установки автоматически не удаляются. Удаление их WSL-дисков
необратимо и выполняется отдельно после проверки задач и решения владельца.
Не редактируйте сгенерированные pins вручную. `installation.example.json` — формат
для тестов, а не обязательный шаг оператора.

## Подготовка комплекта владельцем проекта

Публичный fork сам по себе не предоставляет доступ к закрытому профилю EmotionStat.
Владелец один раз готовит одинаковый комплект для разрешённых разработчиков.
Текущий agent-runner остаётся локальным до пилота; публикации установщик не выполняет.

В Linux/WSL с Python 3.11+:

```bash
python3 -I -B tools/wsl/bundle.py \
  --symphony /path/to/clean/symphony --symphony-commit FULL_COMMIT \
  --profile /path/to/clean/profile --profile-revision FULL_PROFILE_COMMIT \
  --rootfs /path/to/verified/ubuntu.wsl --mise /path/to/verified/mise \
  --image-archive /path/to/accepted-worker.tar --worker-image sha256:FULL_IMAGE_ID \
  --erlang 28.5 --elixir 1.19.5-otp-28 --output /path/to/new-release-directory
```

Профиль должен закреплять эту ревизию Symphony; финальный образ должен иметь labels
`io.symphony.profile-revision` и `io.symphony.runtime-contract=2`. После изменения
runtime обновляются профиль, образ и комплект. Старый PR13 image не является готовой
поставкой нового runtime. Архив образа получают через `podman save` из принятой сборки.

`bundle.py` проверяет чистоту checkouts, создаёт Git bundles и runtime archive,
считает SHA256 каждого файла и печатает хеш manifest. Комплект не включает home,
credentials, delivery store, установленные WSL-диски или рабочие папки задач.
Поставщик проверяет происхождение rootfs/mise и проводит приёмку образа до распространения.
Установщик сверяет комплект **до импорта WSL**, затем сверяет image ID и labels.
Он не ищет образ в старой установке разработчика.

Источники артефактов: [Ubuntu WSL и SHA256](https://releases.ubuntu.com/26.04/)
и [официальные релизы mise](https://github.com/jdx/mise/releases). Хеш manifest передаётся
отдельным доверенным каналом; checksum без доверенного хеша не удостоверяет автора.

Результаты тестов и границы приёмки: [verification.md](verification.md).
