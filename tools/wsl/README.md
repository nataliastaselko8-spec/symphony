# Установщик Symphony для Windows / WSL2

Мастер создаёт **две новые среды**: `Symphony-Controller-<id>` и
`Symphony-Worker-<id>`. Он устанавливает зависимости, собирает controller,
загружает проверенный worker image, создаёт пользователей, ключи и конфигурацию.
Старые Ubuntu, Docker Desktop и `.runtime-local/installation.json` не принимаются
под управление. Личные пути, UID и GitHub IDs не встроены в установщик.

Первый профиль поддерживает Windows 11 x64, WSL2 и Ubuntu 26.04.
Нужны интернет для пакетов/Linux toolchain, не менее 20 GiB свободного места
и разрешённый владельцем комплект проекта. Установка WSL может потребовать UAC
и перезагрузку Windows. Состояние сохраняется перед этим шагом.

## Первая установка

Из папки **той ревизии Symphony, для которой подготовлен комплект**:

```powershell
.\Symphony.cmd Setup
```

Мастер запросит:

1. Файл `bundle.json` и его SHA256, полученный от владельца проекта доверенным каналом.
2. Каталог установки, GitHub App ID, Client ID, Installation ID и путь к PEM.
3. Подтверждение показанного плана создания двух новых сред.
4. Вход в Codex через браузер и явный выбор модели и reasoning effort из доступного списка.

PEM передаётся через бинарный stdin в закрытый каталог controller, не в аргументах
процесса. Worker его не получает. Исходный PEM не удаляется. Новый Codex login
выполняется в изолированном контейнере; старая авторизация не копируется.

Мастер сам создаёт `installation.json`, Linux config, WORKFLOW, manifest и пароль
панели. Он проверяет доступ GitHub чтением и выполняет настоящий тест контейнерной
изоляции с фиктивной задачей, без продуктового задания. Отчёт сохраняется рядом
с локальной конфигурацией. Исходники задачи позднее подготавливает controller;
контейнер получает только рабочую копию и свои инструменты.

При создании локального WORKFLOW время ожидания ответа Codex (`codex.read_timeout_ms`)
по умолчанию составляет 60 секунд: первый запуск может обновлять каталог моделей.
Явное значение из шаблона проекта сохраняется. Это время ожидания ответа,
а не увеличение бюджета задачи. Существующие профили автоматически не переписываются.

Локальный профиль задаёт `workspaceWrite` для `/workspace`, `/workspace/repo` и
`/workspace/repo/.git`: агент может создавать коммиты и сохранять результаты проверок.
Отдельный корень репозитория сохраняет защиту `.codex` и `.agents`. Сеть команд агента
по умолчанию отключена: зависимости для проверок нужно подготовить заранее.
Firewall worker продолжает блокировать host/private endpoints. Диски Windows и папки
controller в контейнер не монтируются.
Явная `turn_sandbox_policy` проекта сохраняется. App-server получает тот же ограниченный
`SYMPHONY_DELIVERY_CONTEXT`, что и hooks; это данные задачи, а не полномочия или секреты.

Для проверки Windows Interop мастер передаёт небольшую копию системного `cmd.exe`
как тестовый файл. В контейнере попытка вывести безвредный маркер должна завершиться
отказом; отдельно проверяются запреты host-vsock и совместимых ABI. Диски Windows
не монтируются. Наличие общей записи `WSLInterop` у другой Ubuntu само по себе не
является ошибкой; настройки выделенной среды и контейнерная граница проверяются отдельно.

Параметры можно передать явно:

```powershell
.\Symphony.cmd Setup -Bundle "E:\release\bundle.json" -BundleSha256 HASH -InstallRoot "E:\Symphony"
```

`-SkipLogin` пропускает вход в Codex и выбор модели. Панель будет доступна,
а готовность worker останется отдельным незавершённым шагом. После установки:

```powershell
.\Symphony.cmd Login
.\Symphony.cmd Select-Model -Model MODEL_FROM_LIST -Effort EFFORT_FROM_LIST
```

## Повседневные команды

| Команда | Результат |
| --- | --- |
| `Symphony.cmd Start` | Запускает скрытый Windows manager, ждёт панель, открывает браузер и возвращает управление |
| `Symphony.cmd Open` | Открывает уже работающую панель |
| `Symphony.cmd Token` | Показывает пароль панели только в локальном терминале |
| `Symphony.cmd Status` | Показывает состояние установки, manager и controller |
| `Symphony.cmd Doctor` | Дополнительно проверяет pins, приватные файлы и доступность worker |
| `Symphony.cmd Stop` | Подтверждает остановку controller и worker и сохраняет работу |
| `Symphony.cmd Models` | После Stop обновляет доступные модели через изолированный контейнер |
| `Symphony.cmd Select-Model -Model … -Effort …` | После Stop сохраняет проверенную пару модели и уровня |
| `Symphony.cmd Select-Pilot -Issue NUMBER` | После Stop проверяет карточку и готовит профиль ровно одной задачи; ничего не запускает |
| `Symphony.cmd Start -Execute` | Явно разрешает работу выбранного пилота с сохранением всех проверок допуска |
| `Symphony.cmd Update -Bundle … -BundleSha256 …` | Готовит комплект отдельно и переносит завершённый четырёхстатусный профиль на семь статусов |
| `Symphony.cmd Rollback-Update` | Возвращает прежний комплект до первого запуска новой версии и только при неизменном состоянии |

Start не требует оставлять терминал открытым. Повторный Start открывает существующую
панель. Setup, manager и обслуживание защищены общей Windows-блокировкой; runtime
сохраняет Linux flock и проверяет владение задачей. После падения manager
controller получает EOF либо теряет heartbeat и запускает процедуру остановки.
Старый stop-запрос не действует на новый процесс. Неподтверждённая остановка блокирует
следующий Start до явного Stop и сверки состояния. Автозапуск после входа в Windows
не устанавливается.

**Начальная установка работает с пустым фильтром карточек:** продуктовые задачи
не запускаются. Допуск пилота и передача рабочей роли выполняются отдельно по PR14.
Между компьютерами действует правило одного активного раннера на Project;
локальная блокировка не заменяет распределённое владение.

### Первый и следующие пилоты

У карточки в настроенном репозитории и Project должны быть статус `Ready for agent`
и `Agent allowed = yes`. Затем в PowerShell из каталога Symphony:

```powershell
.\Symphony.cmd Stop
$pilotIssue = [int](Read-Host 'Номер новой пилотной задачи')
.\Symphony.cmd Select-Pilot -Issue $pilotIssue
.\Symphony.cmd Start -Execute
```

Команда сама находит ID карточки указанной issue в Project.
Она проверяет ровно одну открытую карточку, статус, разрешение и остальные
ограничения профиля. Сетевой сбой или отказ проверки оставляет текущий профиль.
Отсутствие незавершённой работы подтверждается повторным проигрыванием исходного
журнала с его исходной областью. Первый выбор допускает пустой профиль; следующий
требует доказанного `completed` предыдущего пилота, отсутствия активной задачи/recovery,
пауз, проблем среды и незавершённой публикации или синхронизации доски.
История остановленного worker допустима только при совпадении с завершённым владельцем.
Stop сохраняет подтверждение, связанное с конфигурацией и worker metadata; старое или
несовпадающее подтверждение требует повторить Stop после обновления комплекта.

Пилот получает новый локальный config, workflow, manifest и каталог состояния.
Прежний профиль и журнал остаются на месте; исходный Windows descriptor сохранён
в `installation.before-pilot.json` (историческая копия не перезаписывается).
Все новые переходы записываются отдельно в `pilot-history/<transition-id>.json`
и `pilot_history` descriptor. Новые настройки публикуются только после проверки
всех файлов. Повтор текущего выбора безопасен; другую карточку можно выбрать после
завершения текущего пилота. Завершённая issue из истории не создаёт новый цикл.
Установка, ключи, авторизация Codex, модель и усиление сохраняются. Исходники,
образ worker и их закреплённые версии не меняются.

В Linux `pilot-selection.json` сохраняет намерение перехода, исходные доказательства
и hashes выбранной модели. Каталоги пилотов остаются соседними, без роста вложенности.
В новый профиль переносится только проверенная binding-запись остановленного worker;
`worker.json`, delivery journal и подтверждение dev остаются у прежнего пилота.
Это позволяет распознать прежний контейнер, не присваивая его задачу новому профилю.

При прерывании повторить **ту же** `Select-Pilot -Issue NUMBER`. Если Windows уже
сохранила `pilot-selection.pending.json`, другой выбор и Start блокируются до завершения
этого перехода. Повтор завершает переключение и после замены descriptor, не создавая
дубликатов истории. Изменение подготовленных файлов, исходного журнала или модели
приводит к отказу; команда не исправляет и не удаляет их автоматически.
Если ответ Linux потерян ещё до записи Windows pending, сохранённое Linux-намерение
также запрещает Start прежнего профиля и другой выбор. Нужно повторить исходный выбор.

Старый корректный `completed` без журнала статусов сохраняется как `legacy_not_recorded`:
это известное ограничение старой версии, а не подтверждение записи в GitHub. Новый цикл
с журналом статусов требует подтверждённого финального `production_ready`.

**В новом профиле нужно подтвердить исходный dev в панели.** Старое подтверждение
остаётся в старом журнале и автоматически в другую область допуска не переносится.
`Start -Execute` открывает панель; задача может начаться только после этого
подтверждения и успешной свежей сверки. Обычный `Start` после выбора пилота
отказывается запускать его и подсказывает `-Execute`. Для последующего продолжения
этого же пилота также используется `Start -Execute`; бюджеты и журнал не сбрасываются.

## Настройки и продолжение после сбоя

### Обновление установленного комплекта

`Setup` продолжает первоначальную установку. Для принятого нового комплекта используется
явная команда из соответствующего ему checkout Symphony:

```powershell
.\Symphony.cmd Stop
.\Symphony.cmd Update -Bundle "E:\release\bundle.json" -BundleSha256 HASH
.\Symphony.cmd Doctor
```

Обновление проверяет SHA256 manifest и всех assets/helpers, закреплённые исходники,
executable, image ID и labels профиля. Новые исходники, root host config, Windows
helpers, workflow, manifest и состояние готовятся отдельно. Прежняя установка
остаётся на месте; App PEM, operator token, SSH identity и рабочие каталоги worker
сохраняются. Каталог моделей обновляется через новый image; выбранные модель и
усиление должны по-прежнему присутствовать в нём.

Миграция версии 1 поддерживает конкретный переход с четырёх на семь ролей статусов.
Смена Project, репозитория, App identity, выбранной карточки, рабочих правил или
параметров оператора этой командой не разрешается. Активный цикл, recovery,
неопределённые эффекты и неподтверждённое завершение требуют сначала разрешить
исходное состояние. Неизвестные схемы отвергаются.

Новый journal schema 2 содержит исходный snapshot и проверяемый переход; он
воспроизводится по старой и новой области. Завершённая задача, бюджеты и результаты
сохраняются; старый `completed` остаётся `legacy_not_recorded` без записи в GitHub.
Прежнее подтверждение dev сбрасывается. Новый пилот требует своего подтверждения.
Дополнительно сохраняется приватная неизменяемая копия исходных config/workflow/
manifest и файлов состояния. Она не входит в распространяемый bundle.

Windows descriptor переключается последним, после migration, isolation smoke,
чтения GitHub, проверки модели и подтверждённого Stop. Обновление не запускает
продуктовую задачу. Пока существует `update.pending.json`, Start запрещён.
При прерывании повторить Update с **тем же** bundle и SHA256. Если завершающие проверки
уже записаны, повтор проверяет их и завершает переключение без повторного обслуживания.

До первого запуска новой версии доступен `Rollback-Update`. Он проверяет hashes
обоих состояний и переключает descriptor на сохранённую версию; новые данные старым
snapshot не затираются. Первый запуск сохраняет `update-used.json` и закрывает такой
откат, даже если задача ещё не началась. Изменение файлов или выбор другого пилота
также запрещает откат. Прерванный rollback возобновляется той же командой.

### Физическое место Windows

Manager каждые 3 секунды находит VHDX обеих зарегистрированных WSL2-сред и измеряет
доступный пользователю остаток их Windows-томов. Путь установки и буква диска
не зашиты. Две среды на одном томе используют один общий остаток; размер уже
занятого VHDX второй раз не вычитается.

Измерение проходит по существующему stdin manager → controller. Версия сообщения,
установка, обе среды, поколение manager/controller, boot и возраст проверяются.
Допустимый возраст — 15 секунд, включая время сна. Worker не получает Windows API
или mounts. Эффективный остаток каждой среды — минимум между WSL и Windows.

По умолчанию менее 10 GiB означает предупреждение, менее 5 GiB закрывает допуск.
Неизвестное, ошибочное, чужое или устаревшее измерение также закрывает допуск.
Heartbeat действующей задачи передаёт потерю готовности в штатную процедуру
остановки с сохранением работы, владельца и бюджета. Возвращение свободного места
не снимает операторские паузы или другие delivery gates. Панель может оставаться
доступной для диагностики; физическое и виртуальное пространство показаны отдельно.
Свежесть проверяется при каждом обращении; heartbeat worker опрашивается каждые
10 секунд. Проверка не резервирует место от других программ.

Старые установленные config без `windows_installation_id` требуют явного обновления:
новый Windows operator не разрешает Start до него. Отдельный Linux runtime без
Windows manager продолжает использовать свои Linux disk checks.

По умолчанию: `%LOCALAPPDATA%\Symphony\installations\<id>`. В каталоге:

- `setup.json` — комплект, этап и ограниченный журнал установки;
- `installation.json` — адреса/пути/IDs, без содержимого ключей;
- `isolation-report.json`, `readiness-report.json` — результаты проверок;
- `manager.json` — конкретный процесс, поколение и результат остановки;
- `controller.stdout.log`, `controller.stderr.log` — по 8 MiB максимум;
- `controller`, `worker` — диски новых WSL-сред;
- `installer` — проверенные копии вспомогательных программ.

Каталог закрыт Windows ACL для текущего пользователя и SYSTEM. Секреты находятся
в Linux controller/worker auth volume. Не публикуйте локальный каталог и логи.

После обычного сбоя повторите `Symphony.cmd Setup`: ID, keys и существующая
конфигурация сохраняются. Завершённый Setup проверяет свои файлы и не запускает
переустановку. Повреждённый частичный WSL import, изменённый checkout/config или
неизвестная служба требуют разбора; установщик не удаляет их ради продолжения.
Обновление принятой версии является отдельной операцией.

`Start` показывает ожидание запуска и проверяет дашборд через IPv4 loopback без
системного прокси. Заголовок `Host` остаётся `localhost:<port>`, как требует вход
оператора; адрес браузера не меняется. Предыдущий подтверждённо остановленный сбой
не считается результатом новой попытки запуска.

После первой успешной сборки controller установщик сохраняет root-owned запись
`/var/lib/symphony-installer/<id>/controller-build.json`: ревизию исходников,
версии инструментов и SHA256 исполняемого файла. Повторный Setup сверяет запись
и использует те же байты без новой сборки. Это сохраняет привязку `deployment.json`.
Изменение/удаление принятого исполняемого файла или потеря записи после создания
манифеста останавливают установку; автоматической перепривязки нет. Прерванную
первую сборку до сохранения записи и манифеста можно выполнить повторно.

Для другой установки укажите `-Installation` с полным путём к её `installation.json`.
Для продолжения незавершённого мастера укажите `-InstallRoot` с каталогом конкретного ID.
Для отдельной чистой установки укажите `-InstallRoot` с родительским каталогом без
`setup.json`: мастер создаст новый ID и две новые среды, повторно запросит GitHub App
и вход в Codex. Старые установки автоматически не удаляются. Удаление их WSL-дисков
необратимо и выполняется отдельно после проверки задач и решения владельца.
Не редактируйте сгенерированные pins вручную. `installation.example.json` — формат
для тестов, а не обязательный шаг оператора.

## Подготовка комплекта владельцем проекта

Публичный fork сам по себе не предоставляет доступ к закрытому профилю EmotionStat.
Владелец один раз готовит одинаковый комплект для разрешённых разработчиков.
Текущий agent-runner остаётся локальным до пилота; публикации установщик не выполняет.

В Linux/WSL с Python 3.11+:

```bash
python3 -I -B tools/wsl/bundle.py \
  --symphony /path/to/clean/symphony --symphony-commit FULL_COMMIT \
  --profile /path/to/clean/profile --profile-revision FULL_PROFILE_COMMIT \
  --rootfs /path/to/verified/ubuntu.wsl --mise /path/to/verified/mise \
  --image-archive /path/to/accepted-worker.tar --worker-image sha256:FULL_IMAGE_ID \
  --erlang 28.5 --elixir 1.19.5-otp-28 --output /path/to/new-release-directory
```

Профиль должен закреплять эту ревизию Symphony; финальный образ должен иметь labels
`io.symphony.profile-revision` и `io.symphony.runtime-contract=2`. После изменения
runtime обновляются профиль, образ и комплект. Старый PR13 image не является готовой
поставкой нового runtime. Архив образа получают через `podman save` из принятой сборки.

`bundle.py` проверяет чистоту checkouts, создаёт Git bundles и runtime archive,
считает SHA256 каждого файла и печатает хеш manifest. Комплект не включает home,
credentials, delivery store, установленные WSL-диски или рабочие папки задач.
Поставщик проверяет происхождение rootfs/mise и проводит приёмку образа до распространения.
Установщик сверяет комплект **до импорта WSL**, затем сверяет image ID и labels.
Он не ищет образ в старой установке разработчика.

Источники артефактов: [Ubuntu WSL и SHA256](https://releases.ubuntu.com/26.04/)
и [официальные релизы mise](https://github.com/jdx/mise/releases). Хеш manifest передаётся
