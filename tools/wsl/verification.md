# Проверка установщика

Дата: 2026-09-18. Проверка кода не заменяет приёмку чистой установки.

В Linux/WSL прошли 60 runtime-тестов и 32 теста operator/bootstrap/комплекта.
Проверены настоящие приватные файлы, flock, бинарная передача, Git bundles,
отказ при изменённом checkout, безопасное извлечение архивов, сохранение работы
и остановка настоящего тестового controller после закрытия stdin владельца.
В этом тесте GitHub и управление реальным task container подменены.

В Windows PowerShell 5.1 проверены:

- 19 сценариев внутреннего operator с подменёнными WSL endpoints;
- 11 сценариев настоящих native argv/stdin, бинарных SHA256, ограничения логов,
  атомарного checkpoint, Windows ACL/mutex и проверки комплекта;
- передача argv через настоящий wsl.exe в Linux Python, включая пробелы и кавычки;
- мастер с подменёнными WSL endpoints: сбой пакетов, поздний сбой готовности,
  продолжение с тем же ID/descriptor и уже импортированным ключом, отказ от повторной
  настройки завершённой установки и от изменённых helper-файлов;
- настоящий скрытый Windows manager и дочерние fixture-процессы: готовность,
  сохранение процессов, отклонение старого stop-запроса и подтверждённая остановка.

Исправлен nested prepare.lock в maintenance.login/Models/cleanup при сохранённом
worker.json. Launcher lock удерживается; prepare lock проверяется, затем освобождается
перед recover и снова захватывается с повторной проверкой worker. Удалять сохранённую
задачу для обхода ошибки не требуется.

## Воспроизведение

Linux:

```bash
python3 -I -B -m unittest discover -s runtime/tests -p 'test_*.py'
python3 -I -B -m unittest discover -s tools/wsl/tests -p 'test_*.py'
```

Windows PowerShell 5.1:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tools/wsl/tests/test-commands.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tools/wsl/tests/test-installer.ps1 -WslDistro YOUR_TEST_DISTRO
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tools/wsl/tests/test-setup.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tools/wsl/tests/test-manager.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tools/wsl/tests/test-dashboard.ps1
```

Тесты не меняют пакеты, пользователей или службы существующих Ubuntu.
Временные файлы и дочерние процессы принадлежат только каждому тесту.

## Приёмка настоящей установки

### Первый запуск 2026-09-18: BLOCKED на codex-login

Комплект Symphony `2a92ffb1e47d228c5f0b71144ca814427205fbec` / профиль
`3875c8d8f25f60ef5b5e4257527bcb196a053e5c` прошёл начальный isolation smoke,
создание локальной конфигурации и живую GitHub read inspection. Вход в Codex
остановился до браузерной авторизации с `worker_transport_rejected`.

Диагностика двух новых сред показала:

- WSL `2.7.14.0`, ядро `6.18.33.2-2`; Controller и Worker видят одно пространство
  cgroup и одинаковые inode корня, `system.slice` и `user.slice`.
- В cgroup службы worker доступно `memory pids`, но нет `cpu`, несмотря на
  `Delegate=yes`. Журнал Podman/crun фиксирует отказ создания контейнера из-за
  недоступного контроллера `cpu`; runtime требует лимит `--cpus=2`.
- Пользовательская служба Controller `user@1000.service` завершается с
  `Failed to spawn executor: Device or resource busy`. Совпадение иерархий указывает
  на конфликт нескольких systemd в общей cgroup-иерархии; только смена порядка
  запуска не является подтверждённым исправлением.
- После сбоя read-only запрос состояния worker подтвердил `phase=idle`,
  `auth_present=false`, `network_ready=true`. Служба защиты остаётся запущена;
  контейнер входа не работает, продуктовая задача не запускалась.

Начальный smoke не доказывает устойчивую совместную работу обеих сред: нужна
повторная проверка лимитов контейнера при одновременно работающих Controller и
Worker, а также после рестарта каждой среды. Общая ошибка транспорта должна
сопровождаться безопасной диагностикой причины на стороне worker.

В [WSL 2.9.8](https://github.com/microsoft/WSL/releases/tag/2.9.8) Microsoft включила
изоляцию cgroup дистрибутивов (PR #40519 и #41073); выпуск отмечен Pre-release.
Это кандидат для проверки, а не подтверждённое исправление данной установки.
Обновление общей WSL до предварительной версии затрагивает другие дистрибутивы
и требует отдельного решения владелицы. При диагностике WSL не обновлялась,
глобальные cgroup/firewall настройки и ограничения контейнера не изменялись.
Повторный Setup без устранения причины не считается следующим шагом приёмки.

### Согласованное обновление WSL 2026-09-18: выполнено, runtime требует адаптации

После согласия владелицы новая установка остановлена штатной командой Stop:
`stopped=true`, `workspace_preserved=true`, `host_stopped=true`. Старый worker
проверен как `idle`, его оставшиеся службы остановлены перед перезапуском WSL.
Дистрибутивы, рабочие папки и credentials не удалялись и не переносились.

`wsl --update --pre-release` завершился успешно: WSL `2.9.12.0`, ядро
`6.18.40.1-1`. При одновременно удерживаемых новых Controller и Worker обе
службы `user@1000.service` стали `active`, без прежнего отказа запуска. Их systemd
находятся в разных поддеревьях `/wsl-user/distro-<id>/systemd/init.scope`.
Идентификатор cgroup namespace и корень файловой системы cgroup остаются общими;
разделены именно поддеревья дистрибутивов. Эти динамические IDs нельзя закреплять
в конфигурации или исходниках.

Полный штатный `runtime_smoke.py` при обеих работающих средах остановился с
`firewall_cgroup_missing`: текущий HostSession ожидает службу непосредственно
в `system.slice/`, не учитывая новое поддерево WSL. Это несовместимость runtime,
а не успешная приёмка после обновления. Временные службы smoke остановлены.

Отдельная проверка под `symphony-worker` с явным XDG runtime directory и
`--cgroup-manager=cgroupfs`, `--cgroupns=private` подтвердила реальное применение
лимитов в одноразовом контейнере без сети и host volumes:
`cpu.max=200000 100000`, `memory.max=2147483648`, `pids.max=512`.
Это проверка возможностей контейнерной платформы; она не заменяет полный smoke
с сетевой политикой, SSH, restart и рабочим runtime.

Для продолжения требуется определять фактический ControlGroup выделенной службы
через systemd и согласовать этот путь с guardian, сетевой политикой и проверками
владения operator. Нельзя подставлять общий ancestor или отключать firewall/лимиты
ради прохождения проверки. После исправления нужны новый проверенный комплект
и явная процедура продолжения незавершённой установки с сохранением её данных;
подмена файлов уже принятого комплекта и его хешей не выполняется.

До этого исправления повторный Setup/вход в Codex заблокирован. Продуктовые задачи
не запускались. Другие проекты Ubuntu/Docker Desktop после обновления отдельно
не проверялись.

### Исправление runtime и решение о чистой установке 2026-09-18

Runtime определяет полный ControlGroup службы через systemd, включая динамическое
поддерево WSL. Firewall принимает только выделенную `symphony-*.service` внутри
`system.slice`; ancestor, другой unit, traversal и смена inode запрещены. Supervisor
и guardian проверяют наличие `cpu`, `memory`, `pids`. Общие политики WSL не меняются.

Полный реальный smoke при одновременно работающих Controller и Worker прошёл:
ограничения CPU/памяти/pids и файла 256 MiB, отсутствие host mounts, IPv6 cgroup
canary, блокировка приватной сети через pasta, публичный HTTPS, forced-command SSH,
экспорт после остановки, отдельный login-контейнер, deadline, утрата controller,
авария и restart guardian с сохранением работы. Время остановки при утрате controller
— 45,42 секунды. Один DNS-запрос истёк по таймауту; предусмотренный повтор HTTPS
прошёл. Это не проверка браузерной авторизации Codex.

Проверки кода: 65 runtime Python tests, 32 installer/operator/bundle tests;
19 сценариев operator и 10 native/installer сценариев в Windows PowerShell 5.1;
мастер с прерыванием/продолжением и скрытый manager — PASS. В тестовой имитации
shutdown ack устранена гонка: файл публикуется атомарно с правами 0600.
Реальный runtime не ослабляет проверку приватности ack.
Setup теперь удерживает controller во время isolation smoke, чтобы проверять
совместную работу обеих systemd-иерархий.

Владелица выбрала **новую установку с нуля**, затем отдельно подтвердила удаление
неудачной установки. Проверено отсутствие задач, bindings, рабочих копий,
авторизации Codex и активных служб. Удалены только её два дистрибутива и каталог
данных, а также указатель `current.json` на неё. Исходный PEM, репозитории,
обычная Ubuntu, прежняя ручная Ubuntu-26.04 и Docker Desktop сохранены.
Механизм обновления/переноса незавершённой установки в этот фикс не входит.
Новый комплект собирается отдельно; исходный принятый комплект не изменяется.

### Дополнительный отказ host preflight и исправление Interop 2026-09-18

Вторая чистая установка остановилась на `worker-image-and-host` с общим
`command_failed_python3`. Прямой запуск диагностики показал единственный отказ:
`dedicated_wsl_settings / wsl_restart_required`. Образ, IDs, пакеты, cgroups и
остальные prerequisites были готовы; в обоих wsl.conf Interop выключен и диски
Windows не смонтированы. Браузерный login и продуктовые задачи ещё не запускались.

Причина ложного отказа — требование отсутствия записи `/proc/sys/fs/binfmt_misc/WSLInterop`.
Реестр общий для VM, поэтому его сохраняет обычная Ubuntu с включённым Interop.
Это согласуется с [реализацией защиты binfmt в WSL](https://github.com/microsoft/WSL/blob/master/src/linux/init/init.cpp)
и [настройками Interop для отдельных дистрибутивов](https://learn.microsoft.com/en-us/windows/wsl/wsl-config#interop-settings).
Глобальная запись не удаляется. Preflight проверяет настройки и отсутствие Windows
mounts, включая нестандартные точки; принятие контейнера остаётся отдельным gate.

Расширенный smoke выявил, что стандартный профиль Podman допускает AF_VSOCK.
Runtime теперь сужает системный deny-by-default seccomp-профиль: только x86_64 ABI,
socket/socketpair только Unix/IPv4/IPv6/netlink, без socketcall и host AF_VSOCK.
Остальные ограничения профиля сохранены. Root-owned результат и его SHA256 связаны
с lease; guardian и supervisor обнаруживают изменение и закрывают gate.

При работающих новых Controller/Worker и обычной Ubuntu с Interop полный smoke
прошёл: `HOST_VSOCK_BLOCKED`, `COMPAT_ABI_BLOCKED`, `WINDOWS_EXECUTION_BLOCKED`,
ресурсы/файловая граница/публичный HTTPS/приватная сеть/SSH/остановка/экспорт/restart
guardian — PASS. Остановка при утрате controller: 45,51 секунды. Canary — копия
системного cmd.exe с командой печати маркера; без Windows mounts и без секретов.

71 runtime test, 33 installer/operator/bundle tests и сценарий PowerShell wizard
прошли. Неуспешный host preflight теперь возвращает конкретный ограниченный код
причины вместо потери JSON-диагностики в `command_failed_python3`.
Владелица выбрала чистую установку вместо переноса. Неудачные WSL-среды и их
сгенерированные данные удалены отдельно по её запросу; исходный PEM и репозитории
сохранены. Обновление незавершённой установки не выполнялось.

### Повтор Setup после прерывания входа 2026-09-18

Повторная установка дошла до `local-configuration`, но `pin` отказал с
`manifest_exists_choose_new_local_profile`. Сравнение манифеста подтвердило:
изменился только `artifact_sha256`; config, workflow, runtime и ревизии совпадали.
Этап controller при каждом продолжении повторял `mix build`, заменяя уже принятый
escript другим архивом. Контроль целостности манифеста сработал правильно.

После успешной сборки provision сохраняет атомарную root-owned запись с ревизией,
toolchain, хешем mise и исполняемого файла. При продолжении проверяются запись и
существующий исполняемый файл; повторная сборка и автоматическое принятие нового
хеша запрещены. Неполная первая сборка до записи/манифеста допускает повтор.
Пропажа записи после создания манифеста требует разбора вместо перезаписи файла.

Проверки: 38 installer/operator/bundle tests, 71 runtime test и Windows PowerShell
5.1 wizard interruption/resume — PASS. Регрессионные сценарии покрывают сохранение
байтов и манифеста, повреждение/удаление артефакта, изменение toolchain, повреждение
и подмену записи, её потерю после конфигурирования и прерванную первую сборку.
На настоящем escript из закреплённого checkout также выполнены сборка, создание
манифеста и два продолжения: SHA256 и байты манифеста сохранились, повторных вызовов
mise/mix не было. Полный интерактивный Setup нового комплекта ещё предстоит.

По явному запросу владелицы установка, остановившаяся на этой ошибке, удалена.
До удаления подтверждены idle, отсутствие рабочих копий, экспортов и Codex auth;
штатная остановка supervisor подтверждена. Остальные WSL-среды сохранены.

### Таймаут готовности Windows Start 2026-09-18

Полный Setup завершился: реальный вход Codex, каталог моделей и выбор effort
сохранены. При Start controller и дашборд запустились, но Windows manager не
подтвердил готовность. В PowerShell 5.1 обращение к localhost занимало около
2,18 секунды из-за неработающего IPv6 loopback, превышая таймаут пробы в 2 секунды.
Запрос по IPv4 с исходным Host проходил за 1–25 мс. Прямая замена URL на IP без
Host не подходит: проверка origin оператора правильно возвращает 403.

Проверка теперь использует IPv4 loopback, сохранённый Host, отключённый для этой
пробы прокси, ограниченные таймауты и не следует перенаправлениям. Отдельно
исправлено чтение старого attention-required до записи состояния нового manager;
Start показывает, что ожидает дашборд.

Проверены настоящие HTTP-соединения PowerShell 5.1 с IPv4-only fixture: 200,
перенаправление, 503, таймаут и обход тестового прокси. Процессный тест воспроизводит
старую ошибку при задержке нового manager и подтверждает Start/Stop, удержание
дочерних процессов и отказ устаревшей команды Stop. Также прошли 19 сценариев
operator и wizard interruption/resume. 10 native transport/installer сценариев
прошли с явно заданным `[Console]::InputEncoding = New-Object Text.UTF8Encoding($false)`:
без этого окружение тестового запуска добавляло BOM в бинарный stdin. Этот
отдельный вопрос кодировки не меняет реализацию HTTP-проверки.

У существующей завершённой установки Windows helpers можно исправить отдельно
от Linux runtime: только после подтверждённой остановки и сверки старых hashes,
с резервными копиями, записью ревизии исправления и новых hashes. Pins runtime,
образ, авторизация и descriptor при этом не меняются. Это адресное исправление
пилота, не реализация общего механизма обновления установок.

Исправление Windows helpers из `ddcf123` применено к остановленной пилотной
установке с отдельной записью hashes и резервной копией. Реальный Start подтвердил
готовность примерно за 10 секунд; затем Stop и повторный Start прошли. Manager
показывает ready, controller работает, worker готов и idle, Codex auth и выбранные
модель/effort сохранены, активной задачи нет. Linux pins и descriptor не менялись.

### Приёмка после исправлений

На пилотной установке пройдены полный Setup на двух новых WSL-дистрибутивах,
реальный isolation smoke, GitHub read inspection, новый Codex login, model/list
и выбор effort. Start/Stop/повторный Start проверены после адресного исправления
Windows helpers; manager продолжает работу после выхода запускающей команды.
До признания новой полной поставки принятой остаётся чистый Setup из комплекта,
уже включающего это исправление, закрытие окна терминала, сон/пробуждение Windows
и остановка при утрате manager.
Установщик выполняет bootstrap, smoke и доступные проверки; браузерный login
и проверка Windows после сна требуют участия оператора.

Пройденные проверки не заменяют оставшуюся приёмку полного комплекта. Старые
credentials не переносились. Продуктовый пилот, задачи, PR и деплой не запускались.
